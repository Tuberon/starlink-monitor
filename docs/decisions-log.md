# Журнал рішень

Хронологічний запис значущих технічних рішень і знайдених багів.

## Виявлення реальної схеми gRPC (не за здогадками)

На старті проекту помилково припускалось, що Starlink Mini — єдиний
пристрій. Живі виклики `grpcurl describe` на dish (`192.168.100.1:9200`)
і router (`192.168.1.1:9000`) підтвердили: це два окремі логічні
пристрої з різними `DeviceInfo`, різними enum станів оновлення
(`SoftwareUpdateState` vs `WifiSoftwareUpdateState`), різними наборами
alert-полів (`DishAlerts` 19 полів vs `WifiAlerts` 21 поле). Уся
подальша логіка (`starlink_client.py`, `labels.py`) побудована на
цих підтверджених схемах, не на припущеннях.

**Практика, що склалась**: для будь-яких технічних даних (розміри
плат, protobuf-схеми, назви enum) — підтверджувати через `grpcurl
describe`/web_search/фото, не вигадувати правдоподібні числа.

## Баг: конфлікт параметра `timeout` в Telegram API

**Симптом**: `TypeError: got multiple values for argument 'timeout'`,
бот не отримував жодних вхідних команд, помилка тихо гасилась у
`except Exception` кожні 5с.

**Причина**: `_api_call(method, token, timeout, **params)` мав
формальний параметр `timeout`, а виклик `getUpdates` одночасно
передавав HTTP-таймаут позиційно і Telegram API параметр
`timeout=POLL_TIMEOUT_SEC` (long polling) як іменований — колізія.

**Виправлення**: перейменовано внутрішній параметр на `http_timeout`.

## NoNewPrivileges вимкнено на webui та shutdown-button сервісах

`starlink-webui.service` і `starlink-shutdown-button.service`
навмисно **без** `NoNewPrivileges=true` — обидва викликають
`sudo systemctl reboot/poweroff` (ручний reboot/shutdown Pi через
веб-інтерфейс і через фізичну кнопку). `NoNewPrivileges` на рівні
ядра блокує будь-який `sudo` незалежно від `/etc/sudoers`, тож із
цим прапорцем ці виклики не спрацювали б.

`starlink-monitor.service` лишається з `NoNewPrivileges=true` —
той процес sudo не викликає.

## Фізична кнопка виключення: окремий процес, не інтеграція в існуючі

**Рішення**: `app/shutdown_button.py` — окремий Python-модуль і
окремий systemd-сервіс, не частина `monitor.py`/`webapp.py`.

**Чому окремо**:
- GPIO-доступ вимагає групу `gpio` і системний `python3-libgpiod`
  (apt, не pip — чистіше на Raspberry Pi OS) — зайва залежність для
  установок без фізичної кнопки
- Вимкнено за замовчуванням (`SHUTDOWN_BUTTON_GPIO_PIN=0`), сервіс
  одразу виходить — не критична помилка, якщо кнопки немає
- `Restart=on-failure` (не `always`) свідомо: чистий вихід при
  вимкненій кнопці не має спричиняти нескінченний рестарт-цикл systemd

**Побічний ефект**: venv тепер створюється з `--system-site-packages`
(щоб бачити системний `gpiod`) — це змінює поведінку venv для *всіх*
пакетів, не лише gpiod (венв тепер бачить будь-який системний Python-
пакет). Прийнятний компроміс, бо альтернатива (pip-встановлення
gpiod з компіляцією C-розширення) менш надійна на слабкому Pi Zero 2 W.

**Третя зміна NoNewPrivileges**: аналогічно до `starlink-webui.service`
(див. розділ вище), `starlink-shutdown-button.service` теж без
`NoNewPrivileges` — потребує sudo для `poweroff`.

## Баг: reboot-loop при невдалій auto-reboot команді

`last_reboot_ts` оновлювався лише при `reboot_dish() == True`. Якщо
dish ще перезавантажується з попередньої спроби (`connection
refused`), команда reboot теж провалюється — `MIN_REBOOT_INTERVAL_SEC`
ніколи не спрацьовував, watchdog повторював спробу reboot щоцикл
опитування (кожні ~10с) замість одного разу на заданий інтервал.
Виправлено: `last_reboot_ts` оновлюється при кожній *спробі*,
незалежно від результату.

## Налаштування статичних IP (eth0/wlan0) в install.sh — інтерактивне, не автоматичне

Мережева конфігурація (USB-Ethernet + WiFi Starlink) ризикована для
автоматичного застосування без підтвердження — неправильні дефолти
(наприклад, конфлікт підмереж з реальною домашньою мережею) можуть
обірвати SSH-з'єднання, яким адмінить сам Pi. `install.sh` тому
питає підтвердження (`[т/N]`) і дозволяє ввести власні IP/gateway
замість дефолтних, а не застосовує зміни мовчки. `dhcpcd` вимикається
лише в межах цього опційного кроку (не для всіх встановлень) — він
конфліктує з NetworkManager, перевидаючи власні DHCP-лізинги
незалежно від `ipv4.method=manual` у профілі nmcli.

## Баг: gpiod v2 несумісний зі старим API кнопки виключення

**Симптом**: `'Chip' object has no attribute 'get_line'`, сервіс
`starlink-shutdown-button` одразу завершувався з помилкою.

**Причина**: `python3-libgpiod` на Raspberry Pi OS Bookworm+ ставить
gpiod **2.x**, де Python API повністю переписано (`chip.get_line()` +
`line.request()` з v1.x видалені; замість них — `gpiod.request_lines()`
з `LineSettings`, значення через `Value.ACTIVE`/`Value.INACTIVE`
замість `0`/`1`). Код спирався лише на v1 API.

**Виправлення**: `_init_line_v1`/`_init_line_v2` — обидві реалізації,
вибір через `hasattr(gpiod.Chip, "get_line")` (є лише в v1). Значення
з v2 конвертується в 0/1 всередині обгортки `get_value()`, решта
логіки (`watch_button()`) не залежить від версії API.

## Мережевий запит install.sh — лише при першому встановленні, не при оновленні

Питання про статичні IP (eth0/wlan0) обгорнуто умовою `MODE == "install"`
— мережа налаштовується один раз і не потребує перезапиту при кожному
`update.sh`/повторному `install.sh`. `scripts/uninstall.sh` — окремий
файл (не прапорець у `install.sh`), щоб не ускладнювати основний потік
встановлення умовними гілками, які рідко використовуються.

## Придушені конкретні Telegram-сповіщення (журнал не зачіпається)

`MUTED_DISH_ALERTS={"roaming"}`, `MUTED_ROUTER_ALERTS={"install_pending"}`,
`MUTED_ROUTER_UPDATE_STATES={"GETTING_TARGET_VERSION_FAILED"}` — на
запит користувача ці три конкретні події не надсилаються в Telegram
(шумні/непрактичні для сповіщення в реальному часі), але й далі
пишуться в журнал подій дашборду. На відміну від `IGNORED_ROUTER_ALERTS`
(повне ігнорування, включно з БД/журналом) — тут приховується лише
Telegram-звіт.

## Telegram-сповіщення про початок/кінець циклу оновлення ПЗ dish

`DOWNLOADING_UPDATE_STATES={"FETCHING","PRE_CHECK","WRITING","POST_CHECK"}`,
`ACTIVE_UPDATE_STATES` = той самий набір + `REBOOT_REQUIRED`. Перехід
з "не активного" стану в один з `DOWNLOADING_UPDATE_STATES` → "🔽
Розпочато оновлення"; повернення з будь-якого активного стану в
`IDLE` → "✅ Оновлення завершено". `REBOOT_REQUIRED`/`FAULTED`
перевіряються першими в ланцюжку `if/elif`, зберігаючи власні
специфічні повідомлення навіть при прямому переході `IDLE →
REBOOT_REQUIRED` (рідкісний edge case, коли поллінг пропустив
проміжні стани).

## Обмеження журналу watchdog-спроб при дуже тривалій недоступності

`consecutive_failures` не має верхньої межі й зростає на кожному
циклі опитування (10с), поки dish недоступний — при багатогодинній
відсутності WiFi Starlink лічильник сягає тисяч, і кожна watchdog-
спроба (кожні `MIN_REBOOT_INTERVAL_SEC`) писала окремий запис у
журнал/БД з дедалі більшим числом, без нової корисної інформації.
`MAX_LOGGED_CONSECUTIVE_FAILURES` (30) обмежує запис: спроби 1-30
логуються нормально (`watchdog_trigger` + `dish_reboot`), спроба 31
дає один фінальний маркер ("Понад 30... подальші спроби не
записуються"), спроби 32+ мовчать у журналі — але сама функція
`reboot_dish()` викликається на кожному циклі без змін, лише запис
у БД припиняється.

## Баг: Telegram-бот блокувався на повільних командах

**Симптом**: бот деколи довго (до ~15с) відповідав на команди.

**Причина**: `_handle_update()` (обробка `/status` тощо, з блокуючими
gRPC-викликами до dish/router — таймаут до `DISH_HTTP_TIMEOUT`+
router-таймаут ≈15с) виконувалась синхронно в тому самому потоці,
що й `getUpdates` polling-цикл. Поки одна команда оброблялась,
наступний `getUpdates`-запит і будь-які нові команди чекали.

**Виправлення**: `ThreadPoolExecutor(max_workers=3)` — кожен update
обробляється в окремому потоці, `_poll_once()` одразу повертається
до наступного `getUpdates` незалежно від тривалості обробки.

**Побічний ефект, виявлений і виправлений одразу**: паралельна
обробка усувала гарантію порядку виконання — `/reboot` і миттєвий
клік підтвердження від того самого користувача могли потрапити в
різні потоки пулу й завершитись у довільному порядку (callback міг
обробитись раніше за встановлення `_pending_reboot_confirm` командою
`/reboot`). Виправлено групуванням updates за `chat_id` у межах
кожного `getUpdates`-batch: той самий чат обробляється послідовно в
одному потоці (гарантує порядок), різні чати — паралельно (швидкий
чат не чекає повільний).

## Рефакторинг: спільний хелпер для update-ready reboot (dish + router)

`_maybe_reboot_for_update`/`_maybe_reboot_for_router_update` містили
майже ідентичну логіку (auto_reboot_enabled, MIN_REBOOT_INTERVAL_SEC,
insert_event, reboot_dish, notify) — об'єднано в `_reboot_for_update_ready`.
Виявлено й виправлено принагідно **другий екземпляр** того самого
reboot-loop бага, що вже виправлявся для watchdog-шляху: `last_reboot_ts`
оновлювався лише при `ok == True`, тому невдала спроба reboot при
update-ready стані не захищала від негайного повтору на наступному
циклі. Виправлено так само — оновлюється завжди, незалежно від
результату.

## Backup/restore розширено на параметри моніторингу (app/config.py)

`format_version` 1→2: `env_params` у backup містить лише **реально
перевизначені** (`overridden: True` з `config_editor.read_current_values()`)
env-параметри, не всі значення за замовчуванням — інакше відновлення
на іншій версії коду затерло б нові дефолти застарілими значеннями з
моменту створення backup. Restore записує їх через той самий
`config_editor.save_values()`, що й панель "Параметри моніторингу" —
застосовуються після перезапуску сервісів, не автоматично (щоб
restore не спричиняв неочікуваний рестарт сервісів сам по собі).

## Рефакторинг: усунення дублювання коду (webapp.py, telegram_notify.py)

`api_system_reboot`/`api_system_shutdown` (webapp.py) — спільна
логіка (виконати команду, журнал, Telegram) винесена в
`_execute_pi_power_action`, з параметризацією конкретних дієслівних
форм повідомлень (щоб текст лишався природним, не узагальненим).

## Баг: StartLimitIntervalSec/StartLimitBurst у [Service] замість [Unit]

**Симптом**: systemd попереджав `Unknown key 'StartLimitIntervalSec'
in section [Service], ignoring` при кожному старті
`starlink-grpc-fetch.service`.

**Причина**: ці директиви ("Unit start rate limiting") належать до
розділу `[Unit]`, не `[Service]` — у неправильній секції systemd
просто ігнорує їх, обмеження кількості спроб перезапуску (5 за 30хв)
не діяло взагалі.

**Виправлення**: перенесено в `[Unit]`.

## fetch_starlink_grpc.sh: завантаження через eth0 насамперед

wlan0 (WiFi Starlink) навмисно має нижчий route-metric за eth0 (щоб
трафік до dish/router завжди йшов через WiFi) — але це ж означає, що
дефолтний маршрут для ЗОВНІШНЬОГО інтернету (завантаження
`starlink_grpc.py` з GitHub) теж намагається йти через wlan0 першим.
Якщо супутниковий канал Starlink саме недоступний (dish щойно
ввімкнувся, обслуговування, погода), інтернету через wlan0 немає
взагалі, попри робочий eth0 (домашня мережа). Виправлено: скрипт
пробує `curl --interface eth0` спочатку (якщо eth0 підключений), і
лише за невдачі падає на дефолтний маршрут.

## Telegram-сповіщення мовчали при відсутньому інтернеті на Starlink

Той самий root cause, що й для `fetch_starlink_grpc.sh`, але для
Python-коду: `requests.post`/`requests.get` до `api.telegram.org`
теж ідуть через дефолтний маршрут (wlan0), який не має інтернету,
коли супутниковий канал Starlink недоступний — саме тоді, коли
сповіщення про проблему найпотрібніші.

`telegram_notify._request_with_eth0_fallback()` — спільний хелпер:
звичайний запит спочатку, і при мережевій помилці - явний retry з
`requests.Session` + кастомний `HTTPAdapter`, що прив'язує сокет до
IP-адреси eth0 (`_get_eth0_ip()`, ioctl `SIOCGIFADDR`, Linux-специфічно).
Застосовано в `send_message()`, `test_connection()` (telegram_notify.py)
і `_api_call()` (telegram_bot.py, спільний для getUpdates/відповідей
на команди).

## Оптимізація для мобільних (смартфон/планшет)

Перевірено живими скріншотами (Playwright, 320-768px). Виправлено:
`.status-row-label{min-width:150px}` + `.progress-track{width:140px}`
переповнювали рядок на екранах <480px навіть з flex-wrap (кожен
елемент мав власний мінімум ширини, сума перевищувала viewport) —
на `max-width:480px` обидва стають `100%`/гнучкими. Додано
`viewport-fit=cover` + `env(safe-area-inset-*)` для iPhone з
"чубчиком", `-webkit-tap-highlight-color:transparent` + власні
`:active`-стани кнопок (hover не спрацьовує на дотик), збільшений
touch target кнопок на `<600px` (`min-height:44px`, за рекомендацією
Apple/Google), компактніший header і менші відступи на `<600px`,
додатковий брейкпоінт `<360px` (2-колонкова сітка, приховано підзаголовок
у header). Планшет (768px) не потребував окремих правил — наявний
`auto-fit` grid адаптується природно.

## Cache-busting для JS/CSS (застарілий кеш браузера після update.sh)

**Симптом**: після зміни коду (напр. ліміту журналу подій) браузер
користувача показував стару поведінку — `SEND_FILE_MAX_AGE_DEFAULT=3600`
кешує статику на годину, і без ручного hard refresh браузер продовжує
використовувати стару версію `dashboard.js`.

**Виправлення**: `webapp._static_v(filename)` (Jinja-глобал `static_v`)
додає `?v=<mtime файлу>` до URL `dashboard.js`/`settings.js`/`stats.js`/
`pwa.js`/`style.css` в усіх трьох шаблонах. Щойно файл змінюється
(нова версія через `update.sh`), mtime і, відповідно, URL змінюються —
браузер завантажує свіжу версію негайно, стара версія в кеші просто
не використовується (інший URL). Не застосовано до logo.png/іконок —
ті змінюються вкрай рідко, кешування на годину для них не проблема.

## Інструкція оновлення: повний шлях замість відносного

**Симптом**: `bash: scripts/update.sh: Немає такого файла або каталогу`.

**Причина**: фінальний текст `install.sh` і README радили
`sudo bash scripts/update.sh` — коректно лише якщо користувач стоїть
у розпакованому каталозі архіву. Але `update.sh`/`uninstall.sh` уже
встановлені в `/opt/starlink-monitor/scripts/`, і природний сценарій
(покласти новий архів у `~`, лишаючись у домашньому каталозі) веде
саме до цієї помилки.

**Виправлення**: усі згадки `update.sh`/`uninstall.sh` (install.sh
кінцевий текст, README) тепер вказують повний шлях
`/opt/starlink-monitor/scripts/...` — працює з будь-якого поточного
каталогу. `install.sh` (перше встановлення) лишився відносним — той
контекст завжди одразу після `cd` у розпакований архів.

## eth0-fallback для Telegram: SO_BINDTODEVICE, не прив'язка до адреси

**Симптом**: реальні логи показали, що fallback спрацьовує (лог
"пробую через eth0" є), але падає з `NameResolutionError` навіть при
явному DNS-запиті через eth0.

**Причина**: прив'язка сокета до IP-адреси (`source_address`)
прив'язує лише ЗАЯВЛЕНУ джерельну IP пакета. Linux обирає ФІЗИЧНИЙ
інтерфейс за таблицею маршрутизації на основі адреси ПРИЗНАЧЕННЯ,
повністю ігноруючи джерельну IP сокета (якщо не налаштована окрема
policy-based routing на рівні ОС). Тобто пакет із заявленим джерелом
`192.168.0.95` (eth0) усе одно фізично йшов через `wlan0` (бо туди
веде маршрут до `8.8.8.8`) і там же й губився — те саме стосувалось і
DNS-резолвінгу (системний резолвер теж іде тим самим шляхом).

**Виправлення**: `SO_BINDTODEVICE` — системний виклик, що реально
форсує фізичний інтерфейс незалежно від таблиці маршрутизації.
Вимагає `CAP_NET_RAW` — додано через `AmbientCapabilities=CAP_NET_RAW`
у `starlink-monitor.service` й `starlink-webui.service` (сумісно з
`NoNewPrivileges=true` — ambient capability надається systemd до
запуску процесу, не через runtime privilege escalation).
`CapabilityBoundingSet=CAP_NET_RAW` звужено лише в `starlink-monitor.service`
(не викликає sudo) — у `starlink-webui.service` свідомо НЕ звужено,
бо bounding set успадковується навіть дочірнім `sudo systemctl
reboot/poweroff`, і звуження забрало б потрібні для reboot
можливості (`CAP_SYS_BOOT` тощо).

Python: `_Eth0BoundAdapter` (urllib3 `socket_options`) для HTTP;
`_resolve_via_eth0()` — DNS-запит через сокет із явним
`SO_BINDTODEVICE` (`dns.query.udp(..., sock=...)` — власний сокет, не
dnspython's вбудований resolver). Коли й системний DNS не
резолвиться — запит іде напряму на резолвлений IP з `Host` заголовком
і `verify=False` (SNI/hostname-matching неможливий без підміни за IP;
ланцюжок довіри сертифіката лишається валідним, лише перевірка імені
пропускається — свідомий компроміс для вузького фолбек-вікна).

## Баг: WAN-failover не діяв — NetworkManager відновлював свій metric

**Симптом**: лог `wan_failover_check.sh` щоразу (кожні ~20с) рапортував
"знижую пріоритет", хоча мав це вже зробити раніше — реальна таблиця
маршрутів показувала, що `wlan0` так і лишався пріоритетним.

**Причина**: пряма зміна таблиці маршрутів (`ip route`) в обхід
NetworkManager не працює надійно — той сам володіє `wlan0` і
періодично перевідновлює власний `metric` із persistent-конфігурації
з'єднання, ігноруючи зовнішні зміни.

**Виправлення**: керування через сам NetworkManager — `nmcli
connection modify ipv4.route-metric` + `nmcli device reapply` (без
повного перепідключення WiFi). Той самий підхід і в `uninstall.sh`
(відновлення metric при видаленні проєкту).

## Баг: WAN-failover ламав доступ до dish

**Симптом**: після демотування `wlan0` (Starlink без інтернету) Pi
переставав бачити сам dish (`192.168.100.1`), хоча router
(`192.168.1.1`) і локальна мережа лишались доступні.

**Причина**: `192.168.1.0/24` (router) має автоматичний kernel-scope
маршрут (власна підмережа wlan0) — завжди пріоритетніший за дефолтний.
Але `192.168.100.0/24` (dish) такого маршруту не має — трафік туди
йшов лише через дефолтний маршрут, який WAN-failover якраз і
демотував.

**Виправлення**: `install.sh` додає постійний окремий маршрут
(`nmcli +ipv4.routes "192.168.100.0/24 $WLAN_GW"`) на wlan0-з'єднанні
— незалежний від стану WAN-failover.

## WAN-failover сам спричиняв флапи dish — додано гістерезис

**Симптом**: часті сповіщення "Dish знову online" (1-4 невдалі
спроби), кожні кілька хвилин, без obstruction/alerts.

**Причина**: `journalctl` підтвердив точний часовий збіг — кожен флап
dish стається в ту саму секунду, що й `nmcli device reapply` в
`wan_failover_check.sh`. Reapply на мить розриває маршрут до dish;
переключення стається на кожному одиничному "провалі" ping, що
призводить до петлі самопідживлення (reapply впливає на результат
наступної ж перевірки).

**Виправлення**: гістерезис — перемикання лише після
`REQUIRED_CONSECUTIVE=3` поспіль однакових результатів перевірки
(стан у `/run/starlink-wan-failover.state`, tmpfs). Одиничні флапи
більше не тригерять reapply.

## Баг: DISPLAY_ROTATION=90 не працював для 170×320

**Симптом**: `starlink-display.service` падав з `ValueError: Invalid
rotation 90 for 170x320 resolution` при кожному запуску.

**Причина**: бібліотека `st7789` забороняє `rotation=90/270` для
прямокутних (не квадратних) дисплеїв — лише `0`/`180` валідні, коли
`width != height`. Дефолт `DISPLAY_ROTATION=90` був помилковим
припущенням про можливість landscape через rotation-параметр.

**Виправлення**: дефолт змінено на `0` (portrait, без обертання).
Landscape-монтаж вимагає поміняти місцями `WIDTH`/`HEIGHT`
(320×170), не rotation.

## Баг: підсвітка працює, зображення немає (RST не виводився з reset)

**Симптом**: сервіс ініціалізувався без помилок, підсвітка перемикалась
кнопкою, але екран лишався порожнім — жодного зображення.

**Причина**: бібліотека `st7789` в `__init__` налаштовує RST-пін як
output зі стартовим станом LOW (reset-активний), і одразу викликає
`_init()` (SPI-команди ініціалізації контролера) — **до** того, як
RST взагалі підіймається в HIGH. Контролер весь цей час у апаратному
reset і ігнорує всі SPI-команди. Підсвітка (BL) — окрема GPIO-лінія,
не залежить від стану RST, тому світилась нормально попри порожній
екран.

**Виправлення**: після створення `st7789.ST7789(...)`, явно
викликається `display.reset()` (правильна HIGH→LOW→HIGH послідовність
через публічний метод бібліотеки) і **повторно** `display._init()`
(команди з першого виклику в `__init__` контролер проігнорував, поки
був у reset).

## Баг: підтвердження мережевого запиту install.sh не розпізнавалось

**Симптом**: користувач вводив "y" на запит "Налаштувати статичні IP...",
але скрипт показував "Пропущено" (гілка "ні").

**Причина**: `read -r -p ... SETUP_NET` міг захопити прихований `\r`
(термінал користувача) поруч із відповіддю — `[[ "$SETUP_NET" =~
^[TtYyТт] ]]` це не мав би зачепити (regex перевіряє лише перший
символ), але combінація з можливими іншими невидимими символами
могла давати false negative.

**Виправлення**: `SETUP_NET="$(echo "$SETUP_NET" | tr -d
'[:space:]')"` перед перевіркою — прибирає всі пробільні символи
(включно з `\r`), надійніше розпізнає підтвердження.

## Заміна бібліотеки дисплея на Adafruit CircuitPython ST7789

**Причина заміни**: попередня бібліотека мала кілька реальних
проблем, знайдених на живому Pi — RST-баг (`__init__` викликав
`_init()` до виведення RST з reset-стану, вимагало ручного
`reset()`+`_init()` workaround), заборону `rotation=90/270` для
прямокутних дисплеїв (`width != height`), і залишалась невирішена
проблема з шумом/orientaцією, яку так і не вдалось остаточно
діагностувати.

**Нова бібліотека**: `adafruit-circuitpython-rgb-display` +
`adafruit-blinka` (`adafruit_rgb_display.st7789.ST7789`). Перевірено
читанням вихідного коду бібліотеки (не здогадками):
- `DisplaySPI.__init__` сам коректно виводить RST з reset (`rst.value=0`
  → `switch_to_output` → `self.reset()` — LOW→sleep→HIGH→sleep) ДО
  виклику `init()` (SPI-команди) — попередній RST-баг тут відсутній;
- `rotation` дозволяє `0/90/180/270` для будь-якого aspect ratio —
  жодного обмеження на `width==height`;
- обертання застосовується програмно (`img.rotate()` на PIL-зображенні
  в методі `image()`), не через MADCTL-регістр;
- **немає** `set_backlight()` — BL-пін керується напряму окремим
  `digitalio.DigitalInOut` в `app/display.py` (`_set_backlight()`).

**Архітектурні зміни**: ініціалізація тепер через `board`/`digitalio`/
`busio` (Blinka) замість простих цілих BCM-номерів; CS — bit-banged
GPIO (`DISPLAY_SPI_CS_PIN`, дефолт 8), не апаратний номер CE0/CE1
(`STARLINK_DISPLAY_SPI_PORT`/`STARLINK_DISPLAY_SPI_CS` видалено).
`display.image(img)` замість `display.display(img)`.

**Попутно знайдено й видалено**: дублікат-сирота
`DISPLAY_BACKLIGHT_TIMEOUT_SEC` в `config.py` (той самий концепт, що
й `DISPLAY_BACKLIGHT_AUTO_OFF_SEC`, ніде не використовувався).

## Баг: WAN-failover падав з "Read-only file system" на /run

**Симптом**: `starlink-wan-failover.service` падав щоразу (кожен запуск
таймера, ~20с) з `Read-only file system` при спробі записати файл
стану в `/run/starlink-wan-failover.state`. WAN-failover фактично
ніколи не спрацьовував — виявлено на реальному Pi через симптом
"немає інтернету", хоча один з двох інтерфейсів (`eth0`) мав робоче
з'єднання, а маршрут за замовчуванням команду через непрацюючий
`wlan0` (Starlink).

**Причина**: `ProtectSystem=strict` в unit-файлі робить **всю**
файлову систему read-only, окрім явно дозволених шляхів — `/run` сам
по собі НЕ звільнений автоматично від цього обмеження без явного
`RuntimeDirectory=`/`ReadWritePaths=`.

**Виправлення**: `RuntimeDirectory=starlink-wan-failover` (systemd
створює `/run/starlink-wan-failover/` і дозволяє запис туди навіть під
`ProtectSystem=strict`) + `RuntimeDirectoryPreserve=yes` (без цього
systemd видаляє директорію одразу після кожного завершення oneshot-
сервісу — файл стану/гістерезис був би втрачений між кожним запуском
таймера). Шлях у скрипті змінено з `/run/starlink-wan-failover.state`
на `/run/starlink-wan-failover/state`.

## Баг: pip install падав на rpi_ws281x/RPi.GPIO (Python.h відсутній)

**Симптом**: `pip install -r requirements.txt` падав з `fatal error:
Python.h: No such file or directory` при компіляції `rpi_ws281x` та
`RPi.GPIO` (транзитивні залежності `adafruit-blinka` для реального
GPIO-доступу на Raspberry Pi).

**Причина**: `install.sh` не встановлював `python3-dev` (заголовкові
файли Python, потрібні для компіляції будь-яких C-розширень) —
раніше цього не було потрібно, бо попередня бібліотека дисплея не
мала подібних транзитивних C-залежностей.

**Виправлення**: додано `python3-dev build-essential` до списку
apt-пакетів в `install.sh`. Діє лише для нових встановлень
(`MODE=install`) — на вже встановлених системах потрібно виконати
`sudo apt-get install -y python3-dev build-essential` вручну один раз.

## Баг: кирилиця не відображалась на фізичному дисплеї

**Симптом**: український текст ("Оновлення:", "г"/"хв" в uptime тощо)
на TFT-дисплеї не показувався коректно.

**Причина**: `install.sh` не встановлював жодного шрифтового пакету.
`_load_font()` шукає `DejaVuSansMono-Bold.ttf`/`DejaVuSans-Bold.ttf`
за стандартними Debian-шляхами (`/usr/share/fonts/truetype/dejavu/`),
які надає пакет `fonts-dejavu-core` — без нього на мінімальній
системі (Raspberry Pi OS Lite) цих файлів немає, і код тихо (без
попередження) переходив на `ImageFont.load_default()`. Перевірено
функціонально (не лише за типом об'єкта, який у Pillow 10+ завжди
`FreeTypeFont` для обох випадків): різні кириличні літери в цьому
fallback-шрифті рендерились **ідентичним** растровим візерунком
("відсутній гліф"-заглушка), тобто кирилиця справді не підтримується.

**Виправлення**: додано `fonts-dejavu-core` до apt-пакетів в
`install.sh`. Додатково `_load_font()` тепер логує явне попередження,
якщо жоден шрифт з `FONT_PATHS` не знайдено — щоб цю проблему було
видно одразу в журналі, а не виявляти постфактум за зовнішнім
виглядом екрана.

## Баг: довге натискання кнопки не вимикало Pi (NoNewPrivileges)

**Симптом**: коротке натискання (підсвітка) працювало бездоганно,
довге утримання давало в логах `"Кнопка виключення утримана 3.0с ...
- виконую poweroff"`, але одразу після цього — `sudo: The "no new
privileges" flag is set, which prevents sudo from running as root`.
Pi фактично не вимикався.

**Причина**: `starlink-display.service` мав `NoNewPrivileges=true` —
залишок з часів, коли дисплей-сервіс дійсно не виконував жодних
sudo-дій. Коли логіку кнопки виключення (включно з `sudo systemctl
poweroff` на довге натискання) перенесли з окремого
`shutdown_button.py`-сервісу в `display.py` (щоб уникнути конфлікту
за GPIO-пін — див. відповідний запис вище), unit-файл забули
оновити — коментар і далі стверджував "жодних sudo-дій".

**Виправлення**: `NoNewPrivileges=true` видалено з
`starlink-display.service`. `sudoers.d`-правило (`NOPASSWD:
/bin/systemctl poweroff`) уже було на місці й не потребувало змін —
проблема була виключно в systemd security-прапорі, що блокував сам
виклик `sudo` зсередини процесу, незалежно від того, чи дозволено
команду в sudoers.

## Зменшення частоти записів на SD-картку

**Зміна**: `PRAGMA synchronous=NORMAL` (замість дефолтного `FULL`)
для WAL-режиму — офіційно рекомендований SQLite-документацією режим,
що зменшує кількість `fsync()`-викликів (лише при checkpoint, не на
кожному commit metric-опитування кожні ~10с). Безпечно — WAL сам
гарантує захист від пошкодження БД; ризик лише у втраті кількох
останніх транзакцій при раптовому знеструмленні.

**Розглянуто, але НЕ застосовано автоматично**: `Storage=volatile`
для `systemd-journald` (журнал у RAM замість SD-картки) дав би значно
більший виграш, АЛЕ ціною повної втрати `journalctl`-історії між
перезавантаженнями — критично важливий інструмент діагностики, яким
активно користувались протягом усієї розробки цього проєкту (напр.
для знаходження RST-бага дисплея, `NoNewPrivileges`-бага кнопки
виключення тощо). Це реальний trade-off, що вимагає свідомого вибору
користувача, не мовчазного застосування:
```
# Опційно, лише якщо свідомо приймаєш втрату журналів між reboot:
echo "Storage=volatile" | sudo tee -a /etc/systemd/journald.conf
sudo systemctl restart systemd-journald
```

## starlink_grpc.py винесено як vendor-файл для відтворюваності збірки

**Було**: `install.sh` при кожному першому встановленні запускав
`starlink-grpc-fetch.service` у фоні, який динамічно завантажував
`starlink_grpc.py` з GitHub (sparky8512/starlink-grpc-tools) при
старті. Це означало: (а) встановлення залежало від доступності
інтернету саме в той момент, (б) різні інсталяції могли отримати
різні версії файлу залежно від того, коли саме встановлювались, (в)
upstream міг випустити несумісну зміну без нашого відома/тестування.

**Стало**: реальний файл (перевірено — синтаксично валідний, реально
імпортується з `grpc`+`yagrc`) завантажено один раз і покладено в
`app/vendor/starlink_grpc.py` як частину архіву проєкту.
`starlink_client.py` не потребував жодних змін — уже мав graceful
fallback (`from app.vendor import starlink_grpc` / `except ImportError:
starlink_grpc = None`), розрахований саме на цей шлях.
`starlink-grpc-fetch.service` і далі встановлюється (для опційного
ручного оновлення до найновішої upstream-версії), але більше не
`enable`/`start` автоматично з `install.sh`. Ліцензія файлу
залишається окремою (upstream-автора), не MIT цього репозиторію —
явно зазначено в README.

## Сповіщення про зміну версії прошивки dish/router

**Реалізація**: `upsert_known_device_dish()`/`upsert_known_device_router()`
вже обчислювали `version_changed` внутрішньо (для `*_updated_ts` полів),
просто не повертали його назовні. Змінено повертати `(real_change,
old_version)` — `monitor.py` надсилає Telegram-сповіщення, коли
`real_change=True`.

**Знайдений і виправлений edge case**: перша версія логіки вважала
"зміною" будь-яку ситуацію, коли рядок `known_devices` уже існував
(`existing is not None`), незалежно від того, чи конкретне ПОЛЕ
(`dish_software_version`/`router_software_version`) було раніше `NULL`.
Оскільки dish і router опитуються в різних циклах і можуть створити
спільний рядок `known_devices` першим (за `dish_id`), перше заповнення
"свого" поля (наприклад router вперше отримує `router_software_version`,
хоча рядок уже існував через dish) хибно рахувалось "зміною версії з
None". Виправлено: `real_change` тепер `old_version is not None and
old_version != new_version` — перевіряє саме ПОЛЕ, не факт існування
рядка. Перевірено живим тестом обох симетричних сценаріїв (dish
першим/router першим).

## Downsampling старих метрик

**Реалізація**: `downsample_old_metrics()` агрегує raw-рядки
(`metrics`) старші за `DOWNSAMPLE_AFTER_DAYS` (дефолт 3) у
`DOWNSAMPLE_BUCKET_SEC`-секундні (дефолт 300) середні, окрема таблиця
`metrics_downsampled`, видаляючи оригінальні детальні рядки.
Викликається щогодини разом з `prune_old()` (яку теж розширено —
очищує `metrics_downsampled` за повною `HISTORY_RETENTION_DAYS`-межею).

## Групування спаму reboot-сповіщень

**Проблема**: `MIN_REBOOT_INTERVAL_SEC` (180с) гарантує, що реальні
reboot-спроби не частіші за раз на ~3хв, але не запобігає тому, щоб
flapping (dish то доступний, то ні) генерував Telegram-повідомлення
кожні 3хв протягом години й довше — кожне технічно виправдане, але
сукупно виглядає як спам. Існуючий `NOTIFICATIONS_MUTE_AFTER_SEC`
тут не допомагає — той механізм про ОДНУ тривалу безперервну відмову,
а не про частоту КОРОТКИХ окремих циклів.

**Реалізація**: `_notify_reboot()` — ковзний список timestamps
надісланих reboot-сповіщень; при `REBOOT_SPAM_THRESHOLD`+ за
`REBOOT_SPAM_WINDOW_SEC` — одне попередження про групування, далі
мовчки рахує до затишшя (`_check_reboot_spam_recovery()`, викликається
на початку кожного `poll_once()`), тоді підсумкове повідомлення й
повний скид стану — новий цикл флапу після recovery поводиться знову
з нуля.

**Перевірено живим тестом** усі 5 етапів по черзі (нижче порогу →
досягнення порогу → тихий підрахунок → recovery-підсумок → новий
цикл після скидання), включно з підтвердженням, що
`_check_reboot_spam_recovery()` реально автоматично викликається з
`poll_once()`, не лише вручну в тесті.

## Типізація (mypy) — пропорційний підхід, без --strict/CI

**Контекст**: запит на full `mypy --strict` + CI. Перевірено реально
(не гіпотетично): `mypy --strict` на тодішньому стані коду дав **366
помилок у 13 файлах**, при 20% функцій з return type annotation.
Головні джерела: SQLite `dict(row)`-патерни всюди в `db.py`, і
`app/vendor/starlink_grpc.py` — 1799 рядків чужого коду.

**Рішення**: пропорційний підхід замість full-strict retrofit +
CI-інфраструктури з нуля (якої в проєкті немає взагалі) — одноосібний
hobby-проєкт на одному Pi, перевіряється живим тестуванням на
реальному залізі (не automated test suite), CI не додав би
пропорційної цінності:
1. Return type hints для **всього** власного коду (не `--strict`,
   звичайний режим) — усі 10 файлів `app/` (крім vendor)
2. `mypy.ini` — `ignore_errors=True` для `app.vendor.*`,
   `ignore_missing_imports` для hardware-специфічних (`gpiod`,
   `board`, `digitalio`, `busio`, `adafruit_rgb_display`) і сторонніх
   без офіційних stubs (`dns`, `requests`, `psutil`)
3. `mypy` запускається локально/вручну (`requirements-dev.txt`), не
   в CI — інструмент розробки, не production-залежність Pi

**Результат**: `mypy app/` → `Success: no issues found in 17 source
files`.

**Реальні баги, знайдені й виправлені під час типізації** (не просто
додавання анотацій — mypy реально спіймав логічні помилки):
- `StarlinkClient.__init__(dish_addr: str = None, ...)` та кілька
  подібних — PEP 484 явно забороняє неявний `Optional`
- `starlink_client.py`: `starlink_grpc = None` (graceful fallback при
  відсутньому vendor-модулі) конфліктувало з типом "модуль", виведеним
  з успішного `import` — виправлено явним
  `starlink_grpc: Optional[types.ModuleType]`
- `monitor.py`: **власна помилка** — типізував `poll_once()` як
  `-> None`, хоча метод реально повертає `DishStatus`; 6 полів у
  `Watchdog.__init__` (`prev_update_state`, `first_failure_ts` тощо)
  оголошені як `None` без `Optional`, хоча пізніше присвоюються
  реальні значення; `last_prune = 0` (int) замість `0.0`, порівнюване
  з `time.time()` (float)
- `config_editor.py`: `read_current_values() -> dict` — сигнатура,
  що існувала й РАНІШЕ, виявилась неправильною (функція реально
  повертає `list[dict]`) — знайдено лише зараз, під час типізації
- Повторюваний патерн у 3+ місцях (`system_metrics.py`, `display.py`,
  `telegram_bot.py`): `result =
  {"key": значення}` — перше значення "звужує" тип для mypy,
  подальші присвоєння інших типів у той самий словник/список
  конфліктують. Рішення завжди однакове: explicit `dict[str, Any]`
  (чи `list[dict[str, Any]]`) при створенні

## Мобільний PWA офлайн-режим — localStorage-кеш останнього стану

**Оновлює попереднє рішення**: `sw.js` мав явний коментар "жодного
кешування API-відповідей... показ застарілих даних Starlink офлайн
було б оманливим". Це рішення НЕ скасовано (service worker і далі
не кешує API на своєму рівні) — додано ОКРЕМИЙ механізм на рівні
`dashboard.js` з явним маркуванням застарілості (банер + "X хв тому"),
що вирішує саме те занепокоєння, яке спричинило первісне рішення:
показ старих даних БЕЗ індикатора був би оманливим, показ старих
даних З чітким індикатором — корисний UX для мобільного сценарію
(вийшов з WiFi-зони дії Pi, хочеш побачити останній відомий стан, не
порожній екран).

**`localStorage`, не `IndexedDB`**: дані — один невеликий JSON-об'єкт
("останній `latest`"), не потребує транзакцій/великого обсягу/
структурованих запитів, які виправдовували б складніший асинхронний
API `IndexedDB`. Простіший синхронний `localStorage` достатній і
пропорційний задачі.

**Реалізація**: `refreshStatus()` розділено — рендеринг винесено в
окрему `_renderStatusData(latest)`, перевикористовувану і для live-
даних (успішний fetch), і для кешованих (fetch провалився). Формат
"X хв тому" (`fmtAgo()` в `common.js`) — той самий, що вже був у
`telegram_bot.py._fmt_ago()`, для консистентності між Telegram і
веб-UI.

**Перевірено живими тестами**: повний цикл (успіх кешує + ховає
банер → невдача показує кеш + банер з правильним "щойно"/"X хв тому"),
і граничний випадок — перше відкриття без жодного попереднього кешу
при одразу недоступному Pi: код коректно НЕ звертається до банера
взагалі (немає що показати), не намагається відрендерити порожні дані.

**Реалізація**: `[data-theme="light"]`-селектор інвертує значення тих

**Знайдено й виправлено під час реалізації**:
1. **7 хардкоджених hex-кольорів** поза `:root`-блоками (градієнт
   `body` через `#101c33`, warn/crit border, hover/active стани

   спрацьовувало б, "лагідно" провалюючись у catch щоразу. Виправлено
   переміщенням скрипта: після `<meta theme-color>`, до `<link

3. Один хардкоджений колір (`#04121a`, текст на `--signal`-фоні)

**`theme.js` окремий файл, не в `common.js`**: той не підключений на
`/settings` (де саме перемикач), лише на index/stats.

**Перевірено живими тестами**: повний цикл toggle (4 сценарії - init
dark, клік у light, назад у dark, атрибут коректно встановлюється/

## Баг: `pip install --upgrade -r requirements.txt` оновлював незмінені пакети

**Знайдено на реальному Pi** (не гіпотетично): після оновлення лише
"безпечних" пакетів (Flask/requests/dnspython/yagrc) у requirements.txt
попереднього разу, `pip freeze` на Pi показав, що
`adafruit-blinka` теж оновився (8.x→9.2.0) — пакет, який ми
**explicitly домовились не чіпати** (hardware-критичний для
TFT-дисплея, major-стрибок, неможливо перевірити без реального
заліза). Той самий блок торкнувся і protobuf (→7.35.1), Pillow
(→12.3.0), psutil (→7.2.2), grpcio (→1.83.0) — усіх пакетів у файлі,
не лише тих, чий рядок реально змінився.

**Причина**: `install.sh` викликав `pip install --upgrade -r
requirements.txt` — прапорець `--upgrade` застосовується до **всього**
файлу одразу: коли `>=`-піни, pip підтягує найновішу версію, що
задовольняє КОЖЕН рядок, незалежно від того, чи саме цей рядок
змінився в git-diff requirements.txt. Зміна номера версії ХОЧА Б
ОДНОГО пакета (що тригерить `REQ_CHANGED=1`) фактично означала "онови
все до найновішого".

**Виправлення**: `requirements.txt` тепер має **виключно точні `==`
піни** (не `>=`) для всіх пакетів — на версіях, підтверджених реально
встановленими й working на Pi (`pip freeze` з живого пристрою,
користувач підтвердив дисплей і зв'язок з dish справні). `install.sh`
більше НЕ використовує `--upgrade` — з точними пінами звичайний `pip
install -r requirements.txt` природно ідемпотентний (не займає пакет,
чий pin уже задоволений) і торкається ЛИШЕ пакетів, чий точний pin
реально змінився в наступних версіях файлу.

**Перевірено живим тестом** (ізольований venv у пісочниці): `pip
install pkg==X` двічі поспіль без `--upgrade` не робить нічого другого
разу (той самий pin); зміна на `pkg==Y` реально встановлює Y —
підтверджує, що новий механізм справді торкається лише зміненого.

## Сповіщення про встановлення очікуваної версії прошивки

**Реалізація**: `/settings` дозволяє явно вказати ОЧІКУВАНУ версію
(dish/router), і отримати "✅ Останнє оновлення..." саме коли
встановлена версія їй відповідає. Окремо від уже наявного "🔄
прошивка змінилась" (спрацьовує на БУДЬ-ЯКУ зміну) — цей новий
механізм про конкретну, заздалегідь відому версію.

**Дедублікація без окремого boolean-прапорця**: `dish_target_notified`
зберігає САМЕ ЗНАЧЕННЯ target, про яке вже сповістили — порівняння
`notified == target` природно "скидається", коли користувач вводить
НОВИЙ target, без потреби explicit очищати стан десь окремо.

**Першочергове введення**: `GET /api/target-versions` повертає й
`dish_current`/`router_current` — `settings.js` `loadTargetVersions()`
показує поточну відому версію як стартове значення інпута, коли
target ще не задано, замість порожнього поля.

**Знайдена й виправлена прогалина під час реалізації**: нові
налаштування спочатку не потрапляли в `/api/settings-backup`/
`/api/settings-restore` — виявлено і виправлено одразу (перевірено
живим тестом повного циклу backup→restore на "чистому" стані БД).

**Перевірено живими тестами**: усі 5 сценаріїв дедублікації (немає
target / не збігається / збіглось → сповіщення / повтор → без спаму /
новий target → нове сповіщення), pre-fill логіка (обидва варіанти:
target порожній показує current, target уже заданий показує саме
його), повний Flask API-цикл GET/POST, повний backup→restore цикл.

## Очікувана версія прошивки — валідація "лише новіші"

**Реалізація**: `POST /api/target-versions` відхиляє нову версію,
якщо вона старіша за вже відому (максимум із попереднього target і
поточної встановленої версії) — захист від випадкового відкату
(описка, забутий раніше введений новіший target).

**`_version_key()`** — толерантний компаратор для формату
`YYYY.MM.DD.mrXXXXX.N` (не строгий semver, Starlink не документує
формально). Дата-префікс домінує як найнадійніший індикатор "новіше"
(перевірено на реалістичних прикладах: різні дати, однакова дата з
різним mr-номером, ідентичні версії — усі 5 тестових пар дали
правильний результат). Fallback на посегментне порівняння, коли дата
відсутня чи однакова в обох — не падає на нетиповому форматі
(перевірено: `v1.2.3`, порожній рядок, довільний текст).

**Часткова відмова**: dish і router валідуються незалежно — якщо
одне поле старіше, а інше новіше, валідне зберігається, невалідне
відхиляється окремо з поясненням (не "усе або нічого" для обох полів
одночасно). Перевірено живим тестом — саме цей змішаний сценарій.

**Перевірено живими тестами**: перше введення (=поточна встановлена,
приймається), спроба ввести старішу (відхилено, target реально НЕ
перезаписаний), новіша (приймається), змішаний dish-valid/router-
invalid сценарій, відображення реального повідомлення на фронтенді
(не generic "Помилка"), граничні випадки компаратора (нестандартні
формати не падають).

## Комбіноване сповіщення про завершення процедури оновлення (обидва одночасно)

**Реалізація**: окремо від per-component сповіщень (`_check_target_
version_reached()`, спрацьовує на кожен компонент незалежно) —
`_check_both_targets_reached()` надсилає "🎉 Процедуру оновлення
завершено" саме коли ОБИДВІ (тарілка й роутер) очікувані версії
одночасно збігаються зі встановленими. Не замінює per-component
сповіщення, доповнює їх — "dish оновився" все ще корисно знати
окремо, навіть коли router ще не встиг.

**Виклик з обох циклів опитування**: dish і router опитуються
незалежно (`poll_once()`/`poll_router()`, різні цикли) — тому
комбінована перевірка викликається З ОБОХ, бо або один, або інший
цикл може стати тим, що робить умову істинною одночасно (наприклад,
dish уже відповідав target раніше, router щойно оновився — саме
router-цикл має "помітити" повний збіг).

**Дедублікація** — той самий принцип, що вже застосований раніше:
notified-ключ (`both_targets_notified`) зберігає ОБ'ЄДНАНИЙ рядок
обох target одночасно, природно "скидається" при зміні будь-якого з
двох. Internal dedup-стан, свідомо НЕ включений у backup/restore
(той самий принцип, що вже застосований до per-component notified-
ключів).

**Перевірено живими тестами** — усі 7 сценаріїв: немає жодного
target / лише один заданий / обидва задані але не збігаються /
**частковий стан (лише dish відповідає, router ще ні) — найважливіший
випадок, правильно тихо, не спамить** / обидва збіглись одночасно →
сповіщення / повторний виклик без спаму / зміна одного з двох target
природно скидає notified-стан.

## Формальний test suite (pytest) для найкрихкішої логіки

**Контекст**: протягом усієї розробки кожна зміна верифікувалась
живими ad-hoc тестами (`python3 -c "..."` через bash_tool) — реальні
сценарії, mock через `unittest.mock`, перевірка граничних випадків.
Це давало високу впевненість у момент розробки, АЛЕ тести НЕ
персистувались — кожна нова сесія роботи з тією самою логікою
(наприклад watchdog reboot-spam grouping) вимагала реконструювати ті
самі сценарії з нуля.

**Реалізація**: `tests/` (`conftest.py` + 3 файли, 35 тестів) покриває
найкрихкішу, stateful-логіку — не весь проєкт (over-engineering для
solo hobby-проєкту), а саме те, де регресія найімовірніша й найдорожча:
- `test_monitor.py` (21 тест) — групування reboot-спаму (часове вікно,
  5 сценаріїв), дедублікація target-версій (5 сценаріїв), комбінована
  перевірка (7 сценаріїв, включно з найважливішим — частковий стан
  не спамить), `_maybe_reboot()` (4 тести — точний приклад із
  оригінальної пропозиції користувача, перевірено технічну точність
  API перед написанням)
- `test_webapp.py` (10 тестів) — `_is_older_version()`/`_version_key()`
  компаратор (ті самі 5 пар версій, що вже верифікувались ad-hoc
  раніше), валідація `/api/target-versions` (першочергове введення,
  відхилення старішої, частковий success dish/router), backup includes
  target versions but not internal notified-state

**Знайдена й виправлена реальна розбіжність під час написання**:
`test_reboot_spam_recovery_sends_summary_and_resets` спочатку очікував
`muted_reboot_count == 3` після рівно 3 викликів `_notify_reboot()`
(порогове значення) — реальний прогін через `pytest` показав `1`, не
`3`. Причина: `muted_reboot_count` рахує лише reboot **після**
активації групування (включно з тим, що її активував), не загальну
кількість спроб до порогу. Це не баг коду — баг мого тесту (неточне
відтворення семантики). Виправлено додаванням явних reboot ПІСЛЯ
активації, щоб реально отримати очікувані 3.

**Перевірено додатково**: увесь набір (35 тестів) пройшов і в
стандартному, і в **рандомізованому** порядку (`pytest-randomly`,
два різні seed) — підтверджує відсутність прихованих залежностей між
тестами через незскинуті модульні `config.*` globals. `pytest-mock`
встановлений спочатку, але виявився зайвим (усюди `unittest.mock`
напряму) — не додано в `requirements-dev.txt`. `mypy tests/` теж
чистий, узгоджено з рештою проєкту.

## Кілька очікуваних версій прошивки для різних апаратних ревізій

**Проблема**: SpaceX іноді випускає РІЗНІ номери версій під однією
умовною версією, залежно від апаратної ревізії конкретного dish/router
(різні партії обладнання отримують різні build-номери за той самий
логічний реліз). Раніше `dish_target_version`/`router_target_version`
приймали лише ОДНЕ значення — якщо користувач не певен точно, який
рядок реально прийде на його апаратну ревізію, доводилось вгадувати.

**Реалізація**: обидва поля тепер приймають comma-separated список
(той самий формат, що вже існував для `telegram_chat_ids` — консистентно
з наявним паттерном проєкту, не новий концепт). Матч спрацьовує на
БУДЬ-ЯКУ з перелічених версій. `db.parse_version_list()` — спільний
helper, винесений у `db.py` (уникнено дублювання парсингу в
`monitor.py` і `webapp.py` окремо).

**Валідація "лише новіші" розширена**: кожен кандидат у списку
перевіряється окремо проти baseline (максимум з попереднього списку +
поточної встановленої версії). Якщо ХОЧ ОДИН кандидат старіший —
відхиляється ВЕСЬ список для цього поля (простіша семантика, ніж
часткове прийняття окремих кандидатів всередині одного поля — на
відміну від dish/router часткової відмови МІЖ полями, яка залишається
без змін).

**Дедублікація сповіщень оновлена**: notified-ключ тепер зберігає
ПАРУ (яка саме версія зі списку збіглась + повний target-список), не
лише саме target-значення — природно "скидається" при зміні списку
(наприклад додаванні версії для іншої апаратної ревізії).

**Перевірено живими тестами** (4 нові, 39 усього): матч на будь-яку з
кількох перелічених версій, жодна не збігається — тихо; API-валідація
— усі кандидати новіші приймаються повним списком, один старіший
кандидат відхиляє весь список зі старим значенням незмінним. Усі 35
попередніх тестів пройшли без модифікацій — зворотна сумісність
підтверджена (одна версія без коми поводиться ідентично до старої
логіки).

## Backup включає історію всіх підключених Starlink-пристроїв

**Реалізація**: `known_devices` (dish_id, версії ПЗ/апаратні, часові
мітки для кожної відомої тарілки) додано до `/api/settings-backup`.
`db.merge_known_devices()` — restore-логіка, окрема від решти полів:
INSERT OR IGNORE, НЕ перезаписує dish_id, що вже є в цільовій БД,
навіть якщо backup-дані формально виглядають "новішими" за датою
файлу — локальна БД реально працюючого watchdog'а вважається
авторитетнішою за статичний backup-знімок з невідомо якого моменту
в минулому (той самий принцип обережності, що вже застосований до
target-версій прошивки: не перезаписувати потенційно свіжіший стан
старішими даними).

**Перевірено живими тестами** (5 нових, 44 усього): backup реально
включає всі відомі тарілки; restore на чисту БД додає всі записи;
**найважливіший сценарій** — restore, коли dish_id вже є локально з
об'єктивно новішими даними, НЕ перезаписує їх старішими з backup;
записи без dish_id ігноруються без падіння. Окремо перевірено на
API-рівні через `/api/settings-backup`/`/api/settings-restore`.

## Аудит: 2 реальні прогалини знайдені й виправлені (не повторення старих перевірок)

**Знайдено систематичним пошуком**, не випадково:

1. **Неможливо очистити target-версію**: порожній рядок у полі +
   "Зберегти" мовчки ігнорувався (`elif candidates:` — порожній
   список кандидатів falsy, нічого не відбувалось), старе значення
   лишалось назавжди без жодного способу його скасувати. Виправлено:
   явно надісланий порожній рядок тепер розпізнається як команда
   ОЧИСТИТИ поле (`db.set_setting(key, "")`).

2. **API-контракт неповний**: `return jsonify({"success": True})` (без
   `rejected`-кандидатів) НІКОЛИ не містив `message` — фронтенд мав
   graceful fallback (`data.message || 'Збережено'`), тому UI не
   ламався видимо, АЛЕ це виявив мій ЖИВИЙ ТЕСТ, що звертався до
   `data['message']` напряму (API-контракт, не UI-поведінка) —
   `KeyError`. Виправлено: відповідь завжди явно описує реальний
   результат (`"Збережено: X"` / `"Без змін"` / відхилення).

**Хибна тривога, чесно спростована перевіркою**: підозрював, що
`merge_known_devices()` впаде на `IntegrityError`, якщо backup містить
записи без обов'язкових `first_seen_ts`/`last_seen_ts` (`NOT NULL` у
схемі, `d.get(...)` повертає `None`). Реально перевірено: SQLite
`INSERT OR IGNORE` ловить УСІ типи constraint violations (не лише
PRIMARY KEY/UNIQUE), тому неповний запис тихо ігнорується без
винятку — код уже коректний, підозра виявилась неправильною.

**Перевірено живими тестами** (2 нові, 46 усього): очищення поля
реально прибирає значення й узгоджується з `monitor.py` (після
очищення `_check_target_version_reached()` коректно мовчить);
відповідь API завжди містить `message` для всіх шляхів виконання.

## Flash-сповіщення підсвіткою при зміні статусу оновлення

**Реалізація**: коли `update_state` dish чи router змінюється —
підсвітка вмикається на `DISPLAY_UPDATE_FLASH_SEC` (дефолт 5с) і
потім явно вимикається. `_update_state_changed()` — чиста функція
(порівняння відносно попереднього опитування, `prev_*=None` на старті
НЕ вважається зміною).

**Реальний баг знайдений і виправлений під час реалізації**: коли
flash активується, я спершу НЕ оновлював `last_activity_ts` —
`_should_auto_off()` (типовий інтервал 60с, перевіряється РАНІШЕ в
циклі за порядком коду) міг би вирішити, що "пройшло забагато часу" і
вимкнути підсвітку ще ДО завершення значно коротшого flash-періоду
(5с), якщо `last_activity_ts` була давно в минулому (наприклад, з
останнього ручного натискання кнопки годину тому). Виправлено:
`last_activity_ts=now` при активації flash. Додатково — явний guard
`if flash_until_ts is None and _should_auto_off(...)` унеможливлює
конфлікт двох таймерів навіть у малоймовірному edge case, коли
`DISPLAY_UPDATE_FLASH_SEC` налаштований довшим за `DISPLAY_BACKLIGHT_
AUTO_OFF_SEC`.

**UX-деталь**: ручне натискання кнопки під час активного flash-періоду
скасовує `flash_until_ts` — user явно взаємодіє з дисплеєм (щойно
натиснув кнопку), не форсувати несподіване вимкнення одразу після
цього через незалежний flash-таймер.

**Перевірено живими тестами** (9 нових, 55 усього): виявлення зміни
(dish/router окремо, обидва разом, зникнення стану), перше зчитування
НЕ вважається зміною, взаємодія `_should_auto_off()` з щойно
оновленим `last_activity_ts` (не спрацьовує одразу після flash-
активації).

## Дедублікація target-версій ізольована per-dish_id (реальний сценарій користувача)

**Проблема, знайдена через діагностику з користувачем**: user
повідомив "коли очікувана версія = фактична не приходять сповіщення".
Живе тестування базового сценарію (target = поточна версія, реальний
`poll_once()`/`poll_router()`, перше підключення й повторюваний цикл)
підтвердило, що логіка ПРАЦЮЄ коректно у всіх відтворюваних сценаріях
— проблема НЕ була в самій match-логіці. Уточнення з користувачем
виявило реальний контекст: **різні фізичні Starlink** (різні dish_id,
напр. після заміни обладнання) підключені до того самого Pi з часом.

**Реальна логічна прогалина**: `dish_target_notified`/
`both_targets_notified` дедублікаційні ключі НЕ включали `dish_id` —
лише "версія|target". Якщо ІНШИЙ фізичний Starlink (інший dish_id)
пізніше збігався ТІЄЮ САМОЮ версією+target, що вже notified для
ПОПЕРЕДНЬОГО фізичного пристрою, дедублікація помилково блокувала б
сповіщення для НОВОГО пристрою, вважаючи це "тим самим" вже
сповіщеним збігом.

**Виправлення**: `_check_target_version_reached()` тепер приймає
`dish_id` параметром (dish передає `status.dish_id`, router передає
`self.last_known_dish_id` — той самий фізичний Mini). `notified_value`
= `f"{dish_id}|{current_version}|{target_raw}"` замість
`f"{current_version}|{target_raw}"`. `_check_both_targets_reached()`
той самий принцип — `self.last_known_dish_id` додано до `combo_key`.

**Перевірено живими тестами** (3 нові, 58 усього): ІНШИЙ dish_id з
тим самим збігом версія+target отримує ВЛАСНЕ, свіже сповіщення (не
заблоковане дедублікацією попереднього пристрою) — і для per-
component, і для комбінованої перевірки; контрольний тест підтверджує,
що дедублікація ВСЕ ЩЕ працює нормально для ТОГО САМОГО dish_id (фіча
додала лише ізоляцію МІЖ пристроями, не зламала звичайну поведінку).

## Ручна кнопка "Перевірити оновлення" не сповіщала (реальна прогалина, знайдена на запит аудиту)

**Проблема**: користувач попросив перевірити процедуру ручної
перевірки оновлень на помилки. Живий тест-доказ підтвердив: `/api/
check-updates` (кнопка на дашборді) читав статус dish/router і
записував у БД, АЛЕ НЕ викликав жодну з "розумних" перевірок —
0 Telegram-сповіщень навіть при точному збігу з target-версією,
`known_devices` взагалі НЕ оновлювався (`db.get_known_device()`
повертав `None`, хоча версія БУЛА записана в `metrics`).

**Причина**: `webapp.py` (Flask dashboard) і `monitor.py` (watchdog)
— ОКРЕМІ systemd-сервіси/процеси. Уся "розумна" логіка (`_check_
target_version_reached`, `upsert_known_device_dish/router` +
сповіщення) була методами класу `Watchdog`, живого лише в процесі
watchdog-сервісу — `webapp.py` фізично не міг їх викликати напряму.

**Виправлення**: винесено спільну логіку в module-level функції
(`version_in_target_list`, `check_target_version_reached`,
`check_both_targets_reached`, `upsert_dish_and_notify`,
`upsert_router_and_notify` — усі в `app/monitor.py`, ПОЗА класом),
що приймають `notify_fn: Callable[[str], None]` замість `self.
_notify`. `Watchdog`-методи стали тонкими обгортками (зворотно
сумісні — усі 58 наявних тестів пройшли без модифікацій).
`webapp.py api_check_updates()` тепер викликає ті самі функції
напряму, з `telegram_notify.send_message` як `notify_fn`.

**Перевірено живими тестами** (2 нові, 60 усього): ручна перевірка
реально надсилає "✅ Останнє оновлення..." при збігу з target-версією;
`known_devices` реально оновлюється через ручну кнопку (dish і
router поля одночасно). Регресійний тест-доказ ДО фіксу (0 сповіщень,
`known_devices=None`) підтвердив реальність прогалини перед
виправленням, не гіпотетично.

## "🔄 оновлена" вводило б в оману для реального відкату прошивки (запит на аудит)

**Питання від користувача**: чи механізм перевірок target-версії й
сповіщень про зміну прошивки може ВИКЛИКАТИ дивні повідомлення на
кшталт "оновлена: НОВІША → СТАРІША" — точно ті приклади, з якими
користувач раніше реально зіткнувся (router rollback, підтверджений
раніше як SpaceX-side).

**Знахідка**: `real_change` у `db.upsert_known_device_dish/router()`
напрямково-байдужа — детектує БУДЬ-ЯКУ зміну версії (коректно, це і
є мета цієї перевірки), АЛЕ повідомлення "🔄 Прошивка X **оновлена**:
X → Y" завжди використовувало те саме слово, незалежно від напрямку.
Слово "оновлена" сильно натякає на прогрес вперед — оманливо, коли
реальна зміна це downgrade/rollback.

**Виправлення**: `_format_firmware_change_message()` (`app/monitor.
py`) використовує `db.is_older_version()` (той самий толерантний
компаратор, що вже валідує target-версії — перенесено з `webapp.py`
у `db.py` як публічні `version_key()`/`is_older_version()`, спільні
для обох процесів) для визначення напрямку: "🔄 оновлена" для forward,
"⏪ відкочена (можливо, SpaceX-side)" коли нова версія СТАРІША за
попередню. Дані (X → Y) завжди ті самі, чесно показують факт — лише
словесне формулювання адаптується.

**Реальна помилка знайдена й виправлена під час рефакторингу**:
перенісши `_version_key`/`_is_older_version` з `webapp.py` у `db.py`,
спочатку забув оновити 2 місця (`max(..., key=_version_key)`), де
стара назва ще використовувалась напряму — `mypy` (не strict) НЕ
спіймав це (unused/undefined через видалення функції, не type error),
знайдено власним переглядом коду одразу після рефакторингу, до
живого тестування.

**Перевірено живими тестами** (3 нові, 63 усього): forward-зміна
каже "оновлена", backward — "відкочена"; **точний сценарій із
реального повідомлення користувача** (router 2026.07.23.mr82306 →
2025.10.03.mr61821) відтворений і підтверджений — тепер каже "⏪
відкочена", не оманливе "оновлена".

## Кнопка ручної перевірки оновлень системних пакетів (apt)

**Реалізація**: `/api/apt-check` (POST) — примусовий `sudo /usr/bin/
apt-get update` (timeout 30с — мережевий запит до репозиторіїв,
довше за швидкі reboot/shutdown), потім `system_metrics.
get_apt_updates_info(force=True)` — новий параметр, обходить
internal-кеш (1 година), щоб дати СВІЖЕ число одразу після
примусового оновлення, не чекаючи наступного природного циклу
кешування.

**sudoers-правило додано** (`install.sh`) — `/usr/bin/apt-get update`
без пароля, той самий навмисно вузький підхід, що вже застосований
до reboot/poweroff/restart-команд (не blanket `ALL=(ALL) NOPASSWD:
ALL`). Без цього правила ендпоінт провалився б із "password required"
у неінтерактивному Flask-процесі (той самий клас проблеми, що вже
діагностувалась раніше для SD-backup скриптів).

**UI**: кнопка "📦 Перевірити оновлення пакетів" на панелі "Керування
Raspberry Pi", оновлює той самий `#sAptUpdates` елемент, що вже
показував пасивний (кешований) лічильник — user бачить результат
одразу, без очікування наступного циклу опитування системних метрик.

**Перевірено живими тестами** (3 нові, 66 усього): успішний сценарій
повертає `updates_count`, провал (наприклад мережева помилка)
повертає повідомлення про причину, обидва записують подію в журнал.

## Баг: apt-check провалювався через ProtectSystem=strict (знайдено на реальному Pi)

**Помилка на практиці**: кнопка "Перевірити оновлення пакетів"
провалилась з "Read-only file system" для `/var/lib/apt/lists/*`,
хоча `mount | grep ' / '` підтвердив, що коренева файлова система Pi
змонтована `rw` — файлова система САМА не read-only.

**Реальна причина**: `starlink-webui.service` уже мав `ProtectSystem=
strict` (systemd hardening — навмисно ізолює процес від запису по
всій файловій системі, крім явно дозволених `ReadWritePaths=`).
Це mount namespace-обмеження успадковується **дочірніми процесами
незалежно від зміни UID через sudo** — тому `sudo apt-get update`,
запущений із цього сервісу, теж потрапляв під обмеження, навіть
попри root-права. `/var/lib/apt/lists` не було серед дозволених
шляхів (лише `/var/lib/starlink-monitor`,
`/etc/starlink-monitor` — жоден із них не стосується apt).

**Виправлення**: `/var/lib/apt/lists` додано до `ReadWritePaths=` у
`starlink-webui.service`. `install.sh`/`update.sh` вже мають
механізм автовиявлення різниці unit-файлів (`diff` між новим і
встановленим) з автоматичним `daemon-reload`+`restart` — ця правка
застосується сама при наступному `update.sh` без додаткових дій.

**Урок**: перевіряючи новий subprocess-виклик через `_run_system_
command()`, варто явно перевіряти чинні systemd hardening-директиви
сервісу (`ProtectSystem`, `ReadWritePaths`), не лише sudoers-права —
обидва шари можуть незалежно блокувати одну й ту саму команду.

## Валідація target-версій стала channel-aware (різні build-канали mr/cr)

**Проблема, знайдена користувачем на реальному використанні**: спроба
ввести `2026.07.06.cr81950.49600` як target-версію тарілки хибно
відхилялась як "старіша" за вже відому `2026.07.19.mr82648` — хоча
обидві МОЖУТЬ бути легітимними, актуальними версіями одночасно для
РІЗНИХ апаратних ревізій, просто з незалежних build-каналів (`cr`
vs `mr` префікс у build-сегменті).

**Причина**: попередня валідація обчислювала ОДИН глобальний
`baseline` (максимум з усіх target+поточної версії) і порівнювала
КОЖНОГО кандидата проти НЬОГО, незалежно від того, чи candidate
стосується зовсім іншого, незалежного build-каналу.

**Реалізація**: `db.version_channel()` витягує буквений префікс
build-сегмента (`mr`/`cr` тощо). `_find_older_candidates()` (`webapp.
py`) порівнює candidate ЛИШЕ проти baseline ТОГО САМОГО каналу.

**Реальний edge case знайдений власним тестом одразу після першої
реалізації** (до живого запуску): candidate БЕЗ явного каналу (проста
дата `2020.01.01`, без mr/cr-суфікса) спочатку хибно трактувався як
"свій окремий, непорівнюваний канал" — жоден наявний baseline не мав
"None"-каналу, тому старіша версія БЕЗ явного суфікса помилково
приймалась без перевірки. Виправлено: якщо candidate не має явного
каналу, порівнюється ГЛОБАЛЬНО з усіма baseline (fallback на стару
поведінку), channel-isolation застосовується лише коли candidate САМ
має конкретний, явний канал.

**Перевірено живими тестами** (4 нові, 70 усього): `version_channel()`
коректно витягує `cr`/`mr`/`None`; точний сценарій користувача
(`cr` vs `mr`) тепер приймається; контрольний тест — та сама версія
В МЕЖАХ ТОГО САМОГО каналу все ще коректно відхиляється (фіча не
послабила звичайний захист); edge case candidate без каналу порівнюється
глобально, не хибно приймається.

## Можливість вимкнути сповіщення "Dish знову online"

**Запит користувача**: не надсилати в Telegram "✅ Dish знову online
(після N невдалих спроб)".

**Реалізація**: новий параметр `STARLINK_NOTIFY_DISH_RECOVERY`
(дефолт `1`) — обгортає ОБИДВА варіанти цього сповіщення (звичайний
"після N невдалих спроб" і "muted"-варіант з тривалістю простою) в
`poll_once()`. `logger.info(...)` (журнал systemd) лишається
незалежним — пишеться завжди, вимикається лише Telegram-сповіщення.
Консистентно з наявним UI-паттерном bool-параметрів (`config_editor.
py`, той самий стиль, що `DISPLAY_ENABLED`/`AUTO_REBOOT_ENABLED`).

**Перевірено живими тестами** (2 нові, 72 усього): дефолт (увімкнено)
реально надсилає сповіщення; `NOTIFY_DISH_RECOVERY=False` повністю
пригнічує його. Стійкість до рандомізованого порядку виконання тестів
підтверджена (`pytest-randomly`, два прогони) — другий тест явно
відновлює `config.NOTIFY_DISH_RECOVERY=True` у `finally`, щоб не
"протікати" глобальний стан у інші тести.

## Можливість вимкнути сповіщення про відкат прошивки

**Запит користувача**: не надсилати в Telegram "Прошивка роутера
відкочена (можливо, SpaceX-side)".

**Реалізація**: новий параметр `STARLINK_NOTIFY_FIRMWARE_ROLLBACK`
(дефолт `1`) — `_format_firmware_change_message()` повертає `None`
замість тексту, коли це rollback і параметр вимкнений; `Optional[str]`
тип, обидва виклики (`upsert_dish_and_notify()`/`upsert_router_and_
notify()`) перевіряють на `None` перед `notify_fn(...)`. Звичайне
"🔄 оновлена" лишається завжди активним — параметр контролює **лише**
rollback-варіант, окремо. Спільний для dish і router (та сама
функція обробляє обидва компоненти).

**Перевірено живими тестами** (3 нові, 74 усього): точний сценарій
запиту (router rollback) реально пригнічується при вимкненому
параметрі; forward-оновлення ("🔄 оновлена") не зачіпається тим самим
перемикачем (контрольний тест). Стійкість до рандомізованого порядку
виконання підтверджена (два прогони `pytest-randomly`) — обидва нові
тести, що змінюють `config.NOTIFY_FIRMWARE_ROLLBACK`, явно відновлюють
`True` у `finally`, щоб не "протікати" стан у інші тести.

## Target-версія завжди узгоджується з фактично встановленою (навіть після rollback)

**Проблема, знайдена користувачем на практиці**: `2026.07.19.mr82648`
хибно відхилявся як "старіший" за раніше введений target
`2026.07.24.mr83021` — обидва в тому самому build-каналі (`mr`), тому
попередній channel-aware фікс тут не допоміг.

**Реальний сценарій**: dish, ймовірно, зазнав РЕАЛЬНОГО rollback
(SpaceX-side, вже підтверджений раніше в проєкті) ПІСЛЯ того, як user
уже ввів target для очікуваної, новішої версії (07-24). Поточна
встановлена версія (тепер 07-19) стала старішою за збережений target
— user хотів узгодити target із ФАКТИЧНОЮ реальністю, отримати
сповіщення, коли ЦЯ версія стабільно підтвердиться, але стара логіка
блокувала це, порівнюючи проти `max(попередній target, поточна)`, не
розрізняючи "випадкова описка" від "свідоме узгодження з поточним
станом".

**Виправлення**: `_find_older_candidates()` отримав окремий параметр
`current_installed` — candidate, що ТОЧНО збігається з фактично
встановленою версією (`get_latest_metric()`/`get_router_status()`,
не попередній target), ЗАВЖДИ дозволяється, незалежно від старішого
попереднього target. Логіка: узгодження з реальністю НІКОЛИ не є
"випадковим відкатом".

**Перевірено живими тестами** (2 нові, 76 усього): точний сценарій
запиту (target=07-24, потім реальний rollback на 07-19, спроба
узгодити target=07-19) тепер приймається; контрольний тест підтверджує
— справжня описка (candidate, що НЕ збігається з поточною версією і
не новіший) все ще коректно відхиляється, фікс не послабив основний
захист.

## Аудит дублювання - усунуто dish/router валідацію в api_set_target_versions

**Знахідка**: `api_set_target_versions()` мала два блоки (dish/router)
для валідації target-версій, які накопичили **повну структурну
ідентичність** через кілька послідовних правок ОБОХ блоків паралельно
(channel-aware валідація, потім current_installed виняток) — та сама
логіка, лише різні змінні/ключі/лейбли.

**Виправлення**: винесено в `_validate_and_save_target(target_raw,
target_key, current_installed, component_label)` — повертає
`(saved_label, rejected_message)`, викликається двічі (dish/router)
замість дублювання ~20 рядків логіки.

**Перевірено**: усі 27 наявних тестів `test_webapp.py` пройшли БЕЗ
модифікацій після рефакторингу — поведінка ідентична, лише структура
коду змінилась.

**Ширший аудит** (AST-based структурне порівняння Python-функцій,
пошук однойменних JS-функцій між файлами): нових значущих дублювань
не знайдено. `upsert_known_device_dish()`/`upsert_known_device_router()`
(db.py) залишені окремими навмисно — SQL із різними назвами стовпців,
об'єднання через динамічний SQL погіршило б читабельність/безпеку
заради малої вигоди (docstring explicit визнає схожість). JS-функції
з однаковими іменами між файлами (`handleClearEvents`/`refreshEvents`/
`el`) — уже раніше перевірені, легітимні навмисні відмінності.

## Видалено мертвий код (thin-wrapper методи, залишені лише для тестів)

**Знахідка повного аудиту**: AST-based пошук мертвого коду виявив 4
функції, що вважались "живими" через попередні перевірки, АЛЕ
насправді стали мертвими після рефакторингу на module-level функції
(попередній запис) — `Watchdog._check_target_version_reached()`,
`_check_both_targets_reached()`, `_version_in_target_list()` (методи
класу), `webapp._is_older_version()`. Жоден реальний production-код
не викликав їх напряму — лише ~25 тестів (`watchdog._check_...(...)`)
і ~6 тестів (`_is_older_version(...)`), залишені як API-сумісність
під час попереднього рефакторингу.

**Виправлення**: видалено всі 4 thin-wrapper функції. Тести
переписані на прямі виклики module-level функцій
(`monitor.check_target_version_reached(..., watchdog._notify)`,
`monitor.check_both_targets_reached(watchdog.last_known_dish_id,
watchdog._notify)`, `db.is_older_version(...)`).

**Знайдено й виправлено додатково під час рефакторингу**:
`docs/architecture.md` мав 2 застарілі посилання на видалені методи
класу (`Watchdog._check_target_version_reached()` тощо) — не оновлені
разом із попереднім рефакторингом. Одна з правок ВИПАДКОВО залишила
буквальне дублювання абзацу (той самий текст двічі поспіль) —
знайдено й виправлено одразу при перегляді результату власної
правки.

**Перевірено**: AST-based пошук мертвого коду повторно запущений
ПІСЛЯ видалення — підтверджує, що прогалина реально закрита (порожній
результат). Усі 76 тестів пройшли після переписування на прямі
виклики — поведінка ідентична. Стійкість до рандомізованого порядку
виконання підтверджена (два прогони `pytest-randomly`).

## Сповіщення про запуск Pi після перезавантаження

**Запит користувача**: повідомляти в Telegram при запуску після
включення/перезавантаження Raspberry Pi Zero 2 W.

**Реалізація**: `monitor.pi_just_booted()` (чиста, тестована функція)
порівнює `psutil.boot_time()` (уже використовується в `system_metrics.
py`) з `time.time()`, поріг 120с — відрізняє РЕАЛЬНЕ завантаження Pi
від звичайного `sudo systemctl restart starlink-monitor.service`
(напр. під час `update.sh`). Без цього розрізнення сповіщало б
набагато частіше, ніж семантично означає "Pi увімкнувся/
перезавантажився" — кожне оновлення коду теж перезапускає сервіс.

Новий параметр `NOTIFY_PI_STARTUP` (дефолт `1`). Виклик на початку
`run_forever()`, одразу після `db.init_db()`, ПЕРЕД `telegram_bot.
start()` — не залежить від нього (`telegram_notify.send_message()`
самостійний модуль, окремий від `TelegramBot`-класу).

**Перевірено живими тестами** (3 нові, 79 усього): щойно завантажений
Pi (10с тому) → `True`; давно працює (годину тому) → `False`;
кастомний поріг (200с тому, поріг 120с vs 300с) — обидва напрямки
межового випадку.

## Плановий reboot Starlink Mini по таймеру

**Запит користувача**: перезавантаження Starlink Mini по таймеру,
кожні N годин (уточнено: обидва компоненти одночасно, весь Mini).

**Реалізація**: `reboot_dish()` — єдина доступна reboot-команда
(окремої router-reboot команди немає), перезавантажує ВЕСЬ фізичний
Mini (dish+router — той самий пристрій, той самий hardware/живлення
— підтверджено попереднім архітектурним рішенням про `known_devices`:
"router прив'язується до dish_id того самого фізичного Mini").

`should_scheduled_reboot()` — чиста функція. `self.last_scheduled_
reboot_ts` — ОКРЕМИЙ атрибут (не перевикористання наявного `last_
reboot_ts`, який ініціалізується `0.0` навмисно для "дозволити
auto-reboot одразу при невдачах") — ІНІЦІАЛІЗУЄТЬСЯ `time.time()`,
інакше перше застосування спричинило б негайний reboot при КОЖНОМУ
старті сервісу (`now - 0.0` завжди величезне число). Знайдено й
уникнено ДО написання коду, через аналіз наявної ініціалізації
`last_reboot_ts`, не через живий тест постфактум.

Поважає `MIN_REBOOT_INTERVAL_SEC` через СПІЛЬНИЙ `last_reboot_ts` (з
auto-reboot-при-невдачах) — якщо reboot вже стався нещодавно з іншої
причини, плановий природно "відкладається".

`SCHEDULED_REBOOT_ENABLED` — дефолт `0` (opt-in, на відміну від
решти notification-toggles цього проєкту, які типово дефолт `1`) —
свідомий вибір: сама ДІЯ (reboot) потенційно розриває з'єднання на
кілька хвилин, на відміну від пасивних сповіщень.

**Перевірено живими тестами** (6 нових, 85 усього): вимкнено за
замовчуванням; інтервал ще не минув — тихо; інтервал минув — reboot
реально відбувається з коректним сповіщенням; MIN_REBOOT_INTERVAL_SEC
захист — reboot, що вже стався нещодавно з іншої причини, природно
відкладає плановий (не подвоює). Стійкість до рандомізованого порядку
виконання тестів підтверджена (два прогони `pytest-randomly`) — усі
тести, що змінюють `config.SCHEDULED_REBOOT_ENABLED`, явно відновлюють
`False` у `finally`.

## Винесено всі "поведінкові" константи в config.py (аудит на запит користувача)

**Запит**: винести всі змінні для конфігурування в env-змінні.

**Систематичний пошук**: усі module-level UPPERCASE-константи поза
`config.py` (14 знахідок). Класифіковано на дві категорії:

**НЕ конфігураційні** (структурні дані, не поведінка) — залишені як
є: словники локалізованих міток (`*_LABELS`, `*_NAMES` — переклади,
не має сенсу робити env-змінною), sysfs/API-шляхи (`THERMAL_ZONE_
PATH`, `API_BASE` — фіксовані системні/API контракти), `SCHEMA`
(SQL DDL), `EDITABLE_PARAMS` (метадані UI), `BACKUP_FORMAT_VERSION`
(internal versioning). Також залишено error-retry backoff в
`shutdown_button.py` (`time.sleep(1)` після невдалого читання GPIO) —
рідкісний edge-case, не user-facing "поведінка", додавання
конфігурованості сюди — over-engineering без реальної користі.

**Реально конфігураційні** (timeout/interval-значення) — винесено 7
параметрів: `SHUTDOWN_BUTTON_POLL_INTERVAL_SEC`/`DISPLAY_BUTTON_POLL_
INTERVAL_SEC` (GPIO polling, окремі для 2 різних сервісів, той самий
дефолт 0.1с, АЛЕ незалежні параметри), `TELEGRAM_SEND_TIMEOUT_SEC`/
`TELEGRAM_POLL_TIMEOUT_SEC`/`TELEGRAM_CONFIRM_TTL_SEC` (telegram_bot.
py), `TELEGRAM_NOTIFY_TIMEOUT_SEC` (telegram_notify.py, окремий

## Реальний баг: "/id не відповідає" — Telegram API помилки мовчки ігнорувались

**Запит користувача**: не приходить відповідь на команду `/id` (список
підключених тарілок).

**Діагностика**: живий тест методу `_cmd_id()` напряму й через повний
`_handle_update()` показав, що код сам по собі коректний у всіх
відтворюваних сценаріях (порожня БД, з даними, повний ID, частковий
збіг). Проблема НЕ в логіці формування відповіді.

**Реальна причина знайдена в `_api_call()`**: перевірялась ЛИШЕ
`requests.RequestException` (мережеві помилки, timeout тощо). АЛЕ
Telegram API повертає ВАЛІДНИЙ JSON навіть для ВІДХИЛЕНИХ запитів
(`{"ok": false, "description": "message is too long"}` при перевищенні
ліміту 4096 символів на повідомлення, чи невалідному HTML-
форматуванні) — `resp.json()` успішно парситься, виняток НЕ
кидається, `ok`-поле НІКОЛИ не перевірялось. Помилка мовчки
ігнорувалась — точний симптом "команда взагалі не відповідає".

`/id` без аргументу (список УСІХ known_devices) — найвразливіша
команда: список зростає з часом (кожна коли-небудь підключена
тарілка), і при достатній кількості записів міг реально перевищити
ліміт Telegram.

**Виправлення**: (1) `_api_call()` тепер явно перевіряє `ok`-поле,
`logger.warning()` із причиною відхилення — захищає всі 7 місць
виклику одразу, не лише `/id`. (2) `_cmd_id()` без аргументу обмежена
`TELEGRAM_ID_LIST_MAX_ITEMS` (дефолт 40) — показує найновіші записи
(`get_all_known_devices()` вже сортує за `last_seen_ts DESC`), з явним
"…і ще N" поясненням, коли список обрізаний (не мовчки втрачає дані).

**Перевірено живими тестами** (4 нові, 94 усього): `ok=False`
відповідь реально логується з причиною; список `/id` реально
обмежується з поясненням про приховані записи; контрольний тест — коли
записів МЕНШЕ за ліміт, пояснення НЕ з'являється (не вводить в оману).
Стійкість до рандомізованого порядку виконання підтверджена (два
прогони `pytest-randomly`).

фактичного рендеру.

## Тести для starlink_client.get_status() — найкрихкіше місце, тепер покрите

**Мотивація**: найдовша "чиста логіка" функція проєкту (~100 рядків),
парсить ~20 полів сирої protobuf-відповіді через `getattr`-ланцюжки.
Саме тут проєкт УЖЕ двічі мав реальні проблеми (розбіжність версій
прошивки з іншим застосунком, парсинг `software_version`), і саме її
неможливо було перевірити без фізичного dish — до цих тестів.

**Техніка**: `SimpleNamespace` як fake protobuf-відповідь (поводиться
однаково для `getattr`-доступу, який і використовує `get_status()` —
навмисно не `dict()`/`namedtuple`, той API нестабільний між версіями,
як зазначено в самому коді). Це перевіряє САМЕ логіку парсингу, не
мережевий стек.

**24 тести**, зосереджені на реальних ризиках:
- **Конвертація одиниць**: bps→Mbps через ÷1e6, не ÷2^20 — помилка
  дала б ~5% розбіжність з офіційним застосунком, важко помітну на око
- **enum-мапінг** `software_update_state` (int→назва): помилка зламала
  б auto-reboot логіку, яка спрацьовує саме на `REBOOT_REQUIRED`;
  невідоме майбутнє значення enum НЕ ламає парсинг (fallback на рядок)
- **getattr-fallback'и**: порожня відповідь / відсутні поля дають нулі
  й `online=True`, НЕ виняток і не хибний offline (різні версії
  прошивки віддають різний набір полів)
- **`None` замість числа** → 0.0 (`or 0.0` fallback)
- **version-поля** → порожні рядки, НЕ `None` (інакше зламалось би
  порівняння версій — `db.is_older_version()` очікує `str`)
- **alerts** — bool-прапорці, не список; збираються лише активні;
  `install_pending` окремо (від нього залежить auto-reboot)
- **Закриття gRPC-каналу навіть при винятку** — витік каналів при
  кожній невдалій спробі (кожні ~10с) вичерпав би ресурси Pi Zero 2W
  за години
- **`disablement_code`** → `state`, включно з реальним `ACCOUNT_
  DISABLED`, який користувач бачив у сторонньому застосунку

**Результат**: усі 24 пройшли з ПЕРШОГО разу — код `get_status()`
виявився надійним у всіх перевірених сценаріях, реальних багів не
знайдено (на відміну від `config_editor.py`, де тест одразу виявив
пропущений `DISH_TIMEOUT`). Тести цінні як регресійний захист: тепер
будь-яка майбутня зміна парсингу перевіряється без фізичного dish.

**Перевірено**: 143 тести усього (було 119), стійкість до
рандомізованого порядку, `mypy` 26 файлів чисто.

## pytest-cov (dev-only) + тести для get_router_info() — закрито знайдену прогалину

**Мотивація**: `pytest-cov` (запущений одноразово для перевірки цінності

`pytest --cov=app --cov-report=term-missing`, задокументовано в README.

**`get_router_info()` — ІНШИЙ механізм парсингу, ніж `get_status()`**:
`subprocess.run(["grpcurl", ...])` + `json.loads()` з camelCase-ключами
(так реально віддає grpcurl), не protobuf-об'єкт через `getattr`.
Тому окремий mock-шлях у тестах (`run_router_info()` mock'ує
`shutil.which`+`subprocess.run`, не `starlink_grpc`), не
перевикористання dish-фікстури.

- **enum `state`** — int, рядок-цифра (`.isdigit()`-гілка), рядок-не-
  цифра (`elif raw_state:` — майбутній текстовий стан), невідоме число
- **`clients`** (список WiFi-пристроїв, унікальне для router) — fallback

- Ті самі базові ризики: `grpcurl` не знайдено, timeout, non-zero
  returncode, невалідний JSON, порожній `deviceInfo`, загальний виняток
  — усі МАЮТЬ повертати offline з `error`, не кидати виняток назовні

**Результат**: покриття `starlink_client.py` зросло з 66% → **90%**
(залишок — `reboot_dish()`, окрема функція поза межами цього завдання,
і один `except: pass` без гілки). Усі 47 тестів (24 dish + 23 router)
пройшли з ПЕРШОГО разу — код виявився надійним.

**Перевірено**: 166 тестів усього (було 143), стійкість до
рандомізованого порядку, `mypy` чисто.

   взагалі) — обидва виправлено після перевірки реального коду, не
   здогадки.

**Перевірено живими тестами** (4 нові, 170 усього): новий стан реально
дає 0 router-update-рядків; попередній прихований стан (`DOWNLOADING_
UPDATE_IMAGE_FAILED`) не зачеплений; контрольний тест — `FLASHING`
(звичайний стан) лишається видимим, підтверджуючи що приховано ЛИШЕ
2 конкретні стани, не всі router-стани взагалі.

## Реальний баг: "wired_mesh_not_using_wan_iface" повертався через ручну перевірку

**Запит користувача**: не відображати статус/повідомлення "дротовий
mesh не використовує WAN".

**Знайдено**: цей alert уже мав фільтр `IGNORED_ROUTER_ALERTS`,
реалізований раніше в проєкті — АЛЕ як **class-attribute всередині
`Watchdog.poll_router()`**, застосовувався ЛИШЕ у фоновому циклі
watchdog'а. Коли пізніше винесено `check_updates_now()` (спільна
module-level функція для веб-кнопки й `/checkupdates` — окремий
рефакторинг, описаний вище) — цей фільтр **не був перенесений**,
тому `check_updates_now()` записувала router-статус напряму, без
фільтрації. Результат: alert реально ЗНИКАВ (фоновий `poll_router()`
його коректно прибирав кожні ~35с), АЛЕ **повертався щоразу**, коли
user тиснув "Перевірити оновлення" вручну — той самий клас бага, що
вже виправлявся раніше в цьому проєкті (дублювання/розбіжність
бізнес-логіки між кількома інтерфейсами до тієї самої дії).

**Виправлення**: `IGNORED_ROUTER_ALERTS` перенесено з class-attribute
у module-level константу (`app/monitor.py`, перед класом `Watchdog`),
застосовується тепер в ОБОХ місцях запису `db.set_router_status()` —
`Watchdog.poll_router()` (`self.IGNORED_ROUTER_ALERTS` → просто
`IGNORED_ROUTER_ALERTS`) і `check_updates_now()` (новий рядок
фільтрації, доданий перед записом).

**Свідомо не чіпав** `MUTED_DISH_ALERTS`/`MUTED_ROUTER_ALERTS`/
`MUTED_ROUTER_UPDATE_STATES` — інша логіка (контролює, чи надсилати
Telegram-сповіщення про **зміну** стану через change-detection
методи класу Watchdog, не "чи показувати alert взагалі"), поза
межами конкретного запиту користувача.

**Перевірено живим тестом до написання persisted-тестів**: реально
відтворив сценарій через `check_updates_now()` з `active_alerts=
["wired_mesh_not_using_wan_iface"]`, підтвердив — alert реально
потрапляв у БД до фіксу, зникав після. Додано 3 persisted тести
(173 усього): фільтрація реально працює через `check_updates_now()`;
контрольний тест — інші alerts (не в списку) не зачіпаються; сама
множина містить очікуване значення. Усі 77 наявних тестів `test_
monitor.py`/`test_telegram_bot.py`/`test_webapp.py` пройшли без
модифікацій — рефакторинг (class-attribute → module-level) зворотно
сумісний.

## install.sh: не знаходив NetworkManager-профіль для неактивного зараз інтерфейсу

**Помилка на практиці**: реальний запуск `install.sh` видав "Не
вдалося знайти профілі NetworkManager для eth0 і/або wlan0" під час
налаштування статичних IP, хоча профілі реально існували.

**Причина**: пошук робився через `nmcli -t -f NAME,DEVICE connection
show` (без `--active`) і фільтрувався за `DEVICE`-стовпцем — АЛЕ цей
стовпець порожній для профілів, які існують, але НЕ активні саме
зараз (типовий випадок: `wlan0` ще не встиг автоматично підключитись
до Starlink WiFi одразу після завантаження Pi, чи USB-Ethernet щойно
фізично вставлений). Скрипт плутав "профіль існує" з "профіль активний
цієї миті" — різні речі в NetworkManager.

**Виправлення**: `find_nm_connection()` — двоетапний пошук. Спершу
активні з'єднання (`connection show --active`, найшвидше, коли
інтерфейс уже `up`). Якщо не знайдено — fallback: перебирає ВСІ
збережені профілі, звіряючи властивість `connection.interface-name`
кожного (прив'язка інтерфейсу в самому профілі, незалежна від
поточного стану активності).

**Перевірено живим тестом** (fake `nmcli` через `PATH`-override,
емулює реальний сценарій — eth0 активний, wlan0 існує але неактивний):
усі 3 сценарії підтверджені (активне з'єднання знаходиться напряму;
неактивне-але-існуюче знаходиться через fallback; неіснуючий інтерфейс
коректно повертає порожній результат) — включно з ТОЧНИМ сценарієм,
що спричинив баг користувача.

## Debug-логування в тихих cleanup except-блоках (3 місця)

в журнал (`caplog`). `display.py`/`shutdown_button.py` навмисно без
нових тестів — той самий clean-up патерн всередині структурно довгих,
раніше свідомо не тестованих напряму `run_forever()`/`watch_button()`
циклів (потребують реального GPIO для повного тестування), додавання
тестової інфраструктури лише заради 1 маленького except-блоку було б
непропорційним.

**Перевірено**: 174 тести усього (було 173), стійкість до

## SD-card-wear reduction: буферизація dish-метрик + рідший system_metrics

**Запит користувача**: розумно зменшити частоту й кількість записів
на SD-картку, не шкодячи функціоналу.

**Крок 1 (реалізовано без узгодження, безпечно, без компромісів)**:
`poll_system_metrics()` (CPU/температура/пам'ять) викликалась
БЕЗУМОВНО на кожному циклі `run_forever()` (10с) — та сама частота,
що критичні dish-метрики, хоча ці дані змінюються повільно. Додано
окремий таймер (`SYSTEM_METRICS_INTERVAL_SEC`, дефолт 60с) — не
зачіпає основний Starlink-моніторинг взагалі.

**Крок 2 (реалізовано ПІСЛЯ явної згоди користувача, реальний
компроміс)**: dish-метрики записувались кожні 10с окремою
транзакцією (8640 записів/добу). `Watchdog.metrics_buffer` накопичує
зчитування в пам'яті, `flush_metrics_buffer()` пише все одним
batch-INSERT (`db.insert_metrics_batch()`, `executemany`) раз на
`DISH_METRICS_BATCH_INTERVAL_SEC` (дефолт 30с, користувач сам
запропонував це число).

**Реальна проблема, знайдена ДО реалізації (перевірка коду перед
написанням, не після)**: `/healthz` перевіряє свіжість `db.get_
latest_metric()` з порогом `POLL_INTERVAL_SEC * 3` = 30с — це
**точно** збігалося з новим batch-інтервалом. Без коригування
формули сама буферизація хибно спрацьовувала б як "watchdog завис"
щоразу, коли перевірка відбувається прямо перед flush. Виправлено:
`max_age_sec = POLL_INTERVAL_SEC * 3 + DISH_METRICS_BATCH_INTERVAL_
SEC`.

**Graceful shutdown (SIGTERM/SIGINT)**: без цього звичайний
`systemctl restart`/`update.sh` втрачав би буферизовані дані щоразу
(не лише при справжньому раптовому вимкненні живлення, яке ми вже
діагностували на цьому пристрої раніше). `run_forever()` реєструє
обробники сигналів, які flush-ять буфер перед виходом.

**Перевірено, що НЕ зачіпає функціонал**: `check_target_version_
reached()` (головне, per-component target-сповіщення) використовує
live `DishStatus`-об'єкт напряму, не читає БД — працює без жодної
затримки. Лише другорядне `check_both_targets_reached()` ("🎉 обидва")
читає БД і може відставати на до 30с — свідомо прийнятний компроміс
для вторинного сповіщення.

**Спільний helper** `db._metric_row_params()` — уникає дублювання
SQL між `insert_metric()` (один рядок, ручна перевірка через
`check_updates_now()` навмисно НЕ буферизується) і новим `insert_
metrics_batch()` (`executemany`).

**Перевірено живими тестами до написання persisted-версій**:
реальне накопичення в буфері + flush всіх разом; реальний `SIGTERM`
через `os.kill()` з підтвердженням, що дані реально потрапляють у БД.
4 нові persisted тести (178 усього) + тристороння звірка (49
параметрів, 0 розбіжностей). Стійкість до рандомізованого порядку
підтверджена 3 незалежними прогонами.

**Оцінка впливу**: ~19750 записів/добу → ~1440 (system) + ~2470
(router) + ~288 (dish, при 30с batch) ≈ ~4200 записів/добу
(**-79%** від початкового обсягу).

## Три пропозиції покращення надійності — усі реалізовані

**Запит користувача**: реалізувати всі три раніше запропоновані
покращення надійності одразу.

### 1. Перевірка цілісності БД (`db.check_integrity()`)
`PRAGMA quick_check` у тому самому щоденному циклі, що вже наявний
`VACUUM`. При виявленому пошкодженні — `monitor.check_db_integrity_
and_notify()` сповіщає в Telegram і намагається аварійний backup
(в `try/except` — якщо БД реально пошкоджена, сам backup теж може
провалитись, читаючи з тієї самої БД, але спроба краща за мовчання).

**Реальна помилка, знайдена живим тестом одразу після першої
реалізації**: коли файл ВЗАГАЛІ не є SQLite (не просто пошкоджені
дані всередині), `PRAGMA quick_check` кидає `sqlite3.DatabaseError`
замість повернення результату — `check_integrity()` спочатку не

### 2. Автоматичний періодичний backup з ротацією
Виніс спільну логіку побудови backup-словника з `webapp.py
api_settings_backup()` у нову `monitor.build_backup_dict()` (і

ризику циклічного імпорту: `webapp.py` вже імпортує `monitor`, тому

backup()` пише JSON-файл, зберігає останні `AUTO_BACKUP_KEEP_COUNT`
(дефолт 4), старіші видаляє. Дефолт увімкнено (`AUTO_BACKUP_ENABLED
=1`) — на відміну від `SCHEDULED_REBOOT_ENABLED`, backup не має
побічних ефектів на моніторинг.

**Критична помилка, знайдена ДО запуску (не постфактум)**: новий
`AUTO_BACKUP_DIR` обчислювався від `DB_PATH` у своєму визначенні,
але `DB_PATH` була оголошена нижче у файлі — `NameError` при кожному
імпорті `config.py`. Виправлено порядок, підтверджено РЕАЛЬНИМ
імпортом (`py_compile` такого не ловить — лише синтаксична
перевірка, не виконання module-level коду).

**Друга помилка**: `AUTO_BACKUP_INTERVAL_SEC` дефолт спочатку писався
як `str(7 * 86400)` (обчислюваний вираз) замість літерального рядка
`"604800"` — зламало б автоматизовану тристоронню звірку (regex шукає
літеральні рядки в лапках). Виправлено на явне число, консистентно
з рештою проєкту.

**`AUTO_BACKUP_DIR` навмисно поза UI** (`NOT_IN_UI` у тесті) — той

**Перевірено живими тестами до написання persisted-версій** для

## install.sh: find_nm_connection() — третій fallback для netplan-профілів (продовження)

**Реальний баг на практиці, ПІСЛЯ попереднього фіксу**: `find_nm_
connection()` (двоетапний пошук — активне з'єднання + fallback за
`connection.interface-name`) досі не знаходив `wlan0`-профіль на
конкретному пристрої користувача. Ретельна діагностика (кілька
хибних гіпотез — locale-залежна поведінка bash-regex, розрив SSH
при зміні IP eth0, застаріла версія коду — усі спростовані живими
тестами й `bash -x` trace-логом) привела до точної причини:
`nmcli -g connection.interface-name connection show netplan-wlan0-
STARLINK` повертав ПОРОЖНІЙ рядок для профілю, реально прив'язаного
до `wlan0` (судячи з назви). Профілі, згенеровані через **netplan**
(поширений механізм на сучасних Raspberry Pi OS), часто НЕ мають
явної `connection.interface-name` властивості — прив'язка йде іншим
механізмом (SSID-match, MAC), тому попередній fallback структурно
не міг їх знайти.

**Виправлення**: третій fallback-рівень у `find_nm_connection()` —
пошук за `connection.type` (`802-11-wireless` для `wlan*`, `802-3-
ethernet` для `eth*`/`usb*`), **лише** якщо існує РІВНО ОДИН профіль
цього типу (уникає неоднозначного вгадування, якщо кілька WiFi-
профілів існують одночасно — на Pi Zero 2W з одним WiFi-чіпом і
одним USB-Ethernet це надійна, однозначна евристика в переважній
більшості реальних установок).

**Процес діагностики, вартий відзначення**: три послідовні хибні
гіпотези (locale, SSH-розрив, застарілий код) були кожна перевірена
й спростована ЖИВИМ тестом чи прямим питанням користувачу ДО
переходу до наступної, а не залишена як недоведене припущення.
Фінальний, точний діагноз отримано через `bash -x`-trace від
користувача (не подальші здогадки) — конкретний рядок логу
(`bound_iface=` порожній для `netplan-wlan0-STARLINK`) дав
беззаперечний факт.

**Перевірено живим тестом** (fake `nmcli` через `PATH`-override,
точна репродукція реального сценарію користувача — `netplan-eth0`
активний, `netplan-wlan0-STARLINK` існує з порожньою `interface-
name`): обидва інтерфейси тепер реально знаходяться. Контрольний
тест — два WiFi-профілі одночасно (неоднозначний випадок) — функція
коректно відмовляється вгадувати (`exit 1`), не застосовує IP-
налаштування до випадкового профілю.


## LED активності SD-картки — новий опційний GPIO-функціонал

**Запит користувача**: додатковий світлодіод, що індикує активність
запису на SD-картку (аналогічно вбудованому activity-LED настільних
дисків).

**Ключове архітектурне рішення**: на відміну від кнопки/дисплея (окремі
процеси/сервіси, реагують на власний таймер/зовнішню подію) — LED
**не окремий процес**, частина `monitor.py`, бо має реагувати на кожен
реальний commit у SQLite, а не працювати за власним розкладом.
Реалізовано через глобальний callback-хук у `db.py:get_conn()`,
що спрацьовує **лише** після успішного `conn.commit()` (не при
винятку/rollback) — уникає дублювання коду в кожному з багатьох
місць запису (dish-flush, system_metrics, events, router-status,
backup, VACUUM).

**Лише watchdog-процес (`monitor.py`) ініціалізує LED, не `webapp.py`**
— свідоме рішення, щоб уникнути конфлікту двох процесів за один
ексклюзивний GPIO-запит (gpiod character-device API не дозволяє
двом процесам одночасно тримати запит на ту саму лінію).

**Реальна критична прогалина, знайдена ДО тестування на залізі (не
постфактум)**: `starlink-monitor.service` мав `ProtectSystem=strict`,
але **не** мав `SupplementaryGroups=gpio` (на відміну від `starlink-
shutdown-button.service`, де цей рядок явно присутній) — без нього
watchdog-процес не мав би доступу до `/dev/gpiochip*` на реальному Pi,
і фіча просто не працювала б, показуючи лише мовчазний warning у
журналі. Знайдено порівнянням із конфігурацією іншого GPIO-сервісу,
не випадково. `install.sh` уже додає `RUN_USER` до групи `gpio` для
кнопки/дисплея — додаткових кроків встановлення не потрібно.

**Реалізація**:
- `app/gpio_utils.py` — нова `open_output_line()` (симетрична до
  наявної `open_input_line()`, `Direction.OUTPUT`/`LINE_REQ_DIR_OUT`
  замість `INPUT`, gpiod v1/v2-сумісна)
- `app/activity_led.py` — новий модуль, `ActivityLed.blink()`
  неблокуючий: вмикає LED синхронно, вимкнення через `threading.
  Timer` (daemon-потік) — сам запис у БД не отримує додаткової
  затримки. Послідовні `blink()` скасовують попередній таймер
  (`Timer.cancel()`) — LED лишається рівно увімкненим між частими
  записами, не блимає нервово
- `STARLINK_ACTIVITY_LED_PIN=0` (дефолт, вимкнено) — той самий
  принцип opt-in, що кнопка/дисплей; дефолтний пін 17 не перетинається
  з наявними (27 кнопка, 8/25/24/18 дисплей)

**Перевірено живими тестами**: реальне мигання через mock GPIO;
поведінка при pin=0 (не намагається відкрити GPIO взагалі); провал
ініціалізації (пін зайнятий) повертає False, не кидає виняток;
callback реально спрацьовує після `insert_event()`; callback НЕ
спрацьовує при винятку/rollback; провал самого callback не ламає
запис у БД; два послідовні `blink()` дають `[1, 1, 0]`, не
`[1, 0, 1, 0]` (немає проміжного вимкнення).

**Дрібна прогалина, знайдена й виправлена одразу**: опис `test_db.py`
в `docs/index.md` був застарілим (згадував тест безшовності графіка,
видалений разом із функціоналом "Тренди" в попередній сесії) —
виправлено заразом з додаванням нового тестового файлу.

**ASCII-схема підключення в README свідомо НЕ змінена** (ризик
зламати точно вивірене вирівнювання box-drawing символів, підтверджений
раніше в проєкті) — LED задокументовано окремим текстовим рядком під
схемою замість вбудовування в саму графіку.

**Перевірено**: 199 тестів (було 188, +11 нових: 7 для activity_led.py,
4 для callback-хука в db.py), `mypy` чисто (27 файлів, +1 новий),

## Повідомлення на TFT-дисплеї при reboot/poweroff Pi

**Запит користувача**: показувати повідомлення на екрані при
виключенні/перезавантаженні Raspberry Pi з фізичної кнопки або
Telegram-бота. Уточнено: Telegram-команд для Pi reboot/shutdown
не існувало взагалі (`/reboot` у боті стосується Starlink Mini, не
Pi) - користувач підтвердив, що НЕ потрібно додавати нові Telegram-
команди, обсяг звузився до кнопки + веб-дашборду (обидва вже мали
дію, потребували лише показу повідомлення).

**Ключова архітектурна проблема**: `display.py` — окремий процес,
що ексклюзивно тримає SPI-запит (той самий клас обмеження, що вже
вирішувався для LED-активності через GPIO character-device API) —
неможливо намалювати щось на екрані напряму з іншого процесу
(webapp.py/shutdown_button.py). Крім того, `systemctl reboot/
poweroff` надсилає SIGTERM усім systemd-сервісам (включно з
display.py) майже одразу — вікно часу для показу повідомлення дуже
вузьке.

**Рішення**: новий спільний модуль `app/pi_power.py` записує DB-
сигнал (`db.set_setting(PENDING_ACTION_SETTING_KEY, action)`) ПЕРЕД
реальним викликом `systemctl`, чекає `DISPLAY_SHUTDOWN_MESSAGE_
DELAY_SEC` (типово 2с, лише якщо `DISPLAY_ENABLED=1`) - дає час
display.py помітити сигнал. `display.py` опитує цей setting у своєму
швидкому (~100мс) циклі кнопки, НЕ у звичайному 5-секундному циклі
оновлення статусу - надто повільно для вузького вікна до SIGTERM.
Виявивши сигнал, малює `_draw_power_action_message()` і одразу
завершує `run_forever()`.

**Рефакторинг замість дублювання**: `webapp.py` (`/api/system-
reboot`/`-shutdown`) і `shutdown_button.py` (`_trigger_shutdown`)
обидва переведені на `pi_power.execute_pi_power_action()`. `display.
py` вже імпортував `_trigger_shutdown` напряму з `shutdown_button.py`
(не дублював код) - тому одне виправлення в `shutdown_button.py`
автоматично поширилось на обидва шляхи виклику кнопки.

**Провал команди прибирає сигнал** (`db.set_setting(..., "")`) -
інакше він лишився б "завислим", і наступний запуск display.py
показав би застаріле повідомлення про вимкнення, хоча Pi реально
продовжує працювати.

**Реальна помилка в API-дизайні, знайдена живим тестом (не
production-баг, тестова пастка)**: перша версія `notify_fn:
Callable[[str], Any] = telegram_notify.send_message` - early-bound
default-параметр, обчислюється ОДИН раз при імпорті модуля.
`patch("app.telegram_notify.send_message")` у тесті не міг замінити
вже "заморожене" посилання на оригінальну функцію - тест провалився
з "Called 0 times", хоча production-код працював би правильно.
Виправлено на lazy-визначення (`Optional[...] = None`, `if notify_fn
is None: notify_fn = telegram_notify.send_message` всередині функції)
- краща практика незалежно від тестів.

**Реальна регресія, знайдена ЛИШЕ візуальним переглядом зображення,
не автоматизованою перевіркою**: перша версія символів для
повідомлення (`⏻`/`🔁`) виглядала як порожні "тофу"-квадрати на
DejaVu-шрифті. Автоматизована перевірка `font.getmask(ch).getbbox()
is not None` хибно підтвердила "гліф є" - fallback-гліф (тофу) теж
дає непорожній bounding box, тому ця перевірка недостатня. Знайдено
лише реальним рендерингом зображення й переглядом через `view`.
Замінено на `●` (той самий символ, що вже підтверджено працює в
`_status_lines()` для online/offline індикатора) - урок: для
перевірки шрифтового рендерингу потрібен реальний візуальний огляд,
не лише bbox-перевірка гліфа.

**Перевірено живими тестами до написання persisted-версій**: повний
цикл через реальний Flask test-client (`POST /api/system-reboot`)
підтвердив, що DB-сигнал реально записується через справжній HTTP-
запит, не лише прямий виклик функції.

**12 нових persisted тестів** (8 для `pi_power.py`, 4 для `display.
py:_draw_power_action_message()`, включно з regression-тестом на
конкретні заборонені emoji-символи) - виявили обидві реальні помилки
(early-binding default, забутий `db_path`-fixture у власному тесті -
той самий клас помилки, що вже траплявся раніше в проєкті).

**Перевірено**: 211 тестів (було 199), `mypy` чисто (29 файлів, +1
новий), тристороння звірка (56 параметрів, знову забута синхронізація
README виправлена), стійкість до рандомізованого порядку.

## Аудит на зайвий/залишковий код: знайдено 1 реальний баг

**Запит користувача**: перевірити весь проєкт на зайвий/залишковий
код.

**Реальний баг, не просто "зайвий код"**: `config.DB_INTEGRITY_
CHECK_INTERVAL_SEC` (параметр, доданий раніше для `check_db_
integrity_and_notify()`) ніколи не читався в коді - `run_forever()`
використовував жорстко закодоване `86400` (той самий, що й VACUUM-
таймер), ігноруючи власний, окремо задекларований і задокументований
параметр. Знайдено систематичною перевіркою: кожен `config.py`-
параметр мав явно зустрічатись як `config.PARAM` десь у `app/*.py`.

**Наслідок до фіксу**: зміна `STARLINK_DB_INTEGRITY_CHECK_INTERVAL_
SEC` через `/settings`-UI чи `.env`-файл нічого не змінювала -
перевірка цілісності БД завжди відбувалась разом із VACUUM (раз на
добу), незалежно від значення параметра.

**Виправлення**: окремий таймер `last_integrity_check` (був
об'єднаний з `last_vacuum`), реально порівнюється з `config.DB_
INTEGRITY_CHECK_INTERVAL_SEC`, не жорстко закодованим числом.

**Виявлений патерн false positive у власному AST-скрипті для пошуку
мертвого коду**: `_turn_off` (activity_led.py) хибно позначався як
"невикористаний" - метод передається як callback у `threading.Timer
(self.blink_sec, self._turn_off)`, це `ast.Attribute` (self.method),
не `ast.Name`, який попередня версія скрипта не розпізнавала (той
самий клас хибного спрацювання, що вже траплявся раніше з
`_handle_shutdown_signal`, переданим у `signal.signal()`). Скрипт
доповнено розпізнаванням `ast.Attribute`-аргументів теж.

**Решта перевірок - чисто**: мертвий код (з виправленим скриптом),
дублікати функцій, невикористаний CSS, HTML `id` без JS-використання,
залишкові згадки раніше видаленого функціоналу (лише легітимні
`downlink_throughput_bps`/`uplink_throughput_bps` поля від Starlink
API лишаються, не пов'язані з видаленим), API-узгодженість,
тристороння звірка параметрів (56, 0 розбіжностей).

**Тест для цього конкретного бага НЕ додано** - виправлення
всередині `run_forever()` (нескінченний цикл, ініціалізує SPI/GPIO),
яка за встановленим принципом проєкту не тестується напряму без
значного рефакторингу (винесення в окрему, тестовну функцію), що
виходить за межі запиту "перевірити на зайвий код".

**Перевірено**: 211 тестів (без змін - жоден наявний тест не
покривав цю конкретну логіку), `mypy` чисто, тристороння звірка,
живий функціональний тест дашборду.

## Опційне вимкнення непотрібних системних служб в install.sh

**Запит користувача**: під час інсталяції додати можливість видалення
непотрібних пакетів, служб і сервісів для зниження системного
навантаження на Pi.

**Ключове рішення - вимикати, не видаляти пакети**: `apt purge` для
конкретних пакетів ризикує зламаними залежностями (особливо на
Raspberry Pi OS, де пакети можуть мати неочевидні зв'язки), а
"системне навантаження" (CPU/RAM від фонових служб) знижується вже
самим вимкненням (`systemctl disable --now`) - без ризику
пошкодження системи, і легко відновлюється (`enable --now`).

**Критична межа безпеки**: мережеві служби (`ssh`, `NetworkManager`,
`wpa_supplicant`, `dhcpcd`) і core systemd-компоненти НІКОЛИ не
входять у список кандидатів на вимкнення - це headless-пристрій без
гарантованого фізичного доступу; заблокований SSH означав би повну
втрату контролю над Pi без переустановки SD-картки. Це найважливіше
архітектурне обмеження цієї фічі, свідомо застосоване з самого
початку дизайну, не знайдене постфактум.

**Список кандидатів** (короткий, добре задокументований у спільноті
Raspberry Pi як безпечний для headless-використання): `bluetooth`+
`hciuart` (BT-стек, є на Pi Zero 2W, не використовується проєктом),
`avahi-daemon`+`.socket` (mDNS/`.local`), `triggerhappy` (hotkey-
демон), `ModemManager` (USB-модеми).

**Кожен кандидат перевіряється індивідуально** (`systemctl list-
unit-files` + `is-enabled`/`is-active`) ПЕРЕД пропозицією - не
питає про службу, якої немає в системі (мінімальні/Lite-образи вже
можуть бракувати частини списку). Показує лише реально знайдені
активні кандидати, не статичний список "про всяк випадок".

**Явне попередження про avahi-daemon**, якщо він серед виявлених
кандидатів - вимкнення забрало б доступ через `raspberrypi.local`
для тих, хто підключається так (не по IP). Попередження показується
УМОВНО (лише коли avahi реально в списку кандидатів), не завжди.

**Окремий, незалежний крок** (той самий блок, після списку служб) -
опційний `apt-get autoremove`/`clean` - безпечна, стандартна
операція (сирітські залежності, кеш .deb), економить дисковий
простір, не CPU/RAM (інший тип "навантаження", ніж вимкнені служби).

**Перевірено живими тестами** (fake `systemctl` через `PATH`-
override, 4 сценарії): виявлення+вимкнення (відповідь "т"),
виявлення+відмова ("N", жодна команда вимкнення не виконується),
попередження про avahi-daemon показується умовно лише коли він
реально серед кандидатів, порожній список кандидатів (мінімальний
образ) коректно пропускає крок без помилки.

**Перевірено**: `bash -n` install.sh, живі тести всіх 4 сценаріїв.
Не додано pytest-тестів - `install.sh` (bash, hardware/system-
специфічний) не покривається pytest-набором проєкту (Python-код),
той самий принцип, що решта bash-скриптів.

## Видалено метод downsample_old_metrics()/таблицю metrics_downsampled

**Запит користувача**: видалити механізм downsampling, після того як
я на прямий запит "яка думка про непотрібний функціонал" відзначив
цю деталь - `downsample_old_metrics()` продовжувала щогодини писати
й видаляти дані в `metrics_downsampled`, але жодне місце в проєкті
більше не читає цю таблицю (усі UI-графіки, що її споживали, видалені
в попередніх сесіях). Класичний "осиротілий" механізм - працює
без жодного споживача результату.

**Явно повідомлений користувачу трейд-офф ПЕРЕД видаленням**: цей
механізм виконував дві ролі - живлення графіків (уже втрачена) і
зменшення розміру БД (raw-метрики старші за `DOWNSAMPLE_AFTER_DAYS`=3
дні агрегувались у рідші `DOWNSAMPLE_BUCKET_SEC`=300с bucket'и,
замінюючи детальні рядки). Без цього кроку `metrics`-таблиця
зберігає повну 30-денну (`HISTORY_RETENTION_DAYS`) деталізацію
замість перших 3 днів деталізовано + 27 днів агреговано - приблизно
у 5+ разів більша таблиця. Користувач підтвердив видалення, знаючи
про цей наслідок з попередньої відповіді.

**Реальна методологічна знахідка під час видалення тестів**: єдиний
тест для `prune_old()` (`test_prune_old_cleans_both_raw_and_
downsampled`) - незважаючи на назву "both" - реально перевіряв ЛИШЕ
очищення `metrics_downsampled`, ніколи не перевіряв очищення самої
`metrics`-таблиці (raw retention). Якби я просто видалив цей тест
разом з рештою downsampling-тестів, `prune_old()` (функція, що
ЗАЛИШАЄТЬСЯ активною і критичною для контролю розміру БД) лишилась
би зовсім без тестового покриття. Написано новий, окремий тест
(`test_prune_old_removes_expired_raw_metrics_keeps_recent`).

**Обсяг видалення**: схема таблиці `metrics_downsampled` (`db.py`),
функція `downsample_old_metrics()` (~40 рядків, включно з SQL-
агрегацією), виклик у `prune_old()` (DELETE-рядок), виклик у
`monitor.py:run_forever()` watchdog-циклі, 2 config-параметри
(`DOWNSAMPLE_AFTER_DAYS`/`DOWNSAMPLE_BUCKET_SEC`) з `config.py`+
`config_editor.py`, 3 старих тести замінені на 1 новий у `test_db.py`.

**Осиротілі рядки в README, знайдені звіркою**: тристороння звірка
(яка перевіряє лише параметри, присутні в `config_editor.py`) сама
по собі показала "0 розбіжностей" одразу після видалення параметрів
з `config.py`/`config_editor.py` - але це НЕ виявляє рядки README,
що лишаються для вже видалених з `config_editor.py` параметрів
(звірка однонаправлена). Явний `grep` по назвах параметрів знайшов 2

## Аудит "повна та максимальна оптимізація" — систематична перевірка

**Запит користувача**: повна та максимальна оптимізація проєкту.

**Методологія**: систематична перевірка кількох незалежних напрямків
(не повторення попередніх code-quality аудитів) - швидкість тестового
набору, SQLite-схема (індекси), N+1-паттерни в запитах, memory leaks
у довготривалих (watchdog) процесах, ефективність logging, розмір
frontend-файлів, частота HTTP-опитувань, дублювання мережевих
запитів до Starlink API.

**Знайдено 1 реальний, значущий баг (не мікрооптимізацію)**: `Telegram
Bot._pending_reboot_confirm` (dict) - запис додається при кожному
`/reboot`-запиті, але видаляється ЛИШЕ через `_handle_callback()`
(реальне натискання inline-кнопки "підтвердити"/"скасувати"). Якщо
користувач просто ігнорує повідомлення (не тисне жодної кнопки) -
запис лишався б у пам'яті процесу НАЗАВЖДИ. Повільний, але реальний
memory leak у процесі, що працює місяцями без рестарту.

**Виправлення**: `_cmd_reboot_request()` тепер прибирає застарілі
(TTL минув) pending-записи з УСІХ chat_id (не лише поточного) при
кожному новому reboot-запиті - природна точка очищення, не потребує
окремого таймера/фонового потоку.

**Перевірено живим тестом ДО написання persisted-версії**: реальний
сценарій (user1 ігнорує /reboot, TTL минає, user2 робить свій /reboot)
підтвердив - застарілий запис user1 реально прибирається.

**Виміряно й свідомо НЕ оптимізовано** (реальні виміри показали
незначущий вплив, ускладнення коду не виправдане):
- `uptime_stats_24h()` (SQL-агрегація по 8640 рядках, реалістичне
  24-годинне навантаження при POLL_INTERVAL=10с) - 2.74мс середній
  час, викликається раз/секунду через `/api/status` - не вартий
  кешування
- `db.get_setting()` у швидкому 100мс-циклі `display.py` (перевірка
  pending reboot/poweroff-сигналу) - 0.21мс на виклик, ~2.1мс/с
  сумарних накладних витрат - навіть на слабшому Pi Zero 2W
  залишається <1% одного ядра CPU

**Перевірено й підтверджено вже оптимальним** (без змін):
- SQLite-схема: усі часто фільтровані таблиці (`metrics`, `events`,
  `system_metrics`) мають явні індекси на `ts`; `settings`/`known_
  devices` мають TEXT PRIMARY KEY (автоматичний унікальний індекс);
  `router_status` - singleton-таблиця (`CHECK id=1`), індекс не
  потрібен
- N+1-паттерн у `merge_known_devices()` (backup-restore) - прийнятний,
  рідкісна ручна операція, весь цикл в одній транзакції, типова
  кількість елементів мала
- Жодного f-string усередині `logger.debug()`/`logger.info()` -
  проєкт консистентно використовує `%s`-форматування (lazy
  evaluation, рядок не будується, якщо рівень логування неактивний)
- `reboot_notify_ts` (monitor.py, той самий клас патерну, що
  memory-leak-баг) - уже коректно самоочищується при кожному виклику
  (list comprehension фільтрує застарілі елементи)
- Frontend: 59KB усіх JS+CSS разом (без мінімізації) - завантажується
  миттєво навіть на повільному WiFi, мінімізація додала б складність
  debugging без вимірюваної користі
- dish/router опитуються окремими, уже різними інтервалами (10с/35с)
  - жодного дублювання grpc-запитів
- Тестовий набір (264 тести) виконується за ~2с - найповільніші
  окремі тести (0.15с) це реальні timing-тести (`threading.Timer`),
  не випадкова повільність

**Перевірено**: 264 тести (було 262, +2 нових для memory-leak фіксу),
`mypy` чисто, стійкість до рандомізованого порядку.

## Аудит "помилки, невикористовувані функції, непотрібний код"

**Запит користувача**: спробувати знайти помилки, неправильні/
невикористовувані функції та непотрібний код.

**Методологія**: систематична перевірка функцій НЕ лише всередині
одного файлу (як попередні аудити), а по всьому проєкту - для
кожної публічної функції в `db.py`/`monitor.py`/`webapp.py`/
`starlink_client.py`/`telegram_notify.py`/`system_metrics.py`/
`config_editor.py`/`display.py`/`shutdown_button.py`/`gpio_utils.py`/
`pi_power.py`/`activity_led.py`/`telegram_bot.py` перевірено виклики
і всередині власного файлу, і в усіх інших `app/*.py`+`tests/*.py`,
з виключенням Flask `@app.route`-декорованих функцій (викликаються
HTTP-маршрутизацією, не прямим Python-викликом - інакше усі 22
endpoints webapp.py хибно позначились би як "невикористані").

**Знайдено 1 реальний баг, не просто невикористану функцію**:
`TelegramBot.stop()` була визначена, але НІКОЛИ не викликалась -
`monitor.py:run_forever()`'s `_handle_shutdown_signal()` (graceful
shutdown при SIGTERM/SIGINT) викликав `flush_metrics_buffer()` і
`led.close()`, але не `telegram_bot.stop()`. Через `daemon=True`
потік технічно вбивався разом з процесом при виході, але НЕ
gracefully - міг перервати HTTP-запит до Telegram API чи виконання
команди в `ThreadPoolExecutor`-worker'і посередині обробки.

**Виправлення виявило другу, приховану проблему**: `telegram_bot`-
змінна була визначена (`TelegramBot()`) ПІСЛЯ реєстрації signal
handler'а (`signal.signal(...)`), а не до неї (на відміну від `led`,
визначеної symmetричноДО). Якби я просто додав виклик `telegram_bot.
stop()` у вже наявний `_handle_shutdown_signal()`, це створило б
реальний (хоч і малоймовірний) race condition: SIGTERM, що прийшов
би МІЖ реєстрацією handler'а і пізнішим створенням `telegram_bot`,
спричинив би `NameError` замість graceful shutdown. Виправлення:
`TelegramBot()`-створення (не `.start()`) перенесено ДО реєстрації
signal handler'а, симетрично до `led` - `__init__()` перевірено як
безпечний для раннього виклику (лише `StarlinkClient()`/
`ThreadPoolExecutor`/порожні структури даних, без мережевих
запитів).

**Перевірено живим тестом** (ізольовано відтворена та сама
послідовність ініціалізації - `run_forever()` не запускається
напряму в тестах, потребує реального Starlink-заліза): підтверджено
- closure реально має доступ до `telegram_bot` одразу після
створення (без очікування `.start()`), `stop()` реально викликається
при симуляції SIGTERM.

**Решта перевірок - чисто**: JS-функції (усі 3 dashboard/settings/
stats.js файли) - жодної невикористаної; `labels.py` - усі 4
label-словники реально використовуються; мертвий код (AST-скрипт з
розпізнаванням `self.method`-callback-передачі) - немає; config-
параметри - усі реально читаються; тристороння звірка - 54
параметри, 0 розбіжностей.

**Тест для цього конкретного бага не додано** - виправлення
всередині `run_forever()`, яка за встановленим принципом проєкту не
тестується напряму без значного рефакторингу (винесення в окрему,
тестовну функцію), що виходить за межі цього аудиту. Перевірено
живим тестом ізольованої логіки замість цього.

**Перевірено**: 264 тести (без змін - жоден наявний тест не
покривав цю конкретну shutdown-послідовність), `mypy` чисто, живий
функціональний тест дашборду.

## Значне збільшення тестового покриття hardware-коду

**Запит користувача**: збільшити тестове покриття hardware-коду
(gpio_utils.py/shutdown_button.py/display.py) - файли, попередньо
позначені як "неминучий сліпий кут" через залежність від реального
заліза (GPIO/SPI).

**Реальна знахідка ПЕРЕД початком роботи**: розпакований архів
виявився старішим за останні security-фікси (XSS-екранування,
файлові права) з попередньої сесії - архів не був перепакований
після них. Відновлено всі втрачені зміни (`escapeHtml()` у 6 місцях,
`chmod 700`/`0600`, sudoers-фікс, settings.html-фікс) і негайно
перепаковано, щоб остаточно не втратити - ДО початку роботи над цим
запитом.

### Результат покриття

| Файл | Було | Стало |
|---|---|---|
| `gpio_utils.py` | 15% | **100%** |
| `shutdown_button.py` | 18% | **96%** |
| `display.py` | 29% | **89%** |

Загальне покриття проєкту: 54% → 63%.

**Ключова методологічна знахідка**: `ButtonPressTracker` (чиста,
стейтфул логіка натискання кнопки) мала явний docstring "легко
тестується подачею довільної послідовності значень через poll()" -
але не мала ЖОДНОГО тесту. Найлегший, найцінніший кандидат виявився
пропущеним найдовше.

**Технічний підхід - підміна hardware-бібліотек у sys.modules ПЕРЕД
викликом функції** (не на рівні модуля - `import gpiod`/`import
board` тощо відбувається лише УСЕРЕДИНІ функцій, тому підміна в
sys.modules реально підхоплюється): дозволило протестувати логіку
вибору gpiod v1-vs-v2 API, повну ініціалізацію SPI-дисплея
(board/digitalio/busio/adafruit_rgb_display), не лише "чисті" функції
без хардвер-залежностей.

**Реальна пастка, знайдена й виправлена during розробки**: перша
спроба зупинити нескінченний `while True`-цикл `watch_button()`
через власний `Exception`-підклас (`StopLoop`) спричинила РЕАЛЬНИЙ
нескінченний цикл під час тестування - внутрішній `except Exception`
самого циклу (обробка помилок читання GPIO) ловив `StopLoop`,
логував "warning", і продовжував `continue` назавжди. Виправлено
через `SystemExit` (BaseException, не Exception-підклас - `except
Exception` його не ловить).

**Друга пастка**: тест long_press-сценарію спочатку не спрацьовував
через занадто швидке виконання ітерацій (мокнутий `time.sleep`) -
реальний час між викликами `ButtonPressTracker.poll()` (немокнутий
`time.time()`) не встигав перевищити `hold_sec`. Виправлено явним
mock `time.time()` з контрольованою послідовністю значень.

**`display.py:run_forever()` - найскладніша функція проєкту** (SPI-
ініціалізація + PIL-рендеринг + GPIO-кнопка + state-машина flash/
auto-off підсвітки в одному нескінченному циклі) - 10 нових тестів
покрили: обидві early-return гілки (DISPLAY_ENABLED=0, відсутні
пакети), провал SPI-ініціалізації, повний цикл із `stop_event`
(чистіший спосіб зупинки, на відміну від `shutdown_button.py` - ця
функція вже мала цей параметр), pending-shutdown сигнал (`pi_power.

## Періодична відправка останнього backup у Telegram

**Запит користувача**: відправка (з можливістю налаштувань
періодичності) останнього backup-файлу з /var/lib/starlink-monitor/
backups/ у Telegram.

**Ключове архітектурне рішення - окремий, незалежний інтервал від
створення backup**: `TELEGRAM_BACKUP_INTERVAL_HOURS` (типово тиждень)
НЕ прив'язаний до `AUTO_BACKUP_INTERVAL_SEC` (створення файлу) -
явно згадано користувачем ("з можливістю налаштувань періодичності"),
дозволяє створювати backup частіше, надсилати рідше (щоб не спамити
Telegram великими файлами при частих backup), чи навпаки.

**Знайдений і застосований існуючий принцип проєкту**: `last_
telegram_backup_sent_ts` ініціалізується `time.time()` у `__init__()`
(не `0.0`) - той самий підхід, що вже застосований до `last_
scheduled_reboot_ts` з явним поясненням у коментарі коду ("інакше
'now - 0.0' завжди величезне число, спричиняючи НЕГАЙНИЙ... при
КОЖНОМУ старті сервісу"). Без цього кожен `systemctl restart` (напр.
під час `update.sh`) негайно надсилав би backup-файл незалежно від
реально минулого інтервалу.

**Другий застосований принцип** (`_maybe_scheduled_reboot()`): таймер
оновлюється БЕЗУМОВНО, до самої спроби відправки, не лише при успіху
- провал (Telegram тимчасово недоступний) не має спричиняти повторні
спроби щоцикл опитування (~10с), а чекати повного інтервалу до
наступної спроби.

**`send_document()`** (`telegram_notify.py`) - той самий retry/eth0-
fallback підхід, що `send_message()` (`_request_with_eth0_fallback()`
з `**kwargs`, підтримує `files=` без жодних змін самої функції), але
через `sendDocument`-endpoint (multipart/form-data). Реальна деталь,
знайдена й вирішена одразу в дизайні (не постфактум): файл
відкривається ЗАНОВО для кожного chat_id окремо - file handle
споживається один раз при завантаженні, повторне використання того
самого відкритого файлового об'єкта для другого запиту дало б
порожнє тіло другому отримувачу. Перевірено живим тестом і persisted
pytest-тестом (`test_send_document_reopens_file_for_each_chat_id`) -
обидва chat_id реально отримують файл повного розміру, не 0 байт
для другого.

**Найновіший файл, не просто "останній створений"**: `max(backups,
key=os.path.getmtime)` - реальна деталь, а не назва файлу
(`backup-{timestamp}.json` технічно вже сортується лексикографічно
так само через unix-timestamp у назві, але mtime - надійніший,
явний критерій незалежно від формату назви).

**Перевірено живими тестами до написання persisted-версій**: повний
цикл (2 backup-файли різного віку, форсований виклик) підтвердив -
реально надсилається НОВІШИЙ файл, не старіший чи випадковий;
окремо перевірено обидва edge cases (вимкнено через config, каталог
backup ще не існує, каталог існує але порожній) - жоден не кидає
виняток.

**Перевірено**: 375 тестів (було 364, +11 нових - 4 для
send_document(), 7 для _maybe_send_backup_to_telegram()), `mypy`
чисто, тристороння звірка (56 параметрів), живий функціональний тест
підтвердив нові параметри реально доступні через `/api/env-config`
(тобто реально видимі на `/settings`-сторінці).

## Ручна кнопка відправки останнього backup у Telegram

**Запит користувача**: додати в область Backup/restore на /settings
кнопку для ручної відправки останнього backup-файлу.

**Рефакторинг ПЕРЕД додаванням нового коду**: спільна логіка "знайти
найновіший backup-файл у AUTO_BACKUP_DIR + надіслати через
telegram_notify.send_document() + записати подію" була раніше
цілком усередині Watchdog._maybe_send_backup_to_telegram() (метод
класу, з periодичною перевіркою інтервалу навколо). Витягнуто в
окрему функцію рівня модуля monitor.send_latest_backup_to_
telegram() - і periодичний виклик (з перевіркою TELEGRAM_BACKUP_
ENABLED/інтервалу навколо), і нова ручна кнопка викликають ту саму
функцію. Уникнуто дублювання логіки пошуку найновішого файлу.

**Ключове архітектурне рішення - ручна кнопка ігнорує TELEGRAM_
BACKUP_ENABLED**: цей параметр стосується лише автоматичного,
periодичного розкладу. Користувач, що явно натиснув кнопку, очікує
негайну дію незалежно від того, чи периодична відправка взагалі
увімкнена в config - логічна поведінка, аналогічна до вже наявного
патерну "ручна перевірка оновлень" (окрема від автоматичного
watchdog-циклу опитування).

**Розрізнення двох різних "немає що надсилати" сценаріїв** з
окремими, зрозумілими для UI повідомленнями: AUTO_BACKUP_DIR ще не
існує ("Каталог backup ще не створений - зробіть перший backup") vs
каталог існує, але порожній ("Немає жодного backup-файлу для
відправки") - перший сценарій частіше трапляється одразу після
встановлення (AUTO_BACKUP_ENABLED=0 за замовчуванням, чи ще не минув
перший AUTO_BACKUP_INTERVAL_SEC), другий - якщо ротація видалила всі
файли чи користувач вручну очистив каталог.

**Новий endpoint**: `POST /api/send-backup-telegram`, повертає
`{"success": bool, "message": str}` - той самий контракт, що решта

**Живий тест до написання persisted-версій виявив власну помилку**:
мій перший живий тест очікував повідомлення "Немає..." для сценарію
"каталог взагалі не існує", хоча реальна, коректна поведінка коду
розрізняє це від "каталог існує, але порожній" з різними
повідомленнями - виправлено тест, не код (код був правильний).

**Перевірено**: 438 тестів (було 433, +5 нових для нового endpoint),

кнопки в HTML-виводі `/settings`, HTML div-баланс, JS-синтаксис.

(є парне "✅ Часті авто-reboot припинились (усього N згруповано)").
Користувач підтвердив - прибрати ЛИШЕ це одне повідомлення, механізм
групування (лічильник, приглушення подальших сповіщень) продовжує
працювати мовчки, підсумкове "припинились"-повідомлення лишається.

**Реалізація**: видалено виключно `self._notify(...)`-виклик
усередині `if not self.reboot_spam_muted:`-гілки. Стан (`reboot_
spam_muted = True`, `muted_reboot_count = 1`) і далі встановлюється -
подальші reboot-сповіщення все одно мовчки приглушуються й
рахуються, підсумок при відновленні (`_check_reboot_spam_recovery()`)
не зачеплено. Прибрано зайву `window_min`-змінну (використовувалась
виключно в видаленому тексті повідомлення).

**Оновлено 1 тест, що перевіряв стару поведінку** (`test_reboot_
notify_threshold_triggers_grouping_warning` → перейменовано на
`test_reboot_notify_threshold_reached_mutes_silently`) - тепер
перевіряє, що при досягненні порогу НЕ надсилається жодне нове
повідомлення (замість попереднього очікування "3-тє повідомлення -
це попередження про групування").

**Перевірено живим тестом**: реальний сценарій 6 reboot-подій
поспіль (поріг=3) підтвердив - надіслані лише перші 2 (до порогу),
жодного повідомлення про "групування", `reboot_spam_muted=True`,
`muted_reboot_count=4` (реально коректно рахує решту).

**Перевірено**: 432 тести (без зміни кількості - переписано 1 наявний
тест, не додано/видалено), `mypy` чисто, README та architecture.md

## Видалено 2 функціонали: obstruction_map_reset-журналювання та rollback-сповіщення

**Запит користувача**: видалити функціонал/повідомлення/DB-запис/
логування для двох окремих речей: "Попередження знято: карта
перешкод скинута" та "Сповіщати про відкат прошивки".

### 1. "Попередження знято: карта перешкод скинута"

**Реальна знахідка ПЕРЕД реалізацією**: `obstruction_map_reset` -
не вигадана проєктом назва, а реальне, офіційне поле від Starlink
API (`DishAlerts`-message), частина 19-елементного `ALERT_LABELS`-
словника. Це не окремий "функціонал", а один запис у загальному
`_log_alerts_change()`-механізмі журналювання появи/зникнення БУДЬ-
ЯКОГО з 19 dish-алертів.

**Точковий фільтр, не видалення механізму**: додано `if alert ==
"obstruction_map_reset": continue` у `resolved`-циклі (лише для
ЗНИКНЕННЯ, не появи - користувач цитував саме "Попередження знято",
не "Нове попередження"). Starlink періодично скидає карту перешкод
сам по собі як частину нормальної роботи (не аварійна подія) - тому
подія при зникненні цього alert'а взагалі не варта журналювання.
Решта 18 dish-алертів (і сам obstruction_map_reset при ПОЯВІ)
журналюються як раніше, без змін.

**Не чіпав**: JS-словник `ALERT_LABELS`-еквівалент у
`static/dashboard.js` - використовується для відображення активних
alert-chips на дашборді (не resolved-журналу), `appeared`-гілку не
чіпав, тому цей мапінг усе ще потрібен для показу активного
попередження, якщо воно з'явиться.

### 2. "Сповіщати про відкат прошивки" (NOTIFY_FIRMWARE_ROLLBACK)

**Реальна знахідка ПЕРЕД реалізацією**: `db.upsert_known_device_
dish()`/`_router()` (оновлення `known_devices`-таблиці реальною
поточною версією) відбувається ЗАВЖДИ, незалежно від напрямку зміни
чи цього параметра - `_format_firmware_change_message()` контролює
ЛИШЕ чи `notify_fn(msg)` (Telegram-сповіщення) викликається.
Видалення параметра не мало торкатись known_devices-оновлення.

**Реалізація**: `_format_firmware_change_message()` тепер завжди
повертає `None` для відкату (`db.is_older_version()`-детекція
лишається), без config-перемикача - раніше `NOTIFY_FIRMWARE_
ROLLBACK=0` був opt-out (типово `1`, сповіщення про відкат
надсилалось за замовчуванням), тепер це завжди-вимкнена, невід'ємна
поведінка. Видалено параметр з `config.py`/`config_editor.py`.

**Переписано 4 наявні тести**: 2 тести, що очікували текст "⏪
відкочена" в Telegram-повідомленні, переписані на очікування
`sent == []` (з перевіркою, що `known_devices` усе одно оновлюється
реальною версією). 2 тести, що явно перевіряли `NOTIFY_FIRMWARE_
ROLLBACK`-config-перемикач, видалені цілком - параметра більше не
існує, тестувати нічого.

**Перевірено живими тестами до написання/виправлення persisted-
версій**: обидва сценарії (obstruction_map_reset-точковий фільтр,
firmware-rollback-мовчазна поведінка) підтверджені реальним викликом
відповідних функцій із контрольованими вхідними даними ПЕРЕД
редагуванням тестового файлу.

**Перевірено**: 432 тести, `mypy` чисто, тристороння звірка (53
параметри, 0 розбіжностей - 54→53, видалено рівно 1 config-параметр),
живий функціональний тест підтвердив - `/api/env-config` реально не
містить видалений ключ, сторінки рендеряться без сліду параметра.
README та architecture.md оновлені для обох функціоналів.

## Виправлено реальний баг: pending-сигнал дисплея не очищався при успіху

**Запит користувача**: функціонал виводу повідомлення на екран при
виключенні/перезавантаженні Raspberry Pi працює неправильно - під
час перезавантаження нічого не відображається, після перезавантаження
на екрані висить текст "Перезавантажується..." безкінечно довго.

**Знайдено реальну причину (не гіпотетичну)**: `execute_pi_power_
action()` (`pi_power.py`) очищав `PENDING_ACTION_SETTING_KEY`-сигнал
ЛИШЕ у гілці провалу команди (`else`). При УСПІШНОМУ reboot/poweroff
сигнал НІКОЛИ не очищався - код одразу після успіху лише викликав
`notify_fn(success_text)`, без жодного `db.set_setting(...,
"")`-виклику. Docstring для `PENDING_ACTION_SETTING_KEY` явно
обіцяв "видаляється після реального виконання команди" - код цю
обіцянку не виконував для успішного шляху.

**Повний ланцюжок, що пояснює ОБИДВА описані симптоми одним і тим
самим коренем**:
1. Успішний reboot - сигнал лишається в БД
2. Pi реально перезавантажується, `starlink-display.service` стартує
   заново
3. `display.py:run_forever()` на самому початку швидкого 100мс-циклу
   бачить той самий застарілий сигнал, малює повідомлення повторно
   (симптом 2: "текст висить") і одразу `return`
4. `Restart=on-failure` НЕ перезапускає процес після чистого
   завершення (`exit 0` - не `failure`) - сервіс лишається `inactive`
   назавжди
5. **Наступний** раз, коли користувач робить reboot/poweroff - жоден
   процес більше не відстежує сигнал (сервіс вже мертвий) - симптом
   1: "під час перезавантаження нічого не відображається"
6. TFT-дисплей фізично зберігає останній намальований кадр у
   власному framebuffer незалежно від стану процесу, що його малював
   - екран продовжує показувати застарілий текст безкінечно, поки
   сервіс вручну не перезапустять

Обидва описані користувачем симптоми - НЕ дві окремі проблеми, а
той самий баг, що проявляється на різних ітераціях use-case
(перший reboot після виникнення бага залишає "зависле" повідомлення
+ мертвий сервіс; кожен наступний reboot після цього вже не показує
нічого нового, бо малювати нема кому).

**Виправлення**: `db.set_setting(PENDING_ACTION_SETTING_KEY, "")`
тепер викликається ЗАВЖДИ одразу після `_run_system_command()`
(успіх чи провал), ще ДО `if ok:`-розгалуження на success/failure-
сповіщення. `systemctl reboot`/`poweroff` не миттєвий - реальні
кілька секунд до фактичного вимкнення достатні для виконання цього
рядка коду.

**Перевірено живими тестами до написання persisted-версії**: (1)
прямий виклик `execute_pi_power_action()` з mock успішного
`subprocess.run()` підтвердив - сигнал реально очищується; (2) повний
сценарій - симуляція ПОВТОРНОГО запуску `display.py:run_forever()`
через fake CircuitPython-модулі (той самий підхід, що `test_display_
run_forever.py`) після успішного reboot підтвердив - жодного кадру
не намальовано (сигнал уже порожній), сервіс реально продовжує
звичайну роботу, не завершується передчасно.

**Знайдено реальну прогалину в тестовому покритті**: усі 11 наявних
тестів `test_pi_power.py` пройшли й ДО фіксу - жоден не перевіряв,
що сигнал очищується САМЕ при успіху (лише симетричний тест для
провалу існував). Додано `test_success_also_clears_pending_signal` -
відсутність цього тесту й дозволила багу залишитись непоміченим
попри значне покриття файлу (82%→100% у попередній сесії).

**Перевірено**: 433 тести (було 432, +1 новий), `mypy` чисто,
`docs/architecture.md` оновлено з повним поясненням причини й
наслідків для майбутньої довідки.

**Додано 2 нові regression-тести** (не лише разова перевірка):

### Реальна, значуща знахідка: дублювання `_run_system_command()`

**Знайдено систематичним порівнянням назв функцій між усіма файлами
`app/`** (не випадково) - `pi_power.py` і `webapp.py` мали
практично ідентичну функцію з тією самою назвою, з дрібними
відмінностями: `pi_power.py`-версія мала фіксований `timeout=15`,
не обрізала error-message, не розрізняла `TimeoutExpired` окремо;
`webapp.py`-версія мала налаштовуваний `timeout` (дефолт 10),
обрізала error-message до 500 символів, явно ловила
`TimeoutExpired`.

**Перевірено ПЕРЕД рефакторингом**: жоден з 3 реальних викликів (1 у
`pi_power.py`, 2 у `webapp.py`) не передавав власний `timeout` -
обидва покладались на дефолти своїх функцій. Це дозволило безпечно
об'єднати без зміни поведінки, передавши `timeout=15` явно для
єдиного виклику, що раніше мав це як хардкод.

**Реалізація**: об'єднано в `pi_power.py` під новою, ПУБЛІЧНОЮ
назвою `run_system_command()` (без початкового `_`) - функція тепер
реально використовується з іншого модуля, `_`-префікс (Python-
конвенція "модульно-приватне") більше не відповідає реальності.
Використано найповнішу версію (з `webapp.py` - обрізання помилки,
явна `TimeoutExpired`-обробка). `webapp.py` більше не має власної
копії, викликає `pi_power.run_system_command(...)`. Побічний ефект
- `import subprocess` у `webapp.py` став зайвим (це був єдиний його
використання), видалено.

**Перевірено живим тестом**: обидва виклики (`pi_power.execute_pi_
power_action()` і `webapp:/api/env-config-restart`) реально
працюють через об'єднану функцію після рефакторингу.

**Не рефакторив** (свідомо, cost/benefit не виправдовує):
`notify()`-функція, продубльована в `telegram_bot.py`/`webapp.py` -
2-рядкова обгортка над `telegram_notify.send_message()`, винесення
в окремий helper додало б зайвий import+indirection заради
мінімальної економії рядків.

**Перевірено**: 435 тестів (без змін кількості - рефакторинг, не
нові тести), `mypy` чисто (34 файли), HTML div-баланс, JS/bash-
синтаксис, живий функціональний тест усіх сторінок, невикористаний
CSS - немає.
