# Журнал рішень

Хронологічний запис значущих технічних рішень і знайдених багів.

## Виявлення реальної схеми gRPC

Starlink Mini — не єдиний пристрій, а два логічні пристрої (dish +
router) з різними `DeviceInfo`, enum-станами, alert-полями —
підтверджено `grpcurl describe`, не здогадкою. `starlink_client.py`/
`labels.py` побудовані на цих підтверджених схемах.

## Баг: конфлікт параметра `timeout` в Telegram API

**Симптом**: бот не отримував команд. **Причина**: `_api_call()`
передавав HTTP-таймаут позиційно й Telegram `timeout=` (long polling)
іменовано — колізія параметрів. **Фікс**: перейменовано на
`http_timeout`.

## NoNewPrivileges вимкнено на webui/shutdown-button сервісах

Обидва викликають `sudo systemctl reboot/poweroff` — `NoNewPrivileges`
блокує будь-який sudo незалежно від sudoers. `starlink-monitor.service`
(sudo не викликає) лишається з прапорцем.

## Фізична кнопка виключення: окремий процес

`shutdown_button.py` — окремий модуль/сервіс, не частина monitor/webapp:
GPIO вимагає групу `gpio`+`python3-libgpiod` (зайва залежність без
кнопки), вимкнено за замовчуванням (pin=0, чистий вихід),
`Restart=on-failure` (не `always`) — чистий вихід не циклить рестарт.
venv створюється з `--system-site-packages` для системного gpiod.

## Баг: reboot-loop при невдалій auto-reboot команді

`last_reboot_ts` оновлювався лише при успіху — невдала спроба (dish ще
перезавантажується) не блокувала повтор щоцикл (~10с) замість
`MIN_REBOOT_INTERVAL_SEC`. Фікс: оновлюється при кожній спробі,
незалежно від результату.

## Статичні IP в install.sh — інтерактивно, не автоматично

Неправильні мережеві дефолти можуть обірвати SSH — питає підтвердження
замість мовчазного застосування. `dhcpcd` вимикається лише в межах
цього опційного кроку (конфліктує з NetworkManager).

## Баг: gpiod v2 несумісний зі старим API кнопки

**Симптом**: `'Chip' object has no attribute 'get_line'`. **Причина**:
Raspberry Pi OS Bookworm+ ставить gpiod 2.x з повністю переписаним API.
**Фікс**: `_init_line_v1`/`_init_line_v2`, вибір через
`hasattr(gpiod.Chip, "get_line")`.

## Мережевий запит install.sh лише при першому встановленні

Питання про статичні IP обгорнуто `MODE=="install"`. `uninstall.sh` —
окремий файл, не прапорець.

## Придушені конкретні Telegram-сповіщення

`MUTED_DISH_ALERTS={"roaming"}`, `MUTED_ROUTER_ALERTS=
{"install_pending"}`, `MUTED_ROUTER_UPDATE_STATES=
{"GETTING_TARGET_VERSION_FAILED"}` — шумні для Telegram, але й далі
пишуться в журнал дашборду.

## Telegram-сповіщення про цикл оновлення ПЗ dish

Перехід у `DOWNLOADING_UPDATE_STATES` → "🔽 Розпочато"; повернення в
`IDLE` → "✅ Завершено". `REBOOT_REQUIRED`/`FAULTED` мають власні
повідомлення навіть при прямому переході.

## Обмеження журналу watchdog-спроб при тривалій недоступності

`MAX_LOGGED_CONSECUTIVE_FAILURES` (30) обмежує запис у журнал —
спроба 31 дає фінальний маркер, 32+ мовчать (сама `reboot_dish()`
викликається без змін).

## Баг: Telegram-бот блокувався на повільних командах

**Причина**: обробка команд (блокуючі gRPC-виклики, до ~15с) йшла в
тому самому потоці, що `getUpdates` polling. **Фікс**:
`ThreadPoolExecutor(max_workers=3)`. Побічний ефект — паралельність
ламала порядок (`/reboot`+підтвердження в різних потоках) — виправлено
групуванням updates за `chat_id`.

## Рефакторинг: спільний хелпер update-ready reboot (dish+router)

`_maybe_reboot_for_update`/`_maybe_reboot_for_router_update` об'єднано
в `_reboot_for_update_ready`. Виявлено й виправлено другий екземпляр
того самого reboot-loop бага для update-ready шляху.

## Backup/restore розширено на параметри моніторингу

`format_version` 1→2: `env_params` містить лише реально перевизначені
значення. Restore через `config_editor.save_values()`, застосовується
після рестарту сервісів.

## Рефакторинг: усунення дублювання (webapp.py, telegram_notify.py)

Спільна логіка (команда+журнал+Telegram) винесена в
`_execute_pi_power_action`.

## Баг: StartLimitIntervalSec/Burst у [Service] замість [Unit]

Ці директиви належать до `[Unit]` — у неправильній секції systemd
мовчки ігнорує їх. Перенесено.

## fetch_starlink_grpc.sh: завантаження через eth0 насамперед

wlan0 має нижчий route-metric за eth0, але це означає й зовнішній
інтернет іде через wlan0 першим — якщо Starlink недоступний, немає
інтернету попри робочий eth0. Фікс: `curl --interface eth0` спочатку.

## Telegram-сповіщення мовчали при відсутньому інтернеті на Starlink

Той самий root cause — HTTP до api.telegram.org теж іде дефолтним
маршрутом (wlan0). `_request_with_eth0_fallback()` — retry через
eth0-прив'язаний сокет, застосовано в send_message/test_connection/
_api_call.

## Оптимізація для мобільних

`.status-row-label`/`.progress-track` фіксовані ширини переповнювали
<480px — стали гнучкими. Додано safe-area-inset, tap-highlight,
44px touch targets, брейкпоінт <360px.

## Cache-busting для JS/CSS

**Симптом**: браузер показував стару поведінку після update.sh
(`SEND_FILE_MAX_AGE_DEFAULT=3600`). **Фікс**: `_static_v()` додає
`?v=<mtime>` до статичних URL в усіх шаблонах.

## Інструкція оновлення: повний шлях замість відносного

`sudo bash scripts/update.sh` провалювався поза розпакованим архівом.
Виправлено на повний шлях `/opt/starlink-monitor/scripts/...`.

## eth0-fallback для Telegram: SO_BINDTODEVICE, не прив'язка до адреси

**Причина провалу першого підходу**: прив'язка сокета до IP-адреси
джерела не форсує фізичний інтерфейс — Linux обирає його за таблицею
маршрутизації на основі адреси призначення, ігноруючи джерельну IP.
**Фікс**: `SO_BINDTODEVICE` — реально форсує інтерфейс. Вимагає
`CAP_NET_RAW` (`AmbientCapabilities`, сумісно з `NoNewPrivileges`).
Ручна DNS-резолюція через eth0-сокет, коли системний DNS теж не
відповідає — фінальний запит напряму на IP з `Host`-заголовком і
`verify=False`.

## Баг: WAN-failover не діяв — NetworkManager відновлював metric

Пряма зміна `ip route` в обхід NetworkManager не працює надійно — той
сам володіє wlan0 і перевідновлює власний metric. Фікс: `nmcli
connection modify ipv4.route-metric` + `nmcli device reapply`.

## Баг: WAN-failover ламав доступ до dish

192.168.1.0/24 (router) має автоматичний kernel-route, 192.168.100.0/24
(dish) — ні, трафік ішов лише дефолтним маршрутом, який
демотувався. Фікс: постійний окремий маршрут через `nmcli
+ipv4.routes`.

## WAN-failover сам спричиняв флапи dish — додано гістерезис

`nmcli device reapply` на мить розриває маршрут до dish, кожен флап
перемикав WAN-failover знову (петля самопідживлення). Фікс:
перемикання лише після 3 поспіль однакових результатів перевірки.

## Баг: DISPLAY_ROTATION=90 не працював для 170×320

Бібліотека `st7789` забороняє rotation=90/270 для прямокутних
дисплеїв. Дефолт змінено на 0; landscape вимагає поміняти
WIDTH/HEIGHT місцями.

## Помилковий висновок з емпіричного тесту: WIDTH/HEIGHT 320x170

Попередня версія мала дефолти 320x170 (поміняні місцями відносно
паспортних 170x320, підтверджених офіційною документацією виробника
й написом на платі) — це був помилковий висновок з емпіричного
тесту: реальна причина залишкового кольорового шуму на 320x170 —
командування контролеру 320 стовпців, тоді як фізична матриця має
лише 170, не сам факт правильного/неправильного порядку значень.
"Покращення" було випадковим побічним ефектом іншої зміни, не
правильним рішенням саме цієї конфігурації. Виправлено на паспортні
170x320.

## Баг: підсвітка працює, зображення немає (RST не виводився)

Бібліотека налаштовувала RST як output LOW і одразу викликала `_init()`
— контролер весь цей час у reset, ігнорує SPI-команди. Фікс: явний
`display.reset()` + повторний `display._init()`.

## Баг: підтвердження мережевого запиту install.sh не розпізнавалось

Можливий прихований `\r` у введенні термінала. Фікс: `tr -d
'[:space:]'` перед перевіркою.

## Заміна бібліотеки дисплея на Adafruit CircuitPython ST7789

Попередня мала RST-баг і заборону rotation для прямокутних дисплеїв,
плюс невирішений кольоровий шум на SKU MSP1901 — спершу помилково
прийнятий за апаратний дефект, реально викликаний зміщенням GRAM
(вирішено пізніше через `DISPLAY_OFFSET_LEFT`/`_TOP`, значення 35/0
емпірично підтверджені робочими). Нова бібліотека
(`adafruit-circuitpython-rgb-display`) коректно виводить RST у
`__init__`, дозволяє будь-який rotation, обертання програмне
(`img.rotate()`). CS — bit-banged GPIO, не апаратний CE0/CE1.

## Баг: WAN-failover падав з "Read-only file system" на /run

`ProtectSystem=strict` робить усю ФС read-only, крім явно дозволених
шляхів — `/run` сам по собі не звільнений. Фікс: `RuntimeDirectory=`
+ `RuntimeDirectoryPreserve=yes`.

## Баг: pip install падав на rpi_ws281x/RPi.GPIO

Відсутній `Python.h` для компіляції C-розширень. Фікс: додано
`python3-dev build-essential` до install.sh.

## Баг: кирилиця не відображалась на фізичному дисплеї

Відсутній `fonts-dejavu-core` — тихий fallback на `ImageFont.
load_default()` без кирилиці. Фікс: додано пакет + явне попередження
в логах, якщо жоден шрифт не знайдено.

## Баг: довге натискання кнопки не вимикало Pi (NoNewPrivileges)

Залишок `NoNewPrivileges=true` у `starlink-display.service` з часів,
коли той не викликав sudo — після перенесення логіки кнопки з
shutdown_button.py в display.py unit-файл забули оновити. Видалено
прапорець.

## Зменшення частоти записів на SD-картку

`PRAGMA synchronous=NORMAL` для WAL — менше fsync(). Розглянуто, але
НЕ застосовано: `Storage=volatile` для journald (втрата journalctl-
історії між перезавантаженнями — критичний діагностичний інструмент,
активно використовуваний протягом розробки).

## starlink_grpc.py винесено як vendor-файл

Динамічне завантаження з GitHub при кожному встановленні означало
залежність від інтернету й непередбачувані версії. Файл тепер
частина архіву (`app/vendor/`), fetch-сервіс лишається лише для
опційного ручного оновлення.

## Сповіщення про зміну версії прошивки dish/router

`upsert_known_device_*()` повертає `(real_change, old_version)`.
**Знайдений edge case**: перша версія вважала зміною будь-яке
існування рядка `known_devices`, не перевіряючи саме поле — dish і
router створюють спільний рядок у різних циклах, перше заповнення
"свого" поля хибно рахувалось зміною з None. Фікс: перевірка
конкретного поля, не факту існування рядка.

## Групування спаму reboot-сповіщень

`_notify_reboot()` — ковзний список timestamps; поріг+вікно →
мовчазне групування до затишшя, тоді підсумок і повний скид стану.

## Типізація (mypy) — пропорційний підхід, без --strict/CI

`mypy --strict` дав 366 помилок у 13 файлах — переважно SQLite
`dict(row)`-патерни і vendor-код. Рішення: return type hints для
всього власного коду, `ignore_errors` для vendor, локальний запуск
(не CI — одноосібний hobby-проєкт, перевіряється живим тестуванням на
залізі). Реальні логічні баги, знайдені під час типізації: неявний
`Optional` у сигнатурах, `poll_once()` типізований як `None` хоча
повертає `DishStatus`, `read_current_values()` сигнатура була
неправильною (список, не dict) — виявлено лише зараз.

## Мобільний PWA офлайн-режим — localStorage-кеш

Доповнює (не скасовує) попереднє рішення "не кешувати API" —
показує застарілі дані з явним індикатором ("X хв тому"), не мовчки.
`localStorage`, не IndexedDB — простий JSON-об'єкт, не варта
складнішого API.

## Темна/світла тема — CSS custom properties + toggle

`[data-theme="light"]` інвертує ті самі CSS-змінні. Inline-скрипт у
`<head>` застосовує тему синхронно (без FOUC). Знайдено й виправлено:
7 хардкоджених hex-кольорів поза `:root`, порядок inline-скрипта
відносно `<meta theme-color>` (querySelector повертав би null).

## Оновлення "безпечних" пакетів у requirements.txt

`install.sh` оновлює пакети лише коли текст файлу змінюється —
без цього версії застрягають назавжди попри `>=`. Оновлено minor/patch
(Flask, requests, dnspython, yagrc), major-розриви (protobuf,
adafruit-blinka) свідомо не чіпались.

## Баг: `pip install --upgrade` оновлював незмінені пакети

`--upgrade` застосовується до всього файлу одразу — зміна одного
рядка означала "онови все", зачепивши й hardware-критичний
adafruit-blinka. Фікс: точні `==`-піни, без `--upgrade`.

## Сповіщення про встановлення очікуваної версії прошивки

`/settings` дозволяє вказати очікувану версію, отримати сповіщення
при збігу. Дедублікація через збережене значення target (не окремий
boolean) — природно скидається при новому target.

## Очікувана версія прошивки — валідація "лише новіші"

`_version_key()` — толерантний компаратор для `YYYY.MM.DD.mrXXXXX.N`,
дата-префікс домінує. dish/router валідуються незалежно (часткова
відмова).

## Комбіноване сповіщення про завершення оновлення (обидва одночасно)

`_check_both_targets_reached()` — "🎉" лише коли ОБИДВІ версії
збігаються одночасно, доповнює per-component сповіщення. Викликається
з обох циклів опитування (dish/router незалежні).

## Формальний test suite (pytest) для найкрихкішої логіки

35 тестів для groupування reboot-спаму, дедублікації target-версій,
компаратора версій — заміна ad-hoc живих тестів, які не персистували
між сесіями.

## Кілька очікуваних версій прошивки для різних апаратних ревізій

SpaceX випускає різні build-номери під однією версією залежно від
апаратної ревізії. Обидва target-поля тепер приймають comma-separated
список (той самий формат, що telegram_chat_ids). Валідація: якщо хоч
один кандидат старіший — відхиляється весь список.

## Backup включає історію всіх підключених Starlink-пристроїв

`known_devices` додано в backup. `merge_known_devices()` — INSERT OR
IGNORE, не перезаписує dish_id, що вже є локально (локальна БД
авторитетніша за статичний backup-знімок).

## Аудит: 2 реальні прогалини знайдені й виправлені

1. Порожній рядок у target-версії мовчки ігнорувався замість
   очищення поля. 2. API-контракт `/api/target-versions` не завжди
   містив `message` — виявлено власним живим тестом, що звертався
   до поля напряму.

## Flash-сповіщення підсвіткою при зміні статусу оновлення

Підсвітка вмикається на `DISPLAY_UPDATE_FLASH_SEC` при зміні
update_state. **Знайдений баг**: flash не оновлював `last_activity_ts`
— `_should_auto_off()` міг вимкнути підсвітку до завершення
коротшого flash-періоду. Фікс: оновлення `last_activity_ts` при
активації flash.

## Дедублікація target-версій ізольована per-dish_id

**Реальний сценарій користувача**: різні фізичні Starlink (різні
dish_id) підключені до того самого Pi з часом. Дедублікаційні ключі
не включали dish_id — новий пристрій із тим самим збігом версія+target
хибно блокувався як "вже сповіщений". Фікс: dish_id додано до ключа
дедублікації.

## Ручна кнопка "Перевірити оновлення" не сповіщала

**Причина**: webapp.py і monitor.py — окремі процеси, уся "розумна"
логіка була методами класу Watchdog, живого лише в watchdog-сервісі.
Фікс: винесено в module-level функції з `notify_fn`-параметром,
webapp.py викликає їх напряму.

## "🔄 оновлена" вводило б в оману для реального відкату

`real_change` напрямково-байдужа, але повідомлення завжди казало
"оновлена" незалежно від напрямку. Фікс: `_format_firmware_change_
message()` використовує `db.is_older_version()` для вибору "оновлена"
vs "відкочена (можливо, SpaceX-side)".

## Кнопка ручної перевірки оновлень системних пакетів (apt)

`/api/apt-check` — примусовий `apt-get update` + свіже число без
кешу. sudoers-правило додано, той самий вузький підхід, що для
reboot/poweroff. *(Функціонал видалено пізніше — див. запис нижче.)*

## Баг: apt-check провалювався через ProtectSystem=strict

`ProtectSystem=strict` успадковується дочірніми процесами незалежно
від sudo — `/var/lib/apt/lists` не було серед дозволених шляхів.
Фікс: додано до `ReadWritePaths=`.

**Перевірено**: 435 тестів, `mypy` чисто, живий функціональний тест
усіх сторінок дашборду.

## Розширений аудит: логічні помилки, edge cases, документація

**Запит користувача**: розширений аудит усього проєкту, не
зупиняючись на одному файлі.

**Методологія**: систематичний прохід по 15+ файлах/категоріях,
шукаючи логічні помилки (не стиль/дублювання - уже покрито
попереднім рефакторингом), edge cases, race conditions,
документаційні неточності.

**Реальний баг знайдено й виправлено**: `db.prune_old()` мав
`days = days or config.HISTORY_RETENTION_DAYS` - falsy-патерн робив
явно передане `days=0` (легітимне значення - "видалити всю історію")
нерозрізненим від "аргумент не переданий", мовчки підміняючи
дефолтом. Єдиний production-виклик (`monitor.py`) завжди без
аргументів, тому баг не активувався - але API-контракт функції
(сигнатура `Optional[int] = None`) явно дозволяв `0`. Виправлено на
явну перевірку `is None`.

**Знайдено й виправлено документаційна прогалина**: `starlink-
display.service` мав коментар "на відміну від коментаря, який тут
раніше був" - посилання на контекст, що більше не існує у файлі,
незрозуміле для читача, який відкриває файл вперше. Переписано
самодостатнім формулюванням.

**Знайдено, зафіксовано як неоднозначне (не виправлено)**:
1. `monitor._maybe_reboot()` - якщо `MAX_CONSECUTIVE_FAILURES` колись
   перевищить `MAX_LOGGED_CONSECUTIVE_FAILURES + 1` (обидва UI-
   редаговані, дефолти 6/15 роблять це неактуальним зараз), перша
   й найважливіша reboot-подія могла б не потрапити в журнал.
2. `webapp.api_settings_restore()` - `payload.get("dish_target_
   version")` з порожнім рядком (легітимне "очистити поле" значення)
   falsy, тому явно очищене поле в backup мовчки ігнорується при
   restore - можлива навмисна безпечна поведінка (restore не стирає
   існуюче значення), не обов'язково баг.

**Перевірено й підтверджено безпечними (той самий `or`-патерн, різна
семантика)**: `StarlinkClient.__init__()`'s `dish_addr`/`router_addr`/
`timeout` - жоден реальний виклик у проєкті не передає порожній
рядок/0 явно, і ці значення не мають осмисленого legitimate-
використання (на відміну від `days=0`).

**Перевірено й не знайдено проблем**: `gpio_utils.ButtonPressTracker`
(edge case `hold_sec=0`), `display._should_auto_off()`/`_status_
lines()`, `telegram_bot`'s reboot-confirmation (ідемпотентний
`.pop()`), `activity_led.py`'s Timer-скасування, `webapp._find_
older_candidates()`'s channel-aware логіка, `system_metrics._read_
temp_c()`, systemd-файли (усі 7 сервісів реально встановлюються,
healthcheck.timer/.service - той самий паттерн, що wan-failover).

**Додано regression-тест**: `test_prune_old_days_zero_is_not_
silently_replaced_by_default`.

**Перевірено**: 436 тестів (було 435, +1), `mypy` чисто, живий
функціональний тест усіх сторінок дашборду.
