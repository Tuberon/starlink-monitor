# Журнал рішень

Хронологічний запис значущих технічних рішень і знайдених багів.

## Виявлення реальної схеми gRPC

Starlink Mini — не єдиний пристрій, а два логічні пристрої (dish +
router) з різними `DeviceInfo`, enum-станами, alert-полями —
підтверджено `grpcurl describe`, не здогадкою. `starlink_client.py`/
`labels.py` побудовані на цих підтверджених схемах.

## Баг: конфлікт параметра `timeout` в Telegram API

**Симптом**: бот не отримував команд. **Причина**: `_api_call()`
передавав HTTP-таймаут позиційно й Telegram `timeout=` (long polling)
іменовано — колізія параметрів. **Фікс**: перейменовано на
`http_timeout`.

## NoNewPrivileges вимкнено на webui/shutdown-button сервісах

Обидва викликають `sudo systemctl reboot/poweroff` — `NoNewPrivileges`
блокує будь-який sudo незалежно від sudoers. `starlink-monitor.service`
(sudo не викликає) лишається з прапорцем.

## Фізична кнопка виключення: окремий процес

`shutdown_button.py` — окремий модуль/сервіс, не частина monitor/webapp:
GPIO вимагає групу `gpio`+`python3-libgpiod` (зайва залежність без
кнопки), вимкнено за замовчуванням (pin=0, чистий вихід),
`Restart=on-failure` (не `always`) — чистий вихід не циклить рестарт.
venv створюється з `--system-site-packages` для системного gpiod.

## Баг: reboot-loop при невдалій auto-reboot команді

`last_reboot_ts` оновлювався лише при успіху — невдала спроба (dish ще
перезавантажується) не блокувала повтор щоцикл (~10с) замість
`MIN_REBOOT_INTERVAL_SEC`. Фікс: оновлюється при кожній спробі,
незалежно від результату.

## Статичні IP в install.sh — інтерактивно, не автоматично

Неправильні мережеві дефолти можуть обірвати SSH — питає підтвердження
замість мовчазного застосування. `dhcpcd` вимикається лише в межах
цього опційного кроку (конфліктує з NetworkManager).

## Баг: gpiod v2 несумісний зі старим API кнопки

**Симптом**: `'Chip' object has no attribute 'get_line'`. **Причина**:
Raspberry Pi OS Bookworm+ ставить gpiod 2.x з повністю переписаним API.
**Фікс**: `_init_line_v1`/`_init_line_v2`, вибір через
`hasattr(gpiod.Chip, "get_line")`.

## Мережевий запит install.sh лише при першому встановленні

Питання про статичні IP обгорнуто `MODE=="install"`. `uninstall.sh` —
окремий файл, не прапорець.

## Придушені конкретні Telegram-сповіщення

`MUTED_DISH_ALERTS={"roaming"}`, `MUTED_ROUTER_ALERTS=
{"install_pending"}`, `MUTED_ROUTER_UPDATE_STATES=
{"GETTING_TARGET_VERSION_FAILED"}` — шумні для Telegram, але й далі
пишуться в журнал дашборду.

## Telegram-сповіщення про цикл оновлення ПЗ dish

Перехід у `DOWNLOADING_UPDATE_STATES` → "🔽 Розпочато"; повернення в
`IDLE` → "✅ Завершено". `REBOOT_REQUIRED`/`FAULTED` мають власні
повідомлення навіть при прямому переході.

## Обмеження журналу watchdog-спроб при тривалій недоступності

`MAX_LOGGED_CONSECUTIVE_FAILURES` (30) обмежує запис у журнал —
спроба 31 дає фінальний маркер, 32+ мовчать (сама `reboot_dish()`
викликається без змін).

## Баг: Telegram-бот блокувався на повільних командах

**Причина**: обробка команд (блокуючі gRPC-виклики, до ~15с) йшла в
тому самому потоці, що `getUpdates` polling. **Фікс**:
`ThreadPoolExecutor(max_workers=3)`. Побічний ефект — паралельність
ламала порядок (`/reboot`+підтвердження в різних потоках) — виправлено
групуванням updates за `chat_id`.

## Рефакторинг: спільний хелпер update-ready reboot (dish+router)

`_maybe_reboot_for_update`/`_maybe_reboot_for_router_update` об'єднано
в `_reboot_for_update_ready`. Виявлено й виправлено другий екземпляр
того самого reboot-loop бага для update-ready шляху.

## Backup/restore розширено на параметри моніторингу

`format_version` 1→2: `env_params` містить лише реально перевизначені
значення. Restore через `config_editor.save_values()`, застосовується
після рестарту сервісів.

## Рефакторинг: усунення дублювання (webapp.py, telegram_notify.py)

Спільна логіка (команда+журнал+Telegram) винесена в
`_execute_pi_power_action`.

## Баг: StartLimitIntervalSec/Burst у [Service] замість [Unit]

Ці директиви належать до `[Unit]` — у неправильній секції systemd
мовчки ігнорує їх. Перенесено.

## fetch_starlink_grpc.sh: завантаження через eth0 насамперед

wlan0 має нижчий route-metric за eth0, але це означає й зовнішній
інтернет іде через wlan0 першим — якщо Starlink недоступний, немає
інтернету попри робочий eth0. Фікс: `curl --interface eth0` спочатку.

## Telegram-сповіщення мовчали при відсутньому інтернеті на Starlink

Той самий root cause — HTTP до api.telegram.org теж іде дефолтним
маршрутом (wlan0). `_request_with_eth0_fallback()` — retry через
eth0-прив'язаний сокет, застосовано в send_message/test_connection/
_api_call.

## Оптимізація для мобільних

`.status-row-label`/`.progress-track` фіксовані ширини переповнювали
<480px — стали гнучкими. Додано safe-area-inset, tap-highlight,
44px touch targets, брейкпоінт <360px.

## Cache-busting для JS/CSS

**Симптом**: браузер показував стару поведінку після update.sh
(`SEND_FILE_MAX_AGE_DEFAULT=3600`). **Фікс**: `_static_v()` додає
`?v=<mtime>` до статичних URL в усіх шаблонах.

## Інструкція оновлення: повний шлях замість відносного

`sudo bash scripts/update.sh` провалювався поза розпакованим архівом.
Виправлено на повний шлях `/opt/starlink-monitor/scripts/...`.

## eth0-fallback для Telegram: SO_BINDTODEVICE, не прив'язка до адреси

**Причина провалу першого підходу**: прив'язка сокета до IP-адреси
джерела не форсує фізичний інтерфейс — Linux обирає його за таблицею
маршрутизації на основі адреси призначення, ігноруючи джерельну IP.
**Фікс**: `SO_BINDTODEVICE` — реально форсує інтерфейс. Вимагає
`CAP_NET_RAW` (`AmbientCapabilities`, сумісно з `NoNewPrivileges`).
Ручна DNS-резолюція через eth0-сокет, коли системний DNS теж не
відповідає — фінальний запит напряму на IP з `Host`-заголовком і
`verify=False`.

## Баг: WAN-failover не діяв — NetworkManager відновлював metric

Пряма зміна `ip route` в обхід NetworkManager не працює надійно — той
сам володіє wlan0 і перевідновлює власний metric. Фікс: `nmcli
connection modify ipv4.route-metric` + `nmcli device reapply`.

## Баг: WAN-failover ламав доступ до dish

192.168.1.0/24 (router) має автоматичний kernel-route, 192.168.100.0/24
(dish) — ні, трафік ішов лише дефолтним маршрутом, який
демотувався. Фікс: постійний окремий маршрут через `nmcli
+ipv4.routes`.

## WAN-failover сам спричиняв флапи dish — додано гістерезис

`nmcli device reapply` на мить розриває маршрут до dish, кожен флап
перемикав WAN-failover знову (петля самопідживлення). Фікс:
перемикання лише після 3 поспіль однакових результатів перевірки.

## Баг: DISPLAY_ROTATION=90 не працював для 170×320

Бібліотека `st7789` забороняє rotation=90/270 для прямокутних
дисплеїв. Дефолт змінено на 0; landscape вимагає поміняти
WIDTH/HEIGHT місцями.

## Помилковий висновок з емпіричного тесту: WIDTH/HEIGHT 320x170

Попередня версія мала дефолти 320x170 (поміняні місцями відносно
паспортних 170x320, підтверджених офіційною документацією виробника
й написом на платі) — це був помилковий висновок з емпіричного
тесту: реальна причина залишкового кольорового шуму на 320x170 —
командування контролеру 320 стовпців, тоді як фізична матриця має
лише 170, не сам факт правильного/неправильного порядку значень.
"Покращення" було випадковим побічним ефектом іншої зміни, не
правильним рішенням саме цієї конфігурації. Виправлено на паспортні
170x320.

## Баг: підсвітка працює, зображення немає (RST не виводився)

Бібліотека налаштовувала RST як output LOW і одразу викликала `_init()`
— контролер весь цей час у reset, ігнорує SPI-команди. Фікс: явний
`display.reset()` + повторний `display._init()`.

## Баг: підтвердження мережевого запиту install.sh не розпізнавалось

Можливий прихований `\r` у введенні термінала. Фікс: `tr -d
'[:space:]'` перед перевіркою.

## Заміна бібліотеки дисплея на Adafruit CircuitPython ST7789

Попередня мала RST-баг і заборону rotation для прямокутних дисплеїв,
плюс невирішений кольоровий шум на SKU MSP1901 — спершу помилково
прийнятий за апаратний дефект, реально викликаний зміщенням GRAM
(вирішено пізніше через `DISPLAY_OFFSET_LEFT`/`_TOP`, значення 35/0
емпірично підтверджені робочими). Нова бібліотека
(`adafruit-circuitpython-rgb-display`) коректно виводить RST у
`__init__`, дозволяє будь-який rotation, обертання програмне
(`img.rotate()`). CS — bit-banged GPIO, не апаратний CE0/CE1.

## Баг: WAN-failover падав з "Read-only file system" на /run

`ProtectSystem=strict` робить усю ФС read-only, крім явно дозволених
шляхів — `/run` сам по собі не звільнений. Фікс: `RuntimeDirectory=`
+ `RuntimeDirectoryPreserve=yes`.

## Баг: pip install падав на rpi_ws281x/RPi.GPIO

Відсутній `Python.h` для компіляції C-розширень. Фікс: додано
`python3-dev build-essential` до install.sh.

## Баг: кирилиця не відображалась на фізичному дисплеї

Відсутній `fonts-dejavu-core` — тихий fallback на `ImageFont.load_default()` без кирилиці. Фікс: додано пакет + явне попередження
в логах, якщо жоден шрифт не знайдено.

## Баг: довге натискання кнопки не вимикало Pi (NoNewPrivileges)

Залишок `NoNewPrivileges=true` у `starlink-display.service` з часів,
коли той не викликав sudo — після перенесення логіки кнопки з
shutdown_button.py в display.py unit-файл забули оновити. Видалено
прапорець.

## Зменшення частоти записів на SD-картку

`PRAGMA synchronous=NORMAL` для WAL — менше fsync(). Розглянуто, але
НЕ застосовано: `Storage=volatile` для journald (втрата journalctl-
історії між перезавантаженнями — критичний діагностичний інструмент,
активно використовуваний протягом розробки).

## starlink_grpc.py винесено як vendor-файл

Динамічне завантаження з GitHub при кожному встановленні означало
залежність від інтернету й непередбачувані версії. Файл тепер
частина архіву (`app/vendor/`), fetch-сервіс лишається лише для
опційного ручного оновлення.

## Сповіщення про зміну версії прошивки dish/router

`upsert_known_device_*()` повертає `(real_change, old_version)`.
**Знайдений edge case**: перша версія вважала зміною будь-яке
існування рядка `known_devices`, не перевіряючи саме поле — dish і
router створюють спільний рядок у різних циклах, перше заповнення
"свого" поля хибно рахувалось зміною з None. Фікс: перевірка
конкретного поля, не факту існування рядка.

## Групування спаму reboot-сповіщень

`_notify_reboot()` — ковзний список timestamps; поріг+вікно →
мовчазне групування до затишшя, тоді підсумок і повний скид стану.

## Типізація (mypy) — пропорційний підхід, без --strict/CI

`mypy --strict` дав 366 помилок у 13 файлах — переважно SQLite
`dict(row)`-патерни і vendor-код. Рішення: return type hints для
всього власного коду, `ignore_errors` для vendor, локальний запуск
(не CI — одноосібний hobby-проєкт, перевіряється живим тестуванням на
залізі). Реальні логічні баги, знайдені під час типізації: неявний
`Optional` у сигнатурах, `poll_once()` типізований як `None` хоча
повертає `DishStatus`, `read_current_values()` сигнатура була
неправильною (список, не dict) — виявлено лише зараз.

## Мобільний PWA офлайн-режим — localStorage-кеш

Доповнює (не скасовує) попереднє рішення "не кешувати API" —
показує застарілі дані з явним індикатором ("X хв тому"), не мовчки.
`localStorage`, не IndexedDB — простий JSON-об'єкт, не варта
складнішого API.

## Темна/світла тема — CSS custom properties + toggle

`[data-theme="light"]` інвертує ті самі CSS-змінні. Inline-скрипт у
`<head>` застосовує тему синхронно (без FOUC). Знайдено й виправлено:
7 хардкоджених hex-кольорів поза `:root`, порядок inline-скрипта
відносно `<meta theme-color>` (querySelector повертав би null).

## Оновлення "безпечних" пакетів у requirements.txt

`install.sh` оновлює пакети лише коли текст файлу змінюється —
без цього версії застрягають назавжди попри `>=`. Оновлено minor/patch
(Flask, requests, dnspython, yagrc), major-розриви (protobuf,
adafruit-blinka) свідомо не чіпались.

## Баг: `pip install --upgrade` оновлював незмінені пакети

`--upgrade` застосовується до всього файлу одразу — зміна одного
рядка означала "онови все", зачепивши й hardware-критичний
adafruit-blinka. Фікс: точні `==`-піни, без `--upgrade`.

## Сповіщення про встановлення очікуваної версії прошивки

`/settings` дозволяє вказати очікувану версію, отримати сповіщення
при збігу. Дедублікація через збережене значення target (не окремий
boolean) — природно скидається при новому target.

## Очікувана версія прошивки — валідація "лише новіші"

`_version_key()` — толерантний компаратор для `YYYY.MM.DD.mrXXXXX.N`,
дата-префікс домінує. dish/router валідуються незалежно (часткова
відмова).

## Комбіноване сповіщення про завершення оновлення (обидва одночасно)

`_check_both_targets_reached()` — "🎉" лише коли ОБИДВІ версії
збігаються одночасно, доповнює per-component сповіщення. Викликається
з обох циклів опитування (dish/router незалежні).

## Формальний test suite (pytest) для найкрихкішої логіки

35 тестів для groupування reboot-спаму, дедублікації target-версій,
компаратора версій — заміна ad-hoc живих тестів, які не персистували
між сесіями.

## Кілька очікуваних версій прошивки для різних апаратних ревізій

SpaceX випускає різні build-номери під однією версією залежно від
апаратної ревізії. Обидва target-поля тепер приймають comma-separated
список (той самий формат, що telegram_chat_ids). Валідація: якщо хоч
один кандидат старіший — відхиляється весь список.

## Backup включає історію всіх підключених Starlink-пристроїв

`known_devices` додано в backup. `merge_known_devices()` — INSERT OR
IGNORE, не перезаписує dish_id, що вже є локально (локальна БД
авторитетніша за статичний backup-знімок).

## Аудит: 2 реальні прогалини знайдені й виправлені

1. Порожній рядок у target-версії мовчки ігнорувався замість
   очищення поля. 2. API-контракт `/api/target-versions` не завжди
   містив `message` — виявлено власним живим тестом, що звертався
   до поля напряму.

## Flash-сповіщення підсвіткою при зміні статусу оновлення

Підсвітка вмикається на `DISPLAY_UPDATE_FLASH_SEC` при зміні
update_state. **Знайдений баг**: flash не оновлював `last_activity_ts`
— `_should_auto_off()` міг вимкнути підсвітку до завершення
коротшого flash-періоду. Фікс: оновлення `last_activity_ts` при
активації flash.

## Дедублікація target-версій ізольована per-dish_id

**Реальний сценарій користувача**: різні фізичні Starlink (різні
dish_id) підключені до того самого Pi з часом. Дедублікаційні ключі
не включали dish_id — новий пристрій із тим самим збігом версія+target
хибно блокувався як "вже сповіщений". Фікс: dish_id додано до ключа
дедублікації.

## Ручна кнопка "Перевірити оновлення" не сповіщала

**Причина**: webapp.py і monitor.py — окремі процеси, уся "розумна"
логіка була методами класу Watchdog, живого лише в watchdog-сервісі.
Фікс: винесено в module-level функції з `notify_fn`-параметром,
webapp.py викликає їх напряму.

## "🔄 оновлена" вводило б в оману для реального відкату

`real_change` напрямково-байдужа, але повідомлення завжди казало
"оновлена" незалежно від напрямку. Фікс: `_format_firmware_change_message()` використовує `db.is_older_version()` для вибору "оновлена"
vs "відкочена (можливо, SpaceX-side)".

## Кнопка ручної перевірки оновлень системних пакетів (apt)

`/api/apt-check` — примусовий `apt-get update` + свіже число без
кешу. sudoers-правило додано, той самий вузький підхід, що для
reboot/poweroff. *(Функціонал видалено пізніше — див. запис нижче.)*

## Баг: apt-check провалювався через ProtectSystem=strict

`ProtectSystem=strict` успадковується дочірніми процесами незалежно
від sudo — `/var/lib/apt/lists` не було серед дозволених шляхів.
Фікс: додано до `ReadWritePaths=`.

## Систематична перевірка: пакети, документація, edge cases

`pip index versions` знайшов 2 застарілі: grpcio (1.83→1.84),
protobuf (7.35.1→7.36.1) - оновлено, перевірено живим regression
перед зміною requirements.txt. index.md проти реального коду: 4

поведінка). HTML-ID/JS el()-виклики, CSS-теми, systemd-шляхи,

функцій (не лише читання коду) - усі відповідають документації;
єдина знахідка - власна помилка в порядку аргументів при виклику
(не баг проєкту).

## Зменшено частоту опитування дашборду (REFRESH_MS 1000→1500)

dish опитується кожні 10с, router - 35с, system_metrics - 60с, але
фронтенд запитував /api/status щосекунди. HIDDEN_REFRESH_MS=30000
для неактивної вкладки вже застосовував правильний принцип -
поширено на активну. Значення 1500 (компроміс користувача між 1000
і спершу запропонованим 3000). Побічний ефект: uptime-лічильник
(не тікає локально) оновлюється трохи рідше - малопомітно.

## Правила тестів: ізоляція БД, мережі, середовища

- Тест коду, що доходить до `i18n.t()`, — лише з `db_path` (інакше
  залишковий `ui_language='en'` з іншого тесту; так знайдено кілька
  flaky, зокрема один, помилково визнаний "безпечним" статичним оглядом).
- Фікстура `watchdog` фіксує `router_reachable=True`; жоден тест не
  ходить у мережу (Telegram-ретраї: `_get_eth0_ip -> None`).
- Відсутній пакет — `monkeypatch.setitem(sys.modules, m, None)`, не
  `.pop()`; `config.DISPLAY_ENABLED` відкочує autouse-фікстура.
- Перевіряти динамічно, не на око: плагін pytest із забороною TCP і UDP
  (DNS іде через `sendto`, не `connect`) → 0 з'єднань; порожня БД перед
  кожним тестом → увесь набір проходить.
- Ізоляція робочих шляхів — autouse-фікстура в conftest для КОЖНОГО
  тесту: env, тека бекапів і БД за замовчуванням → tmp (БД навмисно не
  ініціалізована: тест без `db_path` падає, а не читає чужий стан —
  структурно прибирає клас "мова з попереднього тесту"). Причина: 11
  тестів писали в справжній `/etc/starlink-monitor/env` (фікстура
  `client` ізолювала БД, але не `ENV_FILE_PATH`), README стверджував
  "без побічних ефектів". Аудит звернень до робочих шляхів 45 → 0;
  тест-запобіжник `test_tests_never_use_real_pi_paths`.
- Запуск тестів на самому Pi — лише в окремому venv, без
  `--break-system-packages` і без бібліотек `adafruit-*` (README), щоб
  жоден тест не торкнувся справжніх GPIO/SPI.

## Продуктивність, розмір сторінок і записи на SD

Цифри — вимір на x86 (на Pi абсолютні числа більші), якщо не сказано
інше.
- **i18n**: мова читалась з БД на кожен `t()` (55 SQLite-з'єднань на
  рендер `/`) → `translator()` + context processor: 1 з'єднання,
  13.7→2.1 мс. Без TTL-кешу між запитами: мову змінює webapp, читає й
  monitor.
- **Розмір сторінок**: `window.I18N` — лише 121 ключ, що використовує JS
  (скан `t('...')` у static/*.js; динамічні `t(var)` заборонені тестом)
  + `ensure_ascii=False`: `/` 67.9→18.3 КБ. PNG — zopfli без втрат.
- **`/api/status`** (кожні 1.5 с): прибрано `uptime_24h_pct` (ніхто не
  читав, ~70% часу запиту, хибна через нічне вимкнення): 2.21→0.60 мс.
- **Дашборд**: було 4 запити на тік → `/api/status` щотіку, журнал подій
  кожен 4-й тік, роутер і Pi кожен 10-й; `tick(true)` оновлює все
  (завантаження, повернення на вкладку, після "Перевірити оновлення"):
  9600→3480 запитів/год на вкладку.
- **TFT-дисплей**: дані читає цикл і передає в `_redraw()` (було двічі
  по 2 читання БД); незмінний кадр не рендериться й не йде по SPI
  (uptime з точністю до хвилини): 17 280→842 перемальовування на добу.
- **Пам'ять**: `pi_power` імпортує `telegram_notify` лише в момент
  сповіщення — процеси дисплея й кнопки не тримають `requests` (22→5
  МБ).
- **Журнал systemd**: таймери WAN-failover (30 с) і healthcheck (60 с) —
  `LogLevelMax=notice` + `SyslogLevel=notice`: на ~13 000 рядків/добу
  менше на SD, вивід скриптів лишається. Фільтр PID 1 про юніт — systemd
  ≥ 248 (PR #19050); ефект перевіряти на Pi.
- **Метрики dish** пишуться пакетом раз на 30 с, але ЗМІНА `(online,
  update_state)` скидає буфер одразу (інакше дашборд і дисплей бачили б
  заміну Starlink із затримкою до 30 с); однакові опитування — пакетом
  (`test_unchanged_state_stays_batched`).
- **Telegram-бот**: `getUpdates` (~3500/добу) — одна `requests.Session`
  лише в потоці `_run_loop` (Session не потокобезпечна: відповіді з пулу
  потоків — без неї); перестворюється після мережевої помилки
  (WAN-failover). Вимір: 20 запитів → 1 TCP-з'єднання.
- `cpu_percent(interval=None)` прогрівається при імпорті
  `system_metrics` (перший замір після запуску був беззмістовним 0.0).
- **Журнал запитів Werkzeug**: рядок на КОЖЕН запит; дашборд ~3500/год
  на вкладку → ~83 000 рядків (~8 МБ)/добу на SD. `_QuietSuccessfulGets`
  відкидає лише успішні GET; POST-дії (з IP) і помилки лишаються —
  єдиний слід дій без автентифікації. Раніше не помічалось:
  `test_client()` обходить лог запитів.
- **VACUUM лише за потреби** (вільних сторінок ≥ 30%): переписує всю БД
  (6.5 МБ → 13.7 МБ записів) і виконувався щодоби І на кожен запуск
  сервісу, а після щоденного prune звільняється ~20% сторінок, які нові
  записи одразу заповнюють. `ANALYZE` лишається (дешево).
- Виміряно й НЕ змінювалось: відповіді веб-інтерфейсу ~1 мс незалежно
  від обсягу (5 чи 14 діб; запити по індексах), сторінки 12–18 КБ (gzip
  на LAN не потрібен); записи БД ~68 МБ/добу (метрики dish 40, Pi 17.5,
  роутер 9.7) ≈ 25 ГБ/рік, менше 0.1%/рік ресурсу SD — зміна
  схеми/індексів (AUTOINCREMENT, індекс по ts: −26% записів) не варта
  ризику міграції; `.pyc` (app/ компілюється ~35 мс на x86 при кожному
  старті, ~0.3 с на Pi).
- **Ледаче завантаження vendored gRPC-модуля**
  (`starlink_client._grpc_module()`, маркер `_UNLOADED`): веб-процес
  імпортує `starlink_client` заради двох кнопок ("перевірити оновлення",
  "перезавантажити тарілку" — обидві лише за кліком), а gRPC + protobuf
  + yagrc + vendored файл на 1800 рядків тримались у ньому все життя.
  Вимір (x86, A/B на однакових умовах): веб-процес у простої 54.1 → 41.3
  МБ (−12.8 МБ, −24%), імпорт 244 → 196 мс; після першого натискання
  "перевірити оновлення" стек завантажується і RSS ≈ як раніше (57 МБ) —
  виграш діє до першого кліку (на Pi — до кліку після кожного
  перезавантаження). Монітор у сталому режимі без змін: вантажить стек
  при першому опитуванні. Тести підміняють глобальну `starlink_grpc` як
  і раніше; блокування потрібне, щоб потоки (монітор, бот, веб-запити)
  не імпортували й не логували помилку кожен окремо.
- **Перевірено й НЕ оптимізовано** (щоб не повертатись): усі запити до
  БД йдуть по індексах (плани `SEARCH … USING INDEX`), ендпоінти < 1 мс
  на 14 добах даних (`limit=500` — 3 мс); статика вже `Cache-Control:
  max-age=3600` + ETag/304; дисплей пропускає рендер і передачу по SPI,
  коли кадр не змінився; `dnspython` вже імпортується лениво (+12.5 МБ
  лише в запасному шляху Telegram); CPU у простої — монітор 0.05%, веб
  0.00% одного ядра; профіль опитування — ≈12.7 відкриття
  SQLite-з'єднання на опитування, ~2.5 мс (x86), разом ~0.1% CPU навіть
  на Pi (кеш налаштувань раніше відхилено).
- Пастка виміру часу імпорту: з `PYTHONDONTWRITEBYTECODE=1` і видаленим
  `__pycache__` кожен запуск перекомпілює vendored файл (3.4 с замість
  90 мс) — міряти з прогрітим `.pyc`, як на Pi; пам'ять (RSS) від цього
  не залежить.

## Мережа й install.sh

WAN-failover — кожні 30 с. На Pi користувача мережевий блок install.sh
не застосувався; причину НЕ встановлено (висновок "баг install.sh"
відкликано), тож install.sh тепер перевіряє, що очікувана адреса є серед
фактичних (`grep -qxF`, не `!=`: кілька IPv4 давали хибне "УВАГА").
На WiFi-профілі `ipv6.method disabled`: IPv6 через мертвий Starlink-канал
блокував DNS/HTTPS. Мережевий блок виконується лише при першому
встановленні — для наявних систем ручна команда в README.

## Starlink вимкнено ≠ зависання тарілки

Dish і роутер (TCP до gRPC-порту, timeout 2 с — без WiFi Starlink
пакети йдуть через eth0 і чекають його повністю) недоступні 3
опитування поспіль (~30 с, гістерезис) → стан "Starlink вимкнено": без reboot і лічильника
збоїв, одна подія на вхід/вихід, Telegram лише при поверненні після >
`NOTIFICATIONS_MUTE_AFTER_SEC` (вибір користувача: "лише вранці"). Без
розкладів — стан визначається фактом. Ніч користувача (симуляція):
reboot 114→0, рядків журналу 5932→2. "Пропускаю авто-reboot" — один
запис на вікно очікування.

## Станція оновлення прошивок: контекст і рішення користувача

3–12 різних Starlink на день, на ніч вимикається. Відкрита WiFi
`STARLINK` без прив'язки до BSSID — ПРАВИЛЬНО (Pi підхоплює будь-який);
НЕ радити унікальну назву/пароль, розділення 2.4/5 ГГц чи прив'язку
BSSID. Дашборд на 0.0.0.0 без автентифікації — свідоме рішення
власника ("доступ маю тільки я"), не виносити як проблему.
Приховано повністю: `obstruction_map_reset` — фільтр у джерелі,
`starlink_client.IGNORED_DISH_ALERTS` (/status і check_updates_now()
читають в обхід poll_once); `DOWNLOADING_UPDATE_IMAGE_FAILED` —
`monitor.HIDDEN_ROUTER_UPDATE_STATES` (попередній стан не змінюється,
у /status — "немає оновлень").
Поле цільових версій прошивки не перевіряє формат — РІШЕННЯ КОРИСТУВАЧА,
не виносити як проблему ("abc" відхиляється як "старіша за версію того
самого build-каналу", "v1.2.3" приймається; шкоди немає — невалідна ціль
просто ніколи не спрацює). Стан роутера `GETTING_TARGET_VERSION_FAILED`
показується як "немає оновлень" скрізь (дашборд, дисплей, Telegram
/status), у журнал подій пишеться, у Telegram не надсилається.

## Розриви WiFi кожні 65.536 с — відома особливість, тему закрито

Роутери Starlink оголошують Country IE з порожнім кодом → ядро не може
застосувати → тайм-аут ~3.14 с → скидання регіону → через ~60 с
перевірка каналів → розрив `reason=3 locally_generated=1`. Виключено:
енергозбереження, сигнал, AP-deauth, друга мережа, база регіонів.
`iw reg set 00` не працює (скидання повертає регіон із cmdline); зміна
cmdline.txt не рекомендована (ризик headless-завантаження). Вплив на
моніторинг — нуль завдяки гістерезису.

## Правила коду (виведені з виправлених багів)

- **Дані Starlink ігнорувати лише в `starlink_client`**
  (`IGNORED_DISH_ALERTS`, `IGNORED_ROUTER_ALERTS` — при розборі
  відповіді), не в споживачах: фільтр у monitor.py тричі пропускали
  шляхи, що читають стан напряму (`check_updates_now()`, Telegram
  `/status` для dish і роутера).
- **Компоненти — ідентифікатори `"dish"`/`"router"`**, людські назви
  лише через i18n (`COMPONENT_NAME`, `COMPONENT_UPDATE`, раніше
  `_COMPONENT_*`; дві граматичні форми); невідомий → `ValueError`
  (раніше опечатка з латинською i тихо ставала сирим текстом у
  сповіщенні). Зліпок 46 текстів до/після — побайтово ідентичний.
- **Коди, не тексти**: рішення за кодом стану, а не за перекладеним
  текстом. `telegram_notify.config_problem()`
  ("disabled"/"no_token"/"no_chat_ids") замість порівняння трьох
  українських рядків у `Watchdog._send_now()` (з перекладом не
  спрацьовувало б і засмічувало лог); `_validate_and_save_target()` →
  "cleared"/"saved"/"rejected"/"unchanged"; відновлення з бекапу →
  список (ключ, параметри). Тексти будуються двічі: мова інтерфейсу —
  відповідь, українська — журнал подій. Те саме для шару даних: `db` не
  імпортує i18n/labels/Telegram/веб, `check_integrity()` повертає код
  (`not_a_database: <деталь>`), переклад — у споживача
  (`services.describe_integrity_problem`). Пастка тесту: мова
  зберігається в тій самій БД, тож при зіпсованому файлі її не прочитати
  → сповіщення українською (задокументовано); переклад перевіряється на
  здоровій БД.
- **Параметри функцій перекладу — лише позиційні** (`_translate(lang,
  key, /, **kw)`): плейсхолдер `{lang}` інакше колізує з параметром →
  TypeError → `/api/set-language` віддавав 500.
- **Жодного `exec()`/`eval()`** у app/ (тест
  `test_no_exec_or_eval_in_app_code`): `config.py` виконував як код
  `/etc/starlink-monitor/config.local.py` — незадокументований залишок у
  КОЖНОМУ процесі, в обхід валідації `/settings`. Підвищення привілеїв
  не було (жоден root-процес не імпортує `app.config`), але це міна для
  майбутніх root-скриптів; на Pi файлу не було — видалено без міграції.
- **`assert` не для захисту**: захист f-рядка з назвами колонок у SQL
  (`_upsert_known_device`) через `assert` зникав під `python -O`
  (перевірено); тепер `if/raise`.
- **Вхід від клієнта**: `_json_body()` (не-об'єкт → `{}`) +
  `_bad_request(field)` → 400 (7 ендпоінтів падали з 500: `payload.get`
  на list/int, `.strip()` на числі); `/api/events?limit` — межі 1..500
  (`LIMIT -1` у SQLite = без обмеження → віддавався весь журнал;
  нечислове → 30); керуючі символи (`\n`, `\r`, NUL, `\t`) у значеннях
  параметрів відхиляються (`\n` створював у env додатковий параметр в
  обхід валідації, NUL ламав EnvironmentFile); краї обрізаються. Тіло
  запиту ≤ 5 МБ (`MAX_CONTENT_LENGTH`; реальний бекап станції — 42 КБ):
  Flask ліміту не має, а `/api/settings-restore` читає JSON у пам'ять.
- **Telegram і JS**: аргумент `/id@ІмяБота X` — усе після першого слова
  (зріз за довжиною давав "@ІмяБота X"); `.get("chat", {})` не рятує від
  `None` → `_obj()`; JS `t()` — `split/join`, не `replace()` (лише перше
  входження, `$&`/`$1` як спецсимволи).
- 6 неіменованих чисел у логіці → константи (паузи бота, DNS-таймаут,
  очікування черги сповіщень); значення не змінено.
- **Метод, що викликається з кількох місць і пише в БД, не кидає**
  (`flush_metrics_buffer()`): виняток із періодичного виклику валив
  увесь процес монітора, з обробника SIGTERM — заважав вийти (з
  `poll_once()` його ковтав би `except`, і сервіс ігнорував би сигнал до
  SIGKILL). Збій → лог, буфер лишається (стеля 8640), повтор через
  інтервал. Це була діра у виправленні "Watchdog не залежить від БД":
  захистили лише одне з трьох місць виклику.
- **Числові параметри `/settings` мають межі**
  (`config_editor.LIMITS`/`CHOICES`), інакше `nan`/`inf`/`0`/`-5` валять
  монітор (`time.sleep` поза обробником), видаляють усю історію
  (`HISTORY_DAYS=0`), шлють бекап кожні 10 с. Нуль допустимий лише де
  означає "вимкнено"; новий числовий параметр без меж — падає тест.
  Пауза опитування має запобіжник і для ручної правки env
  (`monitor._poll_pause()`).
- **Ресурси закривати явно**: сокет `eth0` (`with`) і `requests.Session`
  резервного шляху (`finally`) — раніше лише збиранням сміття CPython.
  Зовнішній CSS у `<head>` — лише асинхронно (`media="print"` +
  `onload`): звичайний `<link rel=stylesheet>` блокує рендер, а дашборд
  відкривають саме коли зв'язку немає.
- **Скрипти від root**: `update.sh` розпаковує через `mktemp -d` (0700)
  + `trap`, не у фіксовану `/tmp/...` (звідти від root ВИКОНУЄТЬСЯ
  `install.sh` — підміна між розпаковуванням і запуском = root).
  Перевірено у 5 сценаріях (успіх, збій install.sh, немає install.sh,
  битий архів, повторний архів): залишкових тек немає; `systemd-analyze
  verify` — усі 9 юнітів чисті.
- **Міграції схеми БД**: лише `metrics`, `router_status`, `events` мають
  `_migrate_table_columns`; `system_metrics`/`known_devices`/`settings`
  — ні (документація стверджувала "усі"). Тест на БД старого формату +
  запобіжник: схему таблиці змінили без міграції — падає тест.
- **Секрети не потрапляють у логи** (`app/log_redact.py`): `requests`
  вставляє ПОВНИЙ URL у текст винятку, а в Telegram токен бота — частина
  шляху (`/bot<токен>/…`); мережеві збої з Telegram — основний сценарій
  проєкту, тож токен писався в журнал systemd на SD щоразу (4 рядки на
  відправку) і повертався в браузер кнопкою "тест Telegram". Два шари:
  `redact()` у джерелах (`_send_to_all_chats`, `test_connection`,
  `_api_call`) + `RedactingFilter` на обробниках кореневого логера
  (`install()` після кожного `basicConfig`; змінює запис НА МІСЦІ, тож

  шар 1 незалежно від шару 2 (інакше сітка маскує пропуск); AST-тест:
  кожна точка входу з `basicConfig` викликає `install()`.
- **Telegram parse_mode=HTML**: динамічний текст у `tg_*` екранується
  централізовано в `i18n._translate` (`html.escape`; `SafeHtml` — для
  готової розмітки; числа/None не чіпаються). Без цього Telegram
  відхиляє ВСЕ повідомлення: при недоступній тарілці grpc-помилка
  починається з `<_MultiThreadedRendezvous…` — `/status` мовчав саме
  тоді, коли потрібен (перевірено на справжньому gRPC до закритого
  порту); так само ехо `/id <що завгодно>`. Властивісний тест: КОЖЕН
  ключ `tg_*` в обох мовах із ворожими значеннями → валідний
  Telegram-HTML (`assert_valid_telegram_html` у conftest). Помилка gRPC
  у чаті — лише `details` (`labels.short_error`).
- **Локальна несправність ≠ збій тарілки** (`DishStatus.local_fault`):
  без модуля `starlink_grpc` (файл видалено/обірваний, немає yagrc)
  `get_status()` віддавав `online=False`, і watchdog перезавантажував
  ТАРІЛКУ кожні `MIN_REBOOT_INTERVAL` (симуляція: 22 рази за 67 хв) —
  пошкоджений локальний файл відключав би інтернет. Тепер `poll_once()`
  при `local_fault` не рахує збій, не перезавантажує, повідомляє РАЗ за
  процес. Імпорт vendored модуля — `except Exception` (не лише
  ImportError: обірваний файл давав SyntaxError, монітор не стартував
  узагалі). Правило: помилка своєї сторони не повинна запускати дію
  проти чужої.
- **Оновлення vendored файлу не пишуть поверх робочого**:
  `fetch_starlink_grpc.sh` — тимчасовий файл → перевірки (розмір,
  синтаксис, контракт `ChannelContext`/`get_status`) → `.prev` →
  атомарна заміна; завантаження за незмінним SHA, походження в
  `app/vendor/PROVENANCE` (upstream-коміт `8f34f4cd…` від 2026-03-20
  знайдено порівнянням sha256 з усією історією; Unlicense). Тест — проти
  ЛОКАЛЬНОГО HTTP-сервера, 9 сценаріїв.
- **Транзитивні залежності закріплені окремо** (`constraints.txt`, `pip
  install -r requirements.txt -c constraints.txt`): нові імена в
  requirements.txt = "суттєва зміна" в install.sh (повне
  перевстановлення), а pip не оновлює вже встановлені (навіть системні

- **mypy strict для `app/*`** (прапорці в mypy.ini; tests/ — м'яко): 11

  чи requests — по одній): запускати в повному dev-середовищі.
- **Тест не виконує зайвого**: фрагмент install.sh для тесту береться до
  ПЕРШОГО `fi` без відступу і має запобіжник на слова
  apt-get/usermod/systemctl/rm -rf/pip — мій перший витяг захопив
  наступний блок, і тест виконав `apt-get update` у sandbox (впав на
  403, нічого не встановивши).
- **Точка входу сервісу не бібліотека**: модуль із `logging.basicConfig`
  (monitor, webapp, display, shutdown_button) не імпортується іншими;
  спільна логіка — у `services.py`, `pi_power.py`. Гарантує
  `tests/test_architecture.py` (граф імпортів з AST, включно з лінивими:

- **Перенос коду між модулями**: скрипт на AST (вирізати сегменти з
  коментарями над ними, перейменовувати Name-вузли за позиціями, а не
  регулярками), сухий прогін перед записом, доведення порівнянням AST.
  Пастка: `def name` (FunctionDef) — не Name-вузол, оголошення
  перейменовувати окремо. Тести переселяти за ІМЕНАМИ, не за межами
  секцій (дописані пізніше не мали заголовків і лежали під чужим).
- **Рефакторинг великого циклу**: спершу переконатись, що наявні тести
  проходять БЕЗ змін (доказ незмінності поведінки), лише потім додавати
  юніт-тести нової одиниці; порядок операцій і виклики допоміжних
  функцій як глобальних імен модуля — інакше ламаються патч-цілі. Єдину
  навмисну зміну поведінки (виняток у
  `poll_router`/`poll_system_metrics` більше не валить цикл) виділяти й
  тестувати окремо. Пастка: помічник, що сам підміняє той самий об'єкт,
  перекриває підміну в тесті (`_running_loop` патчив `poll_router`
  поверх моєї) — параметр замість вкладених patch.
- **Таймери на настінному часі переживають зсув годинника назад**:
  "минуло > інтервал" спрацьовує і при від'ємному минулому часі; мітки
  "останньої події" з майбутнього скидаються на зараз (reboot-loop
  захист зберігається); "останній запис" за `ts` ігнорує рядки з
  майбутнього (допуск 600 с). НЕ переходити на `ORDER BY id DESC`: буфер
  монітора пише рядки пакетом із запізненням, тож свіжий запис
  веб-кнопки мав би менший id за старіші рядки буфера (стан застарівав
  би до 30 с у ЗВИЧАЙНІЙ роботі).
- **"Прочитати → вирішити → записати" над спільним станом — атомарно**
  (`BEGIN IMMEDIATE`, `db.claim_setting()`): `sqlite3` починає
  транзакцію лише перед записом, тож два виклики (монітор і веб-кнопка —
  різні процеси) бачать однаковий старий стан (8 потоків → 8 сповіщень).
  Прапорець "вже сповіщено" ставиться ДО сповіщення.
- **Нескінченні/NaN значення не доходять до JSON**: `±inf` → `Infinity`
  (невалідний JSON) → `JSON.parse` у браузері падає, дашборд перестає
  оновлюватись. `db._finite()` + `_FiniteJSONProvider`; NaN SQLite
  зберігає як NULL.
- **Вільнотекстові параметри env мають формат** (`_address_problem()`:
  `host:порт`, порт 1–65535). За документацією systemd.exec (не
  виміряно, systemd у sandbox немає) незакрита лапка чи слеш у кінці
  значення міняє розбір наступних рядків `EnvironmentFile`, а наївний
  власний читач `env` бачить інше.
- **Весь видимий текст фронтенду — через `t()`** (тест
  `test_frontend_has_no_hardcoded_cyrillic_text`, включно з атрибутами
  `placeholder`): ключі зазвичай уже є — їх просто не викликали.
- **Небезпечні POST-ендпоінти без автентифікації мають бути захищені від
  CSRF**: `_reject_cross_site_posts` (`Origin` + `Sec-Fetch-Site`,
  заголовки, яких скрипт сторінки не підробить) — тест перебирає КОЖЕН
  POST-маршрут × 5 варіантів чужого джерела й перевіряє, що нічого не
  виконано (`sudo`, `Timer`, `execute_pi_power_action`). Тест на кожен
  маршрут із `url_map`, а не на список із пам'яті: новий ендпоінт
  підпадає автоматично. Залишок: DNS-rebinding.
- **Файли, які перезаписує сам застосунок, — лише атомарно**
  (`atomic_io.atomic_write_text`): `open(path, "w")` обнуляє файл ДО
  запису. Тест імітує обрив посеред запису (підміна `os.fdopen`) і
  перевіряє, що старий файл цілий і без `.atomic-*.tmp`.
- **Ротація за іменем-часом: числово й без видалення щойно записаного**:
  після зсуву годинника назад новий файл мав би найменше ім'я й
  видалявся б одразу; рядкове сортування ставить `backup-9999` після
  `backup-1790000000`.
- **README: розділ відповідає змісту.** Інформація про залежності (піни,
  `constraints.txt`, аудит, походження й оновлення vendored
  `starlink_grpc.py`) жила в кінці розділу "Ліцензія"; тепер окремий
  розділ "Залежності" (у розділі "Ліцензія" лишилась лише ліцензійна
  умова vendored-файлу). Новий розділ легко забути додати у зміст —
  `test_readme_table_of_contents_matches_the_headings` вимагає, щоб
  посилання змісту збігались із заголовками `##` за набором і порядком
  (якір як у GitHub: емодзі й U+FE0F зникають, ведучий пробіл дає
  ведучий дефіс).
- **Root виконує лише файли root, у каталозі root** (блок
  `root-owned-scripts` в `install.sh`): юніти healthcheck і WAN-failover
  працюють від root, а `chown -R $RUN_USER` віддавав їхні скрипти
  користувачу веб-інтерфейсу (без автентифікації), монітора й дисплея —

  цілком, тож root-власником має бути й `$PROJECT_DIR`. Блок стоїть

  нього тест нічого не доводить).
- **Атомарність доводити обривом, а не читанням коду**: стрес-тест із
  `SIGKILL` у випадковий момент запису (нова версія — 0 пошкоджених із
  60, старий `open("w")` — 50 із 60) разом з контролем старого способу.
  Він же показав побічний ефект — `.atomic-*.tmp` після вбивств, — який
  огляд коду не виявив; тепер їх прибирає наступний запис.

## Watchdog не залежить від БД і мережі

Сценарій "БД недоступна (заблокована, повна SD) + тарілка зависла":
1. Моя регресія (негайний запис зміни стану в `poll_once()`): збій
   запису обривав опитування ДО лічильника збоїв — watchdog не
   спрацьовував ніколи; тепер збій лише логується.
2. Давня проблема: у `_maybe_reboot()`/`_reboot_for_update_ready()`
   подія "watchdog_trigger" писалась ДО `reboot_dish()` (зламана БД →
   reboot ніколи), а "dish_reboot" — ДО `last_reboot_ts = now` (reboot
   щоопитування). Тепер `_event()` ніколи не кидає. Симуляція 10 хв при
   зламаній БД: 0 винятків, 2 перезавантаження рівно через 300 с.
3. Сповіщення з монітора йшли СИНХРОННО: без інтернету одне проходило
   всі таймаути й повтори (~62 с на чат, ~2 хв на 2 чати) — watchdog
   стояв, `/healthz` перевищував поріг свіжості (60 с), healthcheck
   перезапускав монітор посеред відправки. Тепер `_BackgroundSender`
   (один потік, черга на 50, порядок збережено; бекап у Telegram — теж
   через нього); запускається лише в `run_forever()`, зупиняється в
   `finally` (SIGTERM → SystemExit), чекаючи чергу ≤10 с; поза циклом
   `_notify()` синхронний (тести детерміновані).
Перевірено й НЕ підтвердилось: найсвіжіша метрика — за `ts`, не за
порядком вставки; дисплей не переініціалізується в циклі (пропуск
незмінного кадру безпечний).

## "Якір" WAL: fdatasync −99%

`wal_autocheckpoint=1000` фактично не діяв: кожна операція відкриває й
закриває з'єднання, а закриття останнього змушує SQLite робити повний
checkpoint і видаляти `-wal` (на Pi поруч з history.db не було ні -wal,
ні -shm). Тепер `db.open_anchor()` у `run_forever()` — одне незадіяне
з'єднання на весь час роботи; SQLite відкриває файл ліниво, тож якір
виконує запит (без нього не спрацьовує — перевірено виміром і тестом).
Вимір через strace на коді проєкту (доба записів): fdatasync ~21600 →
~144, видалень WAL ~10800 → ~48, обсяг ~94 → ~48 МБ, час ×4.7.
Компроміс: метрики потрапляють на SD протягом ~30 с (скидання буферів
ядра) — без пошкодження БД (контрольні суми WAL); налаштування й історія
пристроїв — `get_conn(durable=True)` (synchronous=FULL). VACUUM і
quick_check працюють з якорем; закриття в `finally` — штатний
checkpoint; аудит — якір не протікає між тестами. Після оновлення на Pi
поруч із history.db постійно є -wal і -shm (підтверджено).

## Аудити: метод, інструменти, знахідки

перед кожним тестом, "отруєна мова" (БД попереднього тесту з
`ui_language=en`), витік якоря WAL між тестами, звернення до робочих
шляхів Pi; фазинг усіх 27 ендпоінтів (418 запитів обома мовами;
будь-який 500 = баг); скриптова звірка узгодженості (параметри config.py
↔ /settings ↔ README ↔ i18n; docs/index.md ↔ файли; README uk ↔ en за
розділами й числами; таймери ↔ описи; юніти ↔ install/uninstall).
- `ruff check` — частина проєкту: `ruff.toml` (F, B, E9, PLE, S;
