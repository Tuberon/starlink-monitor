# Журнал рішень

Хронологічний запис значущих технічних рішень і знайдених багів.

## Виявлення реальної схеми gRPC (не за здогадками)

На старті проекту помилково припускалось, що Starlink Mini — єдиний
пристрій. Живі виклики `grpcurl describe` на dish (`192.168.100.1:9200`)
і router (`192.168.1.1:9000`) підтвердили: це два окремі логічні
пристрої з різними `DeviceInfo`, різними enum станів оновлення
(`SoftwareUpdateState` vs `WifiSoftwareUpdateState`), різними наборами
alert-полів (`DishAlerts` 19 полів vs `WifiAlerts` 21 поле). Уся
подальша логіка (`starlink_client.py`, `labels.py`) побудована на
цих підтверджених схемах, не на припущеннях.

**Практика, що склалась**: для будь-яких технічних даних (розміри
плат, protobuf-схеми, назви enum) — підтверджувати через `grpcurl
describe`/web_search/фото, не вигадувати правдоподібні числа.

## Баг: конфлікт параметра `timeout` в Telegram API

**Симптом**: `TypeError: got multiple values for argument 'timeout'`,
бот не отримував жодних вхідних команд, помилка тихо гасилась у
`except Exception` кожні 5с.

**Причина**: `_api_call(method, token, timeout, **params)` мав
формальний параметр `timeout`, а виклик `getUpdates` одночасно
передавав HTTP-таймаут позиційно і Telegram API параметр
`timeout=POLL_TIMEOUT_SEC` (long polling) як іменований — колізія.

**Виправлення**: перейменовано внутрішній параметр на `http_timeout`.

## NoNewPrivileges вимкнено на webui та shutdown-button сервісах

`starlink-webui.service` і `starlink-shutdown-button.service`
навмисно **без** `NoNewPrivileges=true` — обидва викликають
`sudo systemctl reboot/poweroff` (ручний reboot/shutdown Pi через
веб-інтерфейс і через фізичну кнопку). `NoNewPrivileges` на рівні
ядра блокує будь-який `sudo` незалежно від `/etc/sudoers`, тож із
цим прапорцем ці виклики не спрацювали б.

`starlink-monitor.service` лишається з `NoNewPrivileges=true` —
той процес sudo не викликає.

## Баг: signature_phrases.txt read-only при веб-редагуванні

**Симптом**: `[Errno 30] Read-only file system` при спробі зберегти
фрази через веб-інтерфейс.

**Причина**: `ProtectSystem=strict` робить всю ФС read-only, крім
`ReadWritePaths`, куди спочатку входив лише `/var/lib/starlink-monitor`,
не `/opt/starlink-monitor/app/signature_phrases.txt`.

**Виправлення**: додано конкретний файл (не весь `/opt/starlink-monitor`)
у `ReadWritePaths` — мінімальне розширення дозволів.

## Фізична кнопка виключення: окремий процес, не інтеграція в існуючі

**Рішення**: `app/shutdown_button.py` — окремий Python-модуль і
окремий systemd-сервіс, не частина `monitor.py`/`webapp.py`.

**Чому окремо**:
- GPIO-доступ вимагає групу `gpio` і системний `python3-libgpiod`
  (apt, не pip — чистіше на Raspberry Pi OS) — зайва залежність для
  установок без фізичної кнопки
- Вимкнено за замовчуванням (`SHUTDOWN_BUTTON_GPIO_PIN=0`), сервіс
  одразу виходить — не критична помилка, якщо кнопки немає
- `Restart=on-failure` (не `always`) свідомо: чистий вихід при
  вимкненій кнопці не має спричиняти нескінченний рестарт-цикл systemd

**Побічний ефект**: venv тепер створюється з `--system-site-packages`
(щоб бачити системний `gpiod`) — це змінює поведінку venv для *всіх*
пакетів, не лише gpiod (венв тепер бачить будь-який системний Python-
пакет). Прийнятний компроміс, бо альтернатива (pip-встановлення
gpiod з компіляцією C-розширення) менш надійна на слабкому Pi Zero 2 W.

**Третя зміна NoNewPrivileges**: аналогічно до `starlink-webui.service`
(див. розділ вище), `starlink-shutdown-button.service` теж без
`NoNewPrivileges` — потребує sudo для `poweroff`.

## Баг: reboot-loop при невдалій auto-reboot команді

`last_reboot_ts` оновлювався лише при `reboot_dish() == True`. Якщо
dish ще перезавантажується з попередньої спроби (`connection
refused`), команда reboot теж провалюється — `MIN_REBOOT_INTERVAL_SEC`
ніколи не спрацьовував, watchdog повторював спробу reboot щоцикл
опитування (кожні ~10с) замість одного разу на заданий інтервал.
Виправлено: `last_reboot_ts` оновлюється при кожній *спробі*,
незалежно від результату.

## Налаштування статичних IP (eth0/wlan0) в install.sh — інтерактивне, не автоматичне

Мережева конфігурація (USB-Ethernet + WiFi Starlink) ризикована для
автоматичного застосування без підтвердження — неправильні дефолти
(наприклад, конфлікт підмереж з реальною домашньою мережею) можуть
обірвати SSH-з'єднання, яким адмінить сам Pi. `install.sh` тому
питає підтвердження (`[т/N]`) і дозволяє ввести власні IP/gateway
замість дефолтних, а не застосовує зміни мовчки. `dhcpcd` вимикається
лише в межах цього опційного кроку (не для всіх встановлень) — він
конфліктує з NetworkManager, перевидаючи власні DHCP-лізинги
незалежно від `ipv4.method=manual` у профілі nmcli.

## Баг: gpiod v2 несумісний зі старим API кнопки виключення

**Симптом**: `'Chip' object has no attribute 'get_line'`, сервіс
`starlink-shutdown-button` одразу завершувався з помилкою.

**Причина**: `python3-libgpiod` на Raspberry Pi OS Bookworm+ ставить
gpiod **2.x**, де Python API повністю переписано (`chip.get_line()` +
`line.request()` з v1.x видалені; замість них — `gpiod.request_lines()`
з `LineSettings`, значення через `Value.ACTIVE`/`Value.INACTIVE`
замість `0`/`1`). Код спирався лише на v1 API.

**Виправлення**: `_init_line_v1`/`_init_line_v2` — обидві реалізації,
вибір через `hasattr(gpiod.Chip, "get_line")` (є лише в v1). Значення
з v2 конвертується в 0/1 всередині обгортки `get_value()`, решта
логіки (`watch_button()`) не залежить від версії API.

## Мережевий запит install.sh — лише при першому встановленні, не при оновленні

Питання про статичні IP (eth0/wlan0) обгорнуто умовою `MODE == "install"`
— мережа налаштовується один раз і не потребує перезапиту при кожному
`update.sh`/повторному `install.sh`. `scripts/uninstall.sh` — окремий
файл (не прапорець у `install.sh`), щоб не ускладнювати основний потік
встановлення умовними гілками, які рідко використовуються.

## Придушені конкретні Telegram-сповіщення (журнал не зачіпається)

`MUTED_DISH_ALERTS={"roaming"}`, `MUTED_ROUTER_ALERTS={"install_pending"}`,
`MUTED_ROUTER_UPDATE_STATES={"GETTING_TARGET_VERSION_FAILED"}` — на
запит користувача ці три конкретні події не надсилаються в Telegram
(шумні/непрактичні для сповіщення в реальному часі), але й далі
пишуться в журнал подій дашборду. На відміну від `IGNORED_ROUTER_ALERTS`
(повне ігнорування, включно з БД/журналом) — тут приховується лише
Telegram-звіт.

## Telegram-сповіщення про початок/кінець циклу оновлення ПЗ dish

`DOWNLOADING_UPDATE_STATES={"FETCHING","PRE_CHECK","WRITING","POST_CHECK"}`,
`ACTIVE_UPDATE_STATES` = той самий набір + `REBOOT_REQUIRED`. Перехід
з "не активного" стану в один з `DOWNLOADING_UPDATE_STATES` → "🔽
Розпочато оновлення"; повернення з будь-якого активного стану в
`IDLE` → "✅ Оновлення завершено". `REBOOT_REQUIRED`/`FAULTED`
перевіряються першими в ланцюжку `if/elif`, зберігаючи власні
специфічні повідомлення навіть при прямому переході `IDLE →
REBOOT_REQUIRED` (рідкісний edge case, коли поллінг пропустив
проміжні стани).

## Обмеження журналу watchdog-спроб при дуже тривалій недоступності

`consecutive_failures` не має верхньої межі й зростає на кожному
циклі опитування (10с), поки dish недоступний — при багатогодинній
відсутності WiFi Starlink лічильник сягає тисяч, і кожна watchdog-
спроба (кожні `MIN_REBOOT_INTERVAL_SEC`) писала окремий запис у
журнал/БД з дедалі більшим числом, без нової корисної інформації.
`MAX_LOGGED_CONSECUTIVE_FAILURES` (30) обмежує запис: спроби 1-30
логуються нормально (`watchdog_trigger` + `dish_reboot`), спроба 31
дає один фінальний маркер ("Понад 30... подальші спроби не
записуються"), спроби 32+ мовчать у журналі — але сама функція
`reboot_dish()` викликається на кожному циклі без змін, лише запис
у БД припиняється.

## Баг: Telegram-бот блокувався на повільних командах

**Симптом**: бот деколи довго (до ~15с) відповідав на команди.

**Причина**: `_handle_update()` (обробка `/status` тощо, з блокуючими
gRPC-викликами до dish/router — таймаут до `DISH_HTTP_TIMEOUT`+
router-таймаут ≈15с) виконувалась синхронно в тому самому потоці,
що й `getUpdates` polling-цикл. Поки одна команда оброблялась,
наступний `getUpdates`-запит і будь-які нові команди чекали.

**Виправлення**: `ThreadPoolExecutor(max_workers=3)` — кожен update
обробляється в окремому потоці, `_poll_once()` одразу повертається
до наступного `getUpdates` незалежно від тривалості обробки.

**Побічний ефект, виявлений і виправлений одразу**: паралельна
обробка усувала гарантію порядку виконання — `/reboot` і миттєвий
клік підтвердження від того самого користувача могли потрапити в
різні потоки пулу й завершитись у довільному порядку (callback міг
обробитись раніше за встановлення `_pending_reboot_confirm` командою
`/reboot`). Виправлено групуванням updates за `chat_id` у межах
кожного `getUpdates`-batch: той самий чат обробляється послідовно в
одному потоці (гарантує порядок), різні чати — паралельно (швидкий
чат не чекає повільний).

## Рефакторинг: спільний хелпер для update-ready reboot (dish + router)

`_maybe_reboot_for_update`/`_maybe_reboot_for_router_update` містили
майже ідентичну логіку (auto_reboot_enabled, MIN_REBOOT_INTERVAL_SEC,
insert_event, reboot_dish, notify) — об'єднано в `_reboot_for_update_ready`.
Виявлено й виправлено принагідно **другий екземпляр** того самого
reboot-loop бага, що вже виправлявся для watchdog-шляху: `last_reboot_ts`
оновлювався лише при `ok == True`, тому невдала спроба reboot при
update-ready стані не захищала від негайного повтору на наступному
циклі. Виправлено так само — оновлюється завжди, незалежно від
результату.

## Backup/restore розширено на параметри моніторингу (app/config.py)

`format_version` 1→2: `env_params` у backup містить лише **реально
перевизначені** (`overridden: True` з `config_editor.read_current_values()`)
env-параметри, не всі значення за замовчуванням — інакше відновлення
на іншій версії коду затерло б нові дефолти застарілими значеннями з
моменту створення backup. Restore записує їх через той самий
`config_editor.save_values()`, що й панель "Параметри моніторингу" —
застосовуються після перезапуску сервісів, не автоматично (щоб
restore не спричиняв неочікуваний рестарт сервісів сам по собі).

## Рефакторинг: усунення дублювання коду (webapp.py, telegram_notify.py)

`api_system_reboot`/`api_system_shutdown` (webapp.py) — спільна
логіка (виконати команду, журнал, Telegram) винесена в
`_execute_pi_power_action`, з параметризацією конкретних дієслівних
форм повідомлень (щоб текст лишався природним, не узагальненим).

`telegram_notify.append_signature()` — той самий патерн (перевірка
`get_signature_phrases_enabled()` + `_random_signature_phrase()` +
конкатенація) був продубльований тричі: у `send_message()` та двічі
в `telegram_bot.py` (`_send`, `_cmd_reboot_request`). Об'єднано в
один хелпер.

## Баг: StartLimitIntervalSec/StartLimitBurst у [Service] замість [Unit]

**Симптом**: systemd попереджав `Unknown key 'StartLimitIntervalSec'
in section [Service], ignoring` при кожному старті
`starlink-grpc-fetch.service`.

**Причина**: ці директиви ("Unit start rate limiting") належать до
розділу `[Unit]`, не `[Service]` — у неправильній секції systemd
просто ігнорує їх, обмеження кількості спроб перезапуску (5 за 30хв)
не діяло взагалі.

**Виправлення**: перенесено в `[Unit]`.

## fetch_starlink_grpc.sh: завантаження через eth0 насамперед

wlan0 (WiFi Starlink) навмисно має нижчий route-metric за eth0 (щоб
трафік до dish/router завжди йшов через WiFi) — але це ж означає, що
дефолтний маршрут для ЗОВНІШНЬОГО інтернету (завантаження
`starlink_grpc.py` з GitHub) теж намагається йти через wlan0 першим.
Якщо супутниковий канал Starlink саме недоступний (dish щойно
ввімкнувся, обслуговування, погода), інтернету через wlan0 немає
взагалі, попри робочий eth0 (домашня мережа). Виправлено: скрипт
пробує `curl --interface eth0` спочатку (якщо eth0 підключений), і
лише за невдачі падає на дефолтний маршрут.

## Telegram-сповіщення мовчали при відсутньому інтернеті на Starlink

Той самий root cause, що й для `fetch_starlink_grpc.sh`, але для
Python-коду: `requests.post`/`requests.get` до `api.telegram.org`
теж ідуть через дефолтний маршрут (wlan0), який не має інтернету,
коли супутниковий канал Starlink недоступний — саме тоді, коли
сповіщення про проблему найпотрібніші.

`telegram_notify._request_with_eth0_fallback()` — спільний хелпер:
звичайний запит спочатку, і при мережевій помилці - явний retry з
`requests.Session` + кастомний `HTTPAdapter`, що прив'язує сокет до
IP-адреси eth0 (`_get_eth0_ip()`, ioctl `SIOCGIFADDR`, Linux-специфічно).
Застосовано в `send_message()`, `test_connection()` (telegram_notify.py)
і `_api_call()` (telegram_bot.py, спільний для getUpdates/відповідей
на команди).

## Оптимізація для мобільних (смартфон/планшет)

Перевірено живими скріншотами (Playwright, 320-768px). Виправлено:
`.status-row-label{min-width:150px}` + `.progress-track{width:140px}`
переповнювали рядок на екранах <480px навіть з flex-wrap (кожен
елемент мав власний мінімум ширини, сума перевищувала viewport) —
на `max-width:480px` обидва стають `100%`/гнучкими. Додано
`viewport-fit=cover` + `env(safe-area-inset-*)` для iPhone з
"чубчиком", `-webkit-tap-highlight-color:transparent` + власні
`:active`-стани кнопок (hover не спрацьовує на дотик), збільшений
touch target кнопок на `<600px` (`min-height:44px`, за рекомендацією
Apple/Google), компактніший header і менші відступи на `<600px`,
додатковий брейкпоінт `<360px` (2-колонкова сітка, приховано підзаголовок
у header). Планшет (768px) не потребував окремих правил — наявний
`auto-fit` grid адаптується природно.

## Cache-busting для JS/CSS (застарілий кеш браузера після update.sh)

**Симптом**: після зміни коду (напр. ліміту журналу подій) браузер
користувача показував стару поведінку — `SEND_FILE_MAX_AGE_DEFAULT=3600`
кешує статику на годину, і без ручного hard refresh браузер продовжує
використовувати стару версію `dashboard.js`.

**Виправлення**: `webapp._static_v(filename)` (Jinja-глобал `static_v`)
додає `?v=<mtime файлу>` до URL `dashboard.js`/`settings.js`/`stats.js`/
`pwa.js`/`style.css` в усіх трьох шаблонах. Щойно файл змінюється
(нова версія через `update.sh`), mtime і, відповідно, URL змінюються —
браузер завантажує свіжу версію негайно, стара версія в кеші просто
не використовується (інший URL). Не застосовано до logo.png/іконок —
ті змінюються вкрай рідко, кешування на годину для них не проблема.

## Інструкція оновлення: повний шлях замість відносного

**Симптом**: `bash: scripts/update.sh: Немає такого файла або каталогу`.

**Причина**: фінальний текст `install.sh` і README радили
`sudo bash scripts/update.sh` — коректно лише якщо користувач стоїть
у розпакованому каталозі архіву. Але `update.sh`/`uninstall.sh` уже
встановлені в `/opt/starlink-monitor/scripts/`, і природний сценарій
(покласти новий архів у `~`, лишаючись у домашньому каталозі) веде
саме до цієї помилки.

**Виправлення**: усі згадки `update.sh`/`uninstall.sh` (install.sh
кінцевий текст, README) тепер вказують повний шлях
`/opt/starlink-monitor/scripts/...` — працює з будь-якого поточного
каталогу. `install.sh` (перше встановлення) лишився відносним — той
контекст завжди одразу після `cd` у розпакований архів.

## eth0-fallback для Telegram: SO_BINDTODEVICE, не прив'язка до адреси

**Симптом**: реальні логи показали, що fallback спрацьовує (лог
"пробую через eth0" є), але падає з `NameResolutionError` навіть при
явному DNS-запиті через eth0.

**Причина**: прив'язка сокета до IP-адреси (`source_address`)
прив'язує лише ЗАЯВЛЕНУ джерельну IP пакета. Linux обирає ФІЗИЧНИЙ
інтерфейс за таблицею маршрутизації на основі адреси ПРИЗНАЧЕННЯ,
повністю ігноруючи джерельну IP сокета (якщо не налаштована окрема
policy-based routing на рівні ОС). Тобто пакет із заявленим джерелом
`192.168.0.95` (eth0) усе одно фізично йшов через `wlan0` (бо туди
веде маршрут до `8.8.8.8`) і там же й губився — те саме стосувалось і
DNS-резолвінгу (системний резолвер теж іде тим самим шляхом).

**Виправлення**: `SO_BINDTODEVICE` — системний виклик, що реально
форсує фізичний інтерфейс незалежно від таблиці маршрутизації.
Вимагає `CAP_NET_RAW` — додано через `AmbientCapabilities=CAP_NET_RAW`
у `starlink-monitor.service` й `starlink-webui.service` (сумісно з
`NoNewPrivileges=true` — ambient capability надається systemd до
запуску процесу, не через runtime privilege escalation).
`CapabilityBoundingSet=CAP_NET_RAW` звужено лише в `starlink-monitor.service`
(не викликає sudo) — у `starlink-webui.service` свідомо НЕ звужено,
бо bounding set успадковується навіть дочірнім `sudo systemctl
reboot/poweroff`, і звуження забрало б потрібні для reboot
можливості (`CAP_SYS_BOOT` тощо).

Python: `_Eth0BoundAdapter` (urllib3 `socket_options`) для HTTP;
`_resolve_via_eth0()` — DNS-запит через сокет із явним
`SO_BINDTODEVICE` (`dns.query.udp(..., sock=...)` — власний сокет, не
dnspython's вбудований resolver). Коли й системний DNS не
резолвиться — запит іде напряму на резолвлений IP з `Host` заголовком
і `verify=False` (SNI/hostname-matching неможливий без підміни за IP;
ланцюжок довіри сертифіката лишається валідним, лише перевірка імені
пропускається — свідомий компроміс для вузького фолбек-вікна).

## Баг: WAN-failover не діяв — NetworkManager відновлював свій metric

**Симптом**: лог `wan_failover_check.sh` щоразу (кожні ~20с) рапортував
"знижую пріоритет", хоча мав це вже зробити раніше — реальна таблиця
маршрутів показувала, що `wlan0` так і лишався пріоритетним.

**Причина**: пряма зміна таблиці маршрутів (`ip route`) в обхід
NetworkManager не працює надійно — той сам володіє `wlan0` і
періодично перевідновлює власний `metric` із persistent-конфігурації
з'єднання, ігноруючи зовнішні зміни.

**Виправлення**: керування через сам NetworkManager — `nmcli
connection modify ipv4.route-metric` + `nmcli device reapply` (без
повного перепідключення WiFi). Той самий підхід і в `uninstall.sh`
(відновлення metric при видаленні проєкту).

## Баг: WAN-failover ламав доступ до dish

**Симптом**: після демотування `wlan0` (Starlink без інтернету) Pi
переставав бачити сам dish (`192.168.100.1`), хоча router
(`192.168.1.1`) і локальна мережа лишались доступні.

**Причина**: `192.168.1.0/24` (router) має автоматичний kernel-scope
маршрут (власна підмережа wlan0) — завжди пріоритетніший за дефолтний.
Але `192.168.100.0/24` (dish) такого маршруту не має — трафік туди
йшов лише через дефолтний маршрут, який WAN-failover якраз і
демотував.

**Виправлення**: `install.sh` додає постійний окремий маршрут
(`nmcli +ipv4.routes "192.168.100.0/24 $WLAN_GW"`) на wlan0-з'єднанні
— незалежний від стану WAN-failover.

## WAN-failover сам спричиняв флапи dish — додано гістерезис

**Симптом**: часті сповіщення "Dish знову online" (1-4 невдалі
спроби), кожні кілька хвилин, без obstruction/alerts.

**Причина**: `journalctl` підтвердив точний часовий збіг — кожен флап
dish стається в ту саму секунду, що й `nmcli device reapply` в
`wan_failover_check.sh`. Reapply на мить розриває маршрут до dish;
переключення стається на кожному одиничному "провалі" ping, що
призводить до петлі самопідживлення (reapply впливає на результат
наступної ж перевірки).

**Виправлення**: гістерезис — перемикання лише після
`REQUIRED_CONSECUTIVE=3` поспіль однакових результатів перевірки
(стан у `/run/starlink-wan-failover.state`, tmpfs). Одиничні флапи
більше не тригерять reapply.

## Баг: DISPLAY_ROTATION=90 не працював для 170×320

**Симптом**: `starlink-display.service` падав з `ValueError: Invalid
rotation 90 for 170x320 resolution` при кожному запуску.

**Причина**: бібліотека `st7789` забороняє `rotation=90/270` для
прямокутних (не квадратних) дисплеїв — лише `0`/`180` валідні, коли
`width != height`. Дефолт `DISPLAY_ROTATION=90` був помилковим
припущенням про можливість landscape через rotation-параметр.

**Виправлення**: дефолт змінено на `0` (portrait, без обертання).
Landscape-монтаж вимагає поміняти місцями `WIDTH`/`HEIGHT`
(320×170), не rotation.

## Баг: підсвітка працює, зображення немає (RST не виводився з reset)

**Симптом**: сервіс ініціалізувався без помилок, підсвітка перемикалась
кнопкою, але екран лишався порожнім — жодного зображення.

**Причина**: бібліотека `st7789` в `__init__` налаштовує RST-пін як
output зі стартовим станом LOW (reset-активний), і одразу викликає
`_init()` (SPI-команди ініціалізації контролера) — **до** того, як
RST взагалі підіймається в HIGH. Контролер весь цей час у апаратному
reset і ігнорує всі SPI-команди. Підсвітка (BL) — окрема GPIO-лінія,
не залежить від стану RST, тому світилась нормально попри порожній
екран.

**Виправлення**: після створення `st7789.ST7789(...)`, явно
викликається `display.reset()` (правильна HIGH→LOW→HIGH послідовність
через публічний метод бібліотеки) і **повторно** `display._init()`
(команди з першого виклику в `__init__` контролер проігнорував, поки
був у reset).

## Баг: підтвердження мережевого запиту install.sh не розпізнавалось

**Симптом**: користувач вводив "y" на запит "Налаштувати статичні IP...",
але скрипт показував "Пропущено" (гілка "ні").

**Причина**: `read -r -p ... SETUP_NET` міг захопити прихований `\r`
(термінал користувача) поруч із відповіддю — `[[ "$SETUP_NET" =~
^[TtYyТт] ]]` це не мав би зачепити (regex перевіряє лише перший
символ), але combінація з можливими іншими невидимими символами
могла давати false negative.

**Виправлення**: `SETUP_NET="$(echo "$SETUP_NET" | tr -d
'[:space:]')"` перед перевіркою — прибирає всі пробільні символи
(включно з `\r`), надійніше розпізнає підтвердження.

## Заміна бібліотеки дисплея на Adafruit CircuitPython ST7789

**Причина заміни**: попередня бібліотека мала кілька реальних
проблем, знайдених на живому Pi — RST-баг (`__init__` викликав
`_init()` до виведення RST з reset-стану, вимагало ручного
`reset()`+`_init()` workaround), заборону `rotation=90/270` для
прямокутних дисплеїв (`width != height`), і залишалась невирішена
проблема з шумом/orientaцією, яку так і не вдалось остаточно
діагностувати.

**Нова бібліотека**: `adafruit-circuitpython-rgb-display` +
`adafruit-blinka` (`adafruit_rgb_display.st7789.ST7789`). Перевірено
читанням вихідного коду бібліотеки (не здогадками):
- `DisplaySPI.__init__` сам коректно виводить RST з reset (`rst.value=0`
  → `switch_to_output` → `self.reset()` — LOW→sleep→HIGH→sleep) ДО
  виклику `init()` (SPI-команди) — попередній RST-баг тут відсутній;
- `rotation` дозволяє `0/90/180/270` для будь-якого aspect ratio —
  жодного обмеження на `width==height`;
- обертання застосовується програмно (`img.rotate()` на PIL-зображенні
  в методі `image()`), не через MADCTL-регістр;
- **немає** `set_backlight()` — BL-пін керується напряму окремим
  `digitalio.DigitalInOut` в `app/display.py` (`_set_backlight()`).

**Архітектурні зміни**: ініціалізація тепер через `board`/`digitalio`/
`busio` (Blinka) замість простих цілих BCM-номерів; CS — bit-banged
GPIO (`DISPLAY_SPI_CS_PIN`, дефолт 8), не апаратний номер CE0/CE1
(`STARLINK_DISPLAY_SPI_PORT`/`STARLINK_DISPLAY_SPI_CS` видалено).
`display.image(img)` замість `display.display(img)`.

**Попутно знайдено й видалено**: дублікат-сирота
`DISPLAY_BACKLIGHT_TIMEOUT_SEC` в `config.py` (той самий концепт, що
й `DISPLAY_BACKLIGHT_AUTO_OFF_SEC`, ніде не використовувався).

## Баг: WAN-failover падав з "Read-only file system" на /run

**Симптом**: `starlink-wan-failover.service` падав щоразу (кожен запуск
таймера, ~20с) з `Read-only file system` при спробі записати файл
стану в `/run/starlink-wan-failover.state`. WAN-failover фактично
ніколи не спрацьовував — виявлено на реальному Pi через симптом
"немає інтернету", хоча один з двох інтерфейсів (`eth0`) мав робоче
з'єднання, а маршрут за замовчуванням команду через непрацюючий
`wlan0` (Starlink).

**Причина**: `ProtectSystem=strict` в unit-файлі робить **всю**
файлову систему read-only, окрім явно дозволених шляхів — `/run` сам
по собі НЕ звільнений автоматично від цього обмеження без явного
`RuntimeDirectory=`/`ReadWritePaths=`.

**Виправлення**: `RuntimeDirectory=starlink-wan-failover` (systemd
створює `/run/starlink-wan-failover/` і дозволяє запис туди навіть під
`ProtectSystem=strict`) + `RuntimeDirectoryPreserve=yes` (без цього
systemd видаляє директорію одразу після кожного завершення oneshot-
сервісу — файл стану/гістерезис був би втрачений між кожним запуском
таймера). Шлях у скрипті змінено з `/run/starlink-wan-failover.state`
на `/run/starlink-wan-failover/state`.

## Баг: pip install падав на rpi_ws281x/RPi.GPIO (Python.h відсутній)

**Симптом**: `pip install -r requirements.txt` падав з `fatal error:
Python.h: No such file or directory` при компіляції `rpi_ws281x` та
`RPi.GPIO` (транзитивні залежності `adafruit-blinka` для реального
GPIO-доступу на Raspberry Pi).

**Причина**: `install.sh` не встановлював `python3-dev` (заголовкові
файли Python, потрібні для компіляції будь-яких C-розширень) —
раніше цього не було потрібно, бо попередня бібліотека дисплея не
мала подібних транзитивних C-залежностей.

**Виправлення**: додано `python3-dev build-essential` до списку
apt-пакетів в `install.sh`. Діє лише для нових встановлень
(`MODE=install`) — на вже встановлених системах потрібно виконати
`sudo apt-get install -y python3-dev build-essential` вручну один раз.

## Баг: кирилиця не відображалась на фізичному дисплеї

**Симптом**: український текст ("Оновлення:", "г"/"хв" в uptime тощо)
на TFT-дисплеї не показувався коректно.

**Причина**: `install.sh` не встановлював жодного шрифтового пакету.
`_load_font()` шукає `DejaVuSansMono-Bold.ttf`/`DejaVuSans-Bold.ttf`
за стандартними Debian-шляхами (`/usr/share/fonts/truetype/dejavu/`),
які надає пакет `fonts-dejavu-core` — без нього на мінімальній
системі (Raspberry Pi OS Lite) цих файлів немає, і код тихо (без
попередження) переходив на `ImageFont.load_default()`. Перевірено
функціонально (не лише за типом об'єкта, який у Pillow 10+ завжди
`FreeTypeFont` для обох випадків): різні кириличні літери в цьому
fallback-шрифті рендерились **ідентичним** растровим візерунком
("відсутній гліф"-заглушка), тобто кирилиця справді не підтримується.

**Виправлення**: додано `fonts-dejavu-core` до apt-пакетів в
`install.sh`. Додатково `_load_font()` тепер логує явне попередження,
якщо жоден шрифт з `FONT_PATHS` не знайдено — щоб цю проблему було
видно одразу в журналі, а не виявляти постфактум за зовнішнім
виглядом екрана.

## Баг: довге натискання кнопки не вимикало Pi (NoNewPrivileges)

**Симптом**: коротке натискання (підсвітка) працювало бездоганно,
довге утримання давало в логах `"Кнопка виключення утримана 3.0с ...
- виконую poweroff"`, але одразу після цього — `sudo: The "no new
privileges" flag is set, which prevents sudo from running as root`.
Pi фактично не вимикався.

**Причина**: `starlink-display.service` мав `NoNewPrivileges=true` —
залишок з часів, коли дисплей-сервіс дійсно не виконував жодних
sudo-дій. Коли логіку кнопки виключення (включно з `sudo systemctl
poweroff` на довге натискання) перенесли з окремого
`shutdown_button.py`-сервісу в `display.py` (щоб уникнути конфлікту
за GPIO-пін — див. відповідний запис вище), unit-файл забули
оновити — коментар і далі стверджував "жодних sudo-дій".

**Виправлення**: `NoNewPrivileges=true` видалено з
`starlink-display.service`. `sudoers.d`-правило (`NOPASSWD:
/bin/systemctl poweroff`) уже було на місці й не потребувало змін —
проблема була виключно в systemd security-прапорі, що блокував сам
виклик `sudo` зсередини процесу, незалежно від того, чи дозволено
команду в sudoers.

## Зменшення частоти записів на SD-картку

**Зміна**: `PRAGMA synchronous=NORMAL` (замість дефолтного `FULL`)
для WAL-режиму — офіційно рекомендований SQLite-документацією режим,
що зменшує кількість `fsync()`-викликів (лише при checkpoint, не на
кожному commit metric-опитування кожні ~10с). Безпечно — WAL сам
гарантує захист від пошкодження БД; ризик лише у втраті кількох
останніх транзакцій при раптовому знеструмленні.

**Розглянуто, але НЕ застосовано автоматично**: `Storage=volatile`
для `systemd-journald` (журнал у RAM замість SD-картки) дав би значно
більший виграш, АЛЕ ціною повної втрати `journalctl`-історії між
перезавантаженнями — критично важливий інструмент діагностики, яким
активно користувались протягом усієї розробки цього проєкту (напр.
для знаходження RST-бага дисплея, `NoNewPrivileges`-бага кнопки
виключення тощо). Це реальний trade-off, що вимагає свідомого вибору
користувача, не мовчазного застосування:
```
# Опційно, лише якщо свідомо приймаєш втрату журналів між reboot:
echo "Storage=volatile" | sudo tee -a /etc/systemd/journald.conf
sudo systemctl restart systemd-journald
```

## starlink_grpc.py винесено як vendor-файл для відтворюваності збірки

**Було**: `install.sh` при кожному першому встановленні запускав
`starlink-grpc-fetch.service` у фоні, який динамічно завантажував
`starlink_grpc.py` з GitHub (sparky8512/starlink-grpc-tools) при
старті. Це означало: (а) встановлення залежало від доступності
інтернету саме в той момент, (б) різні інсталяції могли отримати
різні версії файлу залежно від того, коли саме встановлювались, (в)
upstream міг випустити несумісну зміну без нашого відома/тестування.

**Стало**: реальний файл (перевірено — синтаксично валідний, реально
імпортується з `grpc`+`yagrc`) завантажено один раз і покладено в
`app/vendor/starlink_grpc.py` як частину архіву проєкту.
`starlink_client.py` не потребував жодних змін — уже мав graceful
fallback (`from app.vendor import starlink_grpc` / `except ImportError:
starlink_grpc = None`), розрахований саме на цей шлях.
`starlink-grpc-fetch.service` і далі встановлюється (для опційного
ручного оновлення до найновішої upstream-версії), але більше не
`enable`/`start` автоматично з `install.sh`. Ліцензія файлу
залишається окремою (upstream-автора), не MIT цього репозиторію —
явно зазначено в README.

## Сповіщення про зміну версії прошивки dish/router

**Реалізація**: `upsert_known_device_dish()`/`upsert_known_device_router()`
вже обчислювали `version_changed` внутрішньо (для `*_updated_ts` полів),
просто не повертали його назовні. Змінено повертати `(real_change,
old_version)` — `monitor.py` надсилає Telegram-сповіщення, коли
`real_change=True`.

**Знайдений і виправлений edge case**: перша версія логіки вважала
"зміною" будь-яку ситуацію, коли рядок `known_devices` уже існував
(`existing is not None`), незалежно від того, чи конкретне ПОЛЕ
(`dish_software_version`/`router_software_version`) було раніше `NULL`.
Оскільки dish і router опитуються в різних циклах і можуть створити
спільний рядок `known_devices` першим (за `dish_id`), перше заповнення
"свого" поля (наприклад router вперше отримує `router_software_version`,
хоча рядок уже існував через dish) хибно рахувалось "зміною версії з
None". Виправлено: `real_change` тепер `old_version is not None and
old_version != new_version` — перевіряє саме ПОЛЕ, не факт існування
рядка. Перевірено живим тестом обох симетричних сценаріїв (dish
першим/router першим).

## Графіки трендів на /stats — без сторонньої JS-бібліотеки

**Рішення**: замість Chart.js (чи подібної, зазвичай завантажується
з CDN) — написано власний, малий `drawLineChart()` на голому Canvas
API (`static/stats.js`). Причина: цей дашборд саме про стан мережі —
якщо покластись на CDN-залежність, графіки не завантажаться саме
тоді, коли dish offline і користувачу найбільше потрібно подивитись
історію.

**Дані**: `db.get_metrics_chart_data(hours)` — SQL `GROUP BY` bucket
"на льоту" з таблиці `metrics` (не окрема downsampled-таблиця —
перевірено, що жодна наявна функція/endpoint не читає дані старші за
~14 годин, тому downsampling поки дав би лише зменшення розміру БД,
без візуальної користі; вирішено спершу зробити графіки видимими).
Bucket-розмір масштабується як `period_sec / 150` — довший період
(30д) не повертає пропорційно більше даних, завжди ~150 точок.

**Знайдений і виправлений під час тестування баг**: невалідний
query-параметр (`?hours=abc`) кидав `500 Internal Server Error`
(`float("abc")` без обробки). Той самий патерн уже був у наявному
`/api/history?limit=abc` (не виправлено — поза межами цього завдання),
але для нового `/api/metrics-chart` додано `try/except` з fallback на
дефолт.

## Downsampling старих метрик

**Реалізація**: `downsample_old_metrics()` агрегує raw-рядки
(`metrics`) старші за `DOWNSAMPLE_AFTER_DAYS` (дефолт 3) у
`DOWNSAMPLE_BUCKET_SEC`-секундні (дефолт 300) середні, окрема таблиця
`metrics_downsampled`, видаляючи оригінальні детальні рядки.
Викликається щогодини разом з `prune_old()` (яку теж розширено —
очищує `metrics_downsampled` за повною `HISTORY_RETENTION_DAYS`-межею).

**Ключове архітектурне рішення**: `get_metrics_chart_data()` тепер
`UNION ALL` обидві таблиці з тим самим `cutoff = now - period` для
обох частин запиту — це елегантно уникає потреби явно знати поріг
downsample у самому query. Де `downsample_old_metrics()` вже перенесла
дані, там `metrics` для цього періоду просто порожній, і UNION ALL
природно бере відповідні рядки з `metrics_downsampled` замість них —
без спеціальної гілки коду типу "якщо період > DOWNSAMPLE_AFTER_DAYS,
роби інакше".

**Перевірено живим тестом** (найважливіший сценарій): графік за 7
днів дає **точно ту саму** кількість точок (151) і **нуль** прогалин
до і після виклику `downsample_old_metrics()` — підтверджує, що
перехід від raw до downsampled даних на межі cutoff справді
безшовний, не просто в теорії.

## Групування спаму reboot-сповіщень

**Проблема**: `MIN_REBOOT_INTERVAL_SEC` (180с) гарантує, що реальні
reboot-спроби не частіші за раз на ~3хв, але не запобігає тому, щоб
flapping (dish то доступний, то ні) генерував Telegram-повідомлення
кожні 3хв протягом години й довше — кожне технічно виправдане, але
сукупно виглядає як спам. Існуючий `NOTIFICATIONS_MUTE_AFTER_SEC`
тут не допомагає — той механізм про ОДНУ тривалу безперервну відмову,
а не про частоту КОРОТКИХ окремих циклів.

**Реалізація**: `_notify_reboot()` — ковзний список timestamps
надісланих reboot-сповіщень; при `REBOOT_SPAM_THRESHOLD`+ за
`REBOOT_SPAM_WINDOW_SEC` — одне попередження про групування, далі
мовчки рахує до затишшя (`_check_reboot_spam_recovery()`, викликається
на початку кожного `poll_once()`), тоді підсумкове повідомлення й
повний скид стану — новий цикл флапу після recovery поводиться знову
з нуля.

**Перевірено живим тестом** усі 5 етапів по черзі (нижче порогу →
досягнення порогу → тихий підрахунок → recovery-підсумок → новий
цикл після скидання), включно з підтвердженням, що
`_check_reboot_spam_recovery()` реально автоматично викликається з
`poll_once()`, не лише вручну в тесті.

## Типізація (mypy) — пропорційний підхід, без --strict/CI

**Контекст**: запит на full `mypy --strict` + CI. Перевірено реально
(не гіпотетично): `mypy --strict` на тодішньому стані коду дав **366
помилок у 13 файлах**, при 20% функцій з return type annotation.
Головні джерела: SQLite `dict(row)`-патерни всюди в `db.py`, і
`app/vendor/starlink_grpc.py` — 1799 рядків чужого коду.

**Рішення**: пропорційний підхід замість full-strict retrofit +
CI-інфраструктури з нуля (якої в проєкті немає взагалі) — одноосібний
hobby-проєкт на одному Pi, перевіряється живим тестуванням на
реальному залізі (не automated test suite), CI не додав би
пропорційної цінності:
1. Return type hints для **всього** власного коду (не `--strict`,
   звичайний режим) — усі 10 файлів `app/` (крім vendor)
2. `mypy.ini` — `ignore_errors=True` для `app.vendor.*`,
   `ignore_missing_imports` для hardware-специфічних (`gpiod`,
   `board`, `digitalio`, `busio`, `adafruit_rgb_display`) і сторонніх
   без офіційних stubs (`speedtest`, `dns`, `requests`, `psutil`)
3. `mypy` запускається локально/вручну (`requirements-dev.txt`), не
   в CI — інструмент розробки, не production-залежність Pi

**Результат**: `mypy app/` → `Success: no issues found in 17 source
files`.

**Реальні баги, знайдені й виправлені під час типізації** (не просто
додавання анотацій — mypy реально спіймав логічні помилки):
- `StarlinkClient.__init__(dish_addr: str = None, ...)` та кілька
  подібних — PEP 484 явно забороняє неявний `Optional`
- `starlink_client.py`: `starlink_grpc = None` (graceful fallback при
  відсутньому vendor-модулі) конфліктувало з типом "модуль", виведеним
  з успішного `import` — виправлено явним
  `starlink_grpc: Optional[types.ModuleType]`
- `monitor.py`: **власна помилка** — типізував `poll_once()` як
  `-> None`, хоча метод реально повертає `DishStatus`; 6 полів у
  `Watchdog.__init__` (`prev_update_state`, `first_failure_ts` тощо)
  оголошені як `None` без `Optional`, хоча пізніше присвоюються
  реальні значення; `last_prune = 0` (int) замість `0.0`, порівнюване
  з `time.time()` (float)
- `config_editor.py`: `read_current_values() -> dict` — сигнатура,
  що існувала й РАНІШЕ, виявилась неправильною (функція реально
  повертає `list[dict]`) — знайдено лише зараз, під час типізації
- Повторюваний патерн у 4+ місцях (`speedtest_runner.py`,
  `system_metrics.py`, `display.py`, `telegram_bot.py`): `result =
  {"key": значення}` — перше значення "звужує" тип для mypy,
  подальші присвоєння інших типів у той самий словник/список
  конфліктують. Рішення завжди однакове: explicit `dict[str, Any]`
  (чи `list[dict[str, Any]]`) при створенні

## Мобільний PWA офлайн-режим — localStorage-кеш останнього стану

**Оновлює попереднє рішення**: `sw.js` мав явний коментар "жодного
кешування API-відповідей... показ застарілих даних Starlink офлайн
було б оманливим". Це рішення НЕ скасовано (service worker і далі
не кешує API на своєму рівні) — додано ОКРЕМИЙ механізм на рівні
`dashboard.js` з явним маркуванням застарілості (банер + "X хв тому"),
що вирішує саме те занепокоєння, яке спричинило первісне рішення:
показ старих даних БЕЗ індикатора був би оманливим, показ старих
даних З чітким індикатором — корисний UX для мобільного сценарію
(вийшов з WiFi-зони дії Pi, хочеш побачити останній відомий стан, не
порожній екран).

**`localStorage`, не `IndexedDB`**: дані — один невеликий JSON-об'єкт
("останній `latest`"), не потребує транзакцій/великого обсягу/
структурованих запитів, які виправдовували б складніший асинхронний
API `IndexedDB`. Простіший синхронний `localStorage` достатній і
пропорційний задачі.

**Реалізація**: `refreshStatus()` розділено — рендеринг винесено в
окрему `_renderStatusData(latest)`, перевикористовувану і для live-
даних (успішний fetch), і для кешованих (fetch провалився). Формат
"X хв тому" (`fmtAgo()` в `common.js`) — той самий, що вже був у
`telegram_bot.py._fmt_ago()`, для консистентності між Telegram і
веб-UI.

**Перевірено живими тестами**: повний цикл (успіх кешує + ховає
банер → невдача показує кеш + банер з правильним "щойно"/"X хв тому"),
і граничний випадок — перше відкриття без жодного попереднього кешу
при одразу недоступному Pi: код коректно НЕ звертається до банера
взагалі (немає що показати), не намагається відрендерити порожні дані.

**Побічна знахідка, ще НЕ виправлена** (виходить за межі цього
завдання, лише занотовано): `templates/index.html` підключає Chart.js
через CDN (`cdnjs.cloudflare.com`) для `throughputChart` — це прямо
суперечить принципу "без CDN-залежності" (застосованому пізніше для
графіків на `/stats`, власний canvas без сторонніх бібліотек). Якщо
CDN недоступний (типовий offline-сценарій, який цей самий feature
покращує), `throughputChart` на головній сторінці не працюватиме
взагалі. Вартий окремого виправлення.

## Баг: `pip install --upgrade -r requirements.txt` оновлював незмінені пакети

**Знайдено на реальному Pi** (не гіпотетично): після оновлення лише
"безпечних" пакетів (Flask/requests/dnspython/yagrc) у requirements.txt
попереднього разу, `pip freeze` на Pi показав, що
`adafruit-blinka` теж оновився (8.x→9.2.0) — пакет, який ми
**explicitly домовились не чіпати** (hardware-критичний для
TFT-дисплея, major-стрибок, неможливо перевірити без реального
заліза). Той самий блок торкнувся і protobuf (→7.35.1), Pillow
(→12.3.0), psutil (→7.2.2), grpcio (→1.83.0) — усіх пакетів у файлі,
не лише тих, чий рядок реально змінився.

**Причина**: `install.sh` викликав `pip install --upgrade -r
requirements.txt` — прапорець `--upgrade` застосовується до **всього**
файлу одразу: коли `>=`-піни, pip підтягує найновішу версію, що
задовольняє КОЖЕН рядок, незалежно від того, чи саме цей рядок
змінився в git-diff requirements.txt. Зміна номера версії ХОЧА Б
ОДНОГО пакета (що тригерить `REQ_CHANGED=1`) фактично означала "онови
все до найновішого".

**Виправлення**: `requirements.txt` тепер має **виключно точні `==`
піни** (не `>=`) для всіх пакетів — на версіях, підтверджених реально
встановленими й working на Pi (`pip freeze` з живого пристрою,
користувач підтвердив дисплей і зв'язок з dish справні). `install.sh`
більше НЕ використовує `--upgrade` — з точними пінами звичайний `pip
install -r requirements.txt` природно ідемпотентний (не займає пакет,
чий pin уже задоволений) і торкається ЛИШЕ пакетів, чий точний pin
реально змінився в наступних версіях файлу.

**Перевірено живим тестом** (ізольований venv у пісочниці): `pip
install pkg==X` двічі поспіль без `--upgrade` не робить нічого другого
разу (той самий pin); зміна на `pkg==Y` реально встановлює Y —
підтверджує, що новий механізм справді торкається лише зміненого.

## Сповіщення про встановлення очікуваної версії прошивки

**Реалізація**: `/settings` дозволяє явно вказати ОЧІКУВАНУ версію
(dish/router), і отримати "✅ Останнє оновлення..." саме коли
встановлена версія їй відповідає. Окремо від уже наявного "🔄
прошивка змінилась" (спрацьовує на БУДЬ-ЯКУ зміну) — цей новий
механізм про конкретну, заздалегідь відому версію.

**Дедублікація без окремого boolean-прапорця**: `dish_target_notified`
зберігає САМЕ ЗНАЧЕННЯ target, про яке вже сповістили — порівняння
`notified == target` природно "скидається", коли користувач вводить
НОВИЙ target, без потреби explicit очищати стан десь окремо.

**Першочергове введення**: `GET /api/target-versions` повертає й
`dish_current`/`router_current` — `settings.js` `loadTargetVersions()`
показує поточну відому версію як стартове значення інпута, коли
target ще не задано, замість порожнього поля.

**Знайдена й виправлена прогалина під час реалізації**: нові
налаштування спочатку не потрапляли в `/api/settings-backup`/
`/api/settings-restore` — виявлено і виправлено одразу (перевірено
живим тестом повного циклу backup→restore на "чистому" стані БД).

**Перевірено живими тестами**: усі 5 сценаріїв дедублікації (немає
target / не збігається / збіглось → сповіщення / повтор → без спаму /
новий target → нове сповіщення), pre-fill логіка (обидва варіанти:
target порожній показує current, target уже заданий показує саме
його), повний Flask API-цикл GET/POST, повний backup→restore цикл.

## Очікувана версія прошивки — валідація "лише новіші"

**Реалізація**: `POST /api/target-versions` відхиляє нову версію,
якщо вона старіша за вже відому (максимум із попереднього target і
поточної встановленої версії) — захист від випадкового відкату
(описка, забутий раніше введений новіший target).

**`_version_key()`** — толерантний компаратор для формату
`YYYY.MM.DD.mrXXXXX.N` (не строгий semver, Starlink не документує
формально). Дата-префікс домінує як найнадійніший індикатор "новіше"
(перевірено на реалістичних прикладах: різні дати, однакова дата з
різним mr-номером, ідентичні версії — усі 5 тестових пар дали
правильний результат). Fallback на посегментне порівняння, коли дата
відсутня чи однакова в обох — не падає на нетиповому форматі
(перевірено: `v1.2.3`, порожній рядок, довільний текст).

**Часткова відмова**: dish і router валідуються незалежно — якщо
одне поле старіше, а інше новіше, валідне зберігається, невалідне
відхиляється окремо з поясненням (не "усе або нічого" для обох полів
одночасно). Перевірено живим тестом — саме цей змішаний сценарій.

**Перевірено живими тестами**: перше введення (=поточна встановлена,
приймається), спроба ввести старішу (відхилено, target реально НЕ
перезаписаний), новіша (приймається), змішаний dish-valid/router-
invalid сценарій, відображення реального повідомлення на фронтенді
(не generic "Помилка"), граничні випадки компаратора (нестандартні
формати не падають).
